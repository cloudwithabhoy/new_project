# 4.1 — Deploy the rest of the fleet (the other 11 services)

## Goal
By the end of this part every service in the `shop` namespace is running: `api-gateway`, `auth`, `user`,
`search`, `cart`, `order`, `payment`, `inventory`, `notification`, `recommendation`, and `frontend`
(plus `catalog`, already up from `3.2`). They can all **find and call each other** by name, and the JWT
that `auth` mints will verify everywhere because every replica shares one fixed signing key. You will not
wire up Kafka events yet (that's `4.2`) or lock down traffic (that's `4.3`) — this part is purely "bring
the 11 boxes up and let them talk."

## Why this part exists (read this first)
In `3.2` you proved the **five-object deploy recipe** on exactly one service (`catalog`): ConfigMap +
Secret + Deployment + Service + Ingress. That was deliberate — nail the shape once, and the rest are the
same shape with different names. This part cashes in that investment: you repeat the recipe 11 times.

But two things become real only once there is more than one service, and they're the whole point of this
part:

- **Service-to-service discovery.** `catalog` talked to a *database*. Now `order` has to talk to `payment`,
  `cart` has to talk to `catalog`, `api-gateway` has to talk to all of them. How does one pod find another
  pod's address when pods come and go and their IPs change constantly? The answer is **cluster DNS**, and
  you'll wire it through `*_URL` environment variables.
- **A shared signing key for auth.** `auth` signs JWTs; `api-gateway` verifies them. If `auth` runs 2
  replicas and each signs with a *different* key, half your logins break at random. So `auth` needs **one
  fixed key**, shared by every replica, that survives restarts.

> NEW CONCEPT — cluster DNS service discovery. Inside the cluster there is a built-in DNS server
> (**CoreDNS**, running in `kube-system`). Every `Service` object you create automatically gets a DNS
> name of the form `<service>.<namespace>.svc.cluster.local`. So the moment you create a Service named
> `payment` in `shop`, any pod can reach it at `payment.shop.svc.cluster.local` — and from *within* the
> `shop` namespace, the short name `payment` resolves too. **How it works:** the Service has a stable
> virtual IP (its ClusterIP); CoreDNS maps the name to that IP; the IP load-balances across whichever
> pods are currently ready. **Why we use it here:** pod IPs are ephemeral and change on every restart and
> scale event — you can never hardcode them. The Service name is the *one* stable handle. **Why it fits
> vs alternatives:** you could run your own service registry (Consul, Eureka) and have apps call it, but
> Kubernetes gives you DNS-based discovery for free, with zero app code — so we use the native thing.

## Prerequisites
- [`3.1`](./3.1-datastores.md) — all datastores up in `data`: `postgres-auth`, `postgres-user`,
  `postgres-order`, `postgres-payment`, `postgres-inventory`, `postgres-recommendation`, plus **Redis**
  (for cart), **Elasticsearch** (for search), and **Kafka** (KRaft) as `kafka` in `data`.
- [`3.2`](./3.2-deploy-catalog.md) — `catalog` already running; you know the five-object recipe cold.
- All 11 images already in ECR as `ecom-repo:<svc>-<sha>` (built by Jenkins in Phase 01).

Use the exact env-var keys from each service's `README.md` ("DevOps handoff") — they're reproduced inline
below so you don't have to flip back and forth.

> NEW CONCEPT — database-per-service (why each service gets its OWN ConfigMap + Secret). You may wonder why
> we don't make one big shared `shop` ConfigMap. We don't, on purpose. Each microservice owns **its own
> datastore** — `auth` has `postgres-auth`, `order` has `postgres-order`, and neither can read the
> other's tables. **How it works:** every service gets its own ConfigMap (its port, its `DB_HOST`, the
> URLs of services it calls) and its own Secret (its DB password). **Why we use it here:** it keeps
> services decoupled — you can change `order`'s schema without touching `auth`, and a leaked `cart` Secret
> can't unlock `payment`'s database. **Why it fits vs alternatives:** a single shared database is simpler
> on day one but couples every team to one schema and one blast radius; database-per-service is the
> standard microservice pattern and it's what this project is built to teach.

## The repeatable per-service recipe (memorize this once)
Every service below is the **identical five objects from `3.2`**, varying only by name, port, env keys,
and which other services it calls. The shape is always:

```
   ConfigMap  (non-secret config: PORT, LOG_LEVEL, DB_HOST..., and *_URL of callees)
   Secret     (DB_PASSWORD / REDIS_PASSWORD / JWT key — the sensitive bits)
   Deployment (2 replicas, envFrom the ConfigMap + Secret, liveness /healthz, readiness /readyz)
   Service    (stable ClusterIP + DNS name on the service's port)
   Ingress    (ONLY for the two public edges: api-gateway and frontend)
```

Most services are **internal** — they get ConfigMap + Secret + Deployment + Service, but **no Ingress**.
Only `api-gateway` and `frontend` face the internet, so only those two get an Ingress. Everything else is
reached purely by in-cluster DNS.

Here is the full port + dependency map you'll wire up. Keep it next to you:

```
   service          port   datastore                 calls (set these *_URL)
   ───────────────────────────────────────────────────────────────────────────────
   auth             8081   postgres-auth             user
   user             8082   postgres-user             (none — leaf)
   catalog          8083   postgres-catalog          (none — done in 3.2)
   search           8084   elasticsearch             catalog (only on /reindex)
   cart             8085   redis                     catalog
   order            8086   postgres-order            cart, payment, inventory
   payment          8087   postgres-payment          (none — leaf)
   inventory        8088   postgres-inventory        (none — async consumer in 4.2)
   notification     8089   (none — stateless)        (none — async consumer in 4.2)
   recommendation   8090   postgres-recommendation   (none — async consumer in 4.2)
   api-gateway      8080   (none)                    auth,user,catalog,search,cart,order,recommendation
   frontend         3000   (none)                    api-gateway (via the BROWSER, not in-cluster)
```

## Steps

### Step 1 — Mint the one shared `auth` signing key (do this FIRST, once)
> What's happening here: `auth` signs every JWT with an RSA private key. If you don't give it a fixed key,
> it invents a throwaway one on each pod start — so a token signed by replica A won't verify against
> replica B's key, and tokens break on every restart. You generate **one** key now and store it in a
> Secret that all `auth` replicas share.

Run this where `kubectl` talks to `ecom-cluster`:
```bash
# 1. generate a 2048-bit RSA private key in PEM format
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out auth-jwt.pem

# 2. store it in a Secret in the shop namespace, keyed exactly as the service expects
kubectl -n shop create secret generic auth-jwt \
  --from-file=JWT_PRIVATE_KEY_PEM=auth-jwt.pem
```
Read it back in plain English: `openssl genpkey` writes a real RSA private key to `auth-jwt.pem`. Then
`--from-file=JWT_PRIVATE_KEY_PEM=auth-jwt.pem` creates a Secret whose **key name** is exactly
`JWT_PRIVATE_KEY_PEM` (the env var the service reads) and whose **value** is the file's contents. Because
all `auth` pods mount this same Secret, they all sign with the same key — and `api-gateway` (which fetches
`auth`'s JWKS) can verify any of them.

What to expect: `secret/auth-jwt created`. Keep `auth-jwt.pem` out of git. If you skip this step, logins
will work intermittently and you'll chase a ghost — set the key.

> Why this MUST be one fixed Secret all replicas share: a JWT is only trustworthy because the verifier can
> check the signature against the signer's public key. `api-gateway` discovers `auth`'s public keys from
> `auth`'s JWKS endpoint. If every `auth` replica had its own random key, the JWKS would flap and tokens
> minted seconds ago would suddenly fail to verify. One key, shared, stable across restarts = stable
> trust. This is the auth-specific twist on top of the normal recipe.

### Step 2 — Deploy `auth` (config + the two secrets + deployment + service)
> What's happening here: `auth` is the first service with TWO secrets — its database password AND the JWT
> key from Step 1. It also calls `user`, so its ConfigMap carries `USER_URL`.

Create its non-secret config and DB-password secret:
```bash
kubectl -n shop create configmap auth \
  --from-literal=PORT=8081 --from-literal=LOG_LEVEL=info \
  --from-literal=DB_HOST=postgres-auth.data.svc.cluster.local \
  --from-literal=DB_PORT=5432 --from-literal=DB_USER=auth \
  --from-literal=DB_NAME=auth --from-literal=DB_SSLMODE=disable \
  --from-literal=USER_URL=http://user.shop.svc.cluster.local:8082 \
  --from-literal=JWT_ISSUER=auth.ecommerce.local \
  --from-literal=JWT_AUDIENCE=ecommerce \
  --from-literal=JWT_TTL_MINUTES=60

kubectl -n shop create secret generic auth-db \
  --from-literal=DB_PASSWORD='<auth-db-pw-from-3.1>'
```
Read the key line: `USER_URL=http://user.shop.svc.cluster.local:8082` is service discovery in action —
`auth` will reach the `user` service at its DNS name, not at any pod IP. The `JWT_ISSUER`/`JWT_AUDIENCE`
must match what `api-gateway` expects (they do — both default to `auth.ecommerce.local` / `ecommerce`).

Now the Deployment + Service. Create `auth.yaml`:
```bash
nano auth.yaml
```
Paste (note it pulls env from THREE sources — the ConfigMap, the DB Secret, and the JWT Secret):
```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: auth, namespace: shop }
spec:
  replicas: 2
  selector: { matchLabels: { app: auth } }
  template:
    metadata: { labels: { app: auth } }
    spec:
      terminationGracePeriodSeconds: 20
      containers:
      - name: auth
        image: 169424082295.dkr.ecr.ap-south-1.amazonaws.com/ecom-repo:auth-<sha>
        ports: [{ containerPort: 8081 }]
        envFrom:
        - configMapRef: { name: auth }       # PORT, DB_HOST, USER_URL, JWT_ISSUER...
        - secretRef:    { name: auth-db }     # DB_PASSWORD
        - secretRef:    { name: auth-jwt }    # JWT_PRIVATE_KEY_PEM (the shared key from Step 1)
        livenessProbe:  { httpGet: { path: /healthz, port: 8081 }, periodSeconds: 10 }
        readinessProbe: { httpGet: { path: /readyz,  port: 8081 }, periodSeconds: 5 }
        resources:
          requests: { cpu: 50m,  memory: 64Mi }
          limits:   { cpu: 250m, memory: 128Mi }
---
apiVersion: v1
kind: Service
metadata: { name: auth, namespace: shop }
spec:
  selector: { app: auth }
  ports: [{ port: 8081, targetPort: 8081 }]
```
Apply and watch:
```bash
kubectl apply -f auth.yaml
kubectl -n shop rollout status deploy/auth
```
What to expect: `deployment "auth" successfully rolled out`, pods `READY 1/1` (which means `/readyz`
passed — `auth` reached `postgres-auth`). If a pod is `0/1`, it usually can't reach its database — check
the `DB_HOST` spelling and that the Secret password matches the one you set in `3.1`. Logs:
`kubectl -n shop logs deploy/auth`.

### Step 3 — Deploy `user` (the simplest service — your template for the rest)
> What's happening here: `user` is a leaf — it has a database but calls nobody, so its ConfigMap has no
> `*_URL` at all. This is the minimal version of the recipe.

```bash
kubectl -n shop create configmap user \
  --from-literal=PORT=8082 --from-literal=LOG_LEVEL=info \
  --from-literal=DB_HOST=postgres-user.data.svc.cluster.local \
  --from-literal=DB_PORT=5432 --from-literal=DB_USER=user_svc \
  --from-literal=DB_NAME=users --from-literal=DB_SSLMODE=disable

kubectl -n shop create secret generic user \
  --from-literal=DB_PASSWORD='<user-db-pw-from-3.1>'
```
Create `user.yaml` — same skeleton as `catalog.yaml` from `3.2`, just renamed and on port 8082:
```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: user, namespace: shop }
spec:
  replicas: 2
  selector: { matchLabels: { app: user } }
  template:
    metadata: { labels: { app: user } }
    spec:
      terminationGracePeriodSeconds: 20
      containers:
      - name: user
        image: 169424082295.dkr.ecr.ap-south-1.amazonaws.com/ecom-repo:user-<sha>

        envFrom:
        - configMapRef: { name: user }
        - secretRef:    { name: user }
        livenessProbe:  { httpGet: { path: /healthz, port: 8082 }, periodSeconds: 10 }
        readinessProbe: { httpGet: { path: /readyz,  port: 8082 }, periodSeconds: 5 }
```

```bash
kubectl -n shop rollout status deploy/user
```
This is your **template**. Every service below is this file with the name, port, image, env, and resource
hints swapped. Deploy `auth` and `user` first because `api-gateway` and `auth` depend on `user` being up.

### Step 4 — Deploy `search` (talks to Elasticsearch; no secret)
> What's happening here: `search` reads/writes Elasticsearch and only calls `catalog` during a reindex.
> Local-dev ES has security off, so there's no Secret here.

```bash
kubectl -n shop create configmap search \
  --from-literal=PORT=8084 --from-literal=LOG_LEVEL=info \
  --from-literal=ELASTICSEARCH_URL=http://elasticsearch.data.svc.cluster.local:9200 \
  --from-literal=CATALOG_URL=http://catalog.shop.svc.cluster.local:8083
```
Deployment + Service are the template again, on port 8084, with **only** a `configMapRef` (no
`secretRef`), liveness/readiness on `/healthz` and `/readyz`. Apply it, then
`kubectl -n shop rollout status deploy/search`. A `0/1` here means it can't reach Elasticsearch — confirm
`elasticsearch` is up in `data` and the URL is right.

### Step 5 — Deploy `cart` (talks to Redis + catalog)
> What's happening here: `cart` stores carts in Redis and calls `catalog` to price items. Redis may have
> an empty password, but you still keep it in a Secret (never a ConfigMap), so the manifest shape stays
> identical whether or not Redis has AUTH.

```bash
kubectl -n shop create configmap cart \
  --from-literal=PORT=8085 --from-literal=LOG_LEVEL=info \
  --from-literal=REDIS_ADDR=redis.data.svc.cluster.local:6379 \
  --from-literal=REDIS_DB=0 \
  --from-literal=CATALOG_URL=http://catalog.shop.svc.cluster.local:8083

kubectl -n shop create secret generic cart \
  --from-literal=REDIS_PASSWORD='<redis-pw-or-empty>'
```
Deployment + Service on port 8085, `envFrom` both the `cart` ConfigMap and `cart` Secret. Apply, then
`rollout status`. `0/1` here means Redis is unreachable — check `REDIS_ADDR`.

### Step 6 — Deploy `payment` (a leaf with a fault hook)
> What's happening here: `payment` authorizes payments against `postgres-payment` and calls nobody. It has
> a `FAIL_MODE` knob you'll use later for chaos demos; leave it at `approve` now.

```bash
kubectl -n shop create configmap payment \
  --from-literal=PORT=8087 --from-literal=LOG_LEVEL=info \
  --from-literal=DB_HOST=postgres-payment.data.svc.cluster.local \
  --from-literal=DB_PORT=5432 --from-literal=DB_USER=payment \
  --from-literal=DB_NAME=payment --from-literal=DB_SSLMODE=disable \
  --from-literal=FAIL_MODE=approve

kubectl -n shop create secret generic payment \
  --from-literal=DB_PASSWORD='<payment-db-pw-from-3.1>'
```
Deployment + Service on port 8087 (the standard template). Apply and check rollout.

### Step 7 — Deploy `inventory`, `notification`, `recommendation` (HTTP side only for now)

> `4.2`. Right now you bring up their HTTP side so they're alive and readiness-green. Their ConfigMaps
> will already carry the Kafka keys (harmless until `4.2` confirms they consume), so set them now.

`inventory` (port 8088, own Postgres):
```bash
kubectl -n shop create configmap inventory \
  --from-literal=PORT=8088 --from-literal=LOG_LEVEL=info \
  --from-literal=DB_HOST=postgres-inventory.data.svc.cluster.local \

  --from-literal=DB_NAME=inventory --from-literal=DB_SSLMODE=disable \

kubectl -n shop create secret generic inventory \

```
`recommendation` (port 8090, own Postgres, plus the `VARIANT` A/B knob):
```bash
kubectl -n shop create configmap recommendation \
  --from-literal=PORT=8090 --from-literal=LOG_LEVEL=info \
  --from-literal=DB_HOST=postgres-recommendation.data.svc.cluster.local \
  --from-literal=DB_PORT=5432 --from-literal=DB_USER=recommendation \
  --from-literal=DB_NAME=recommendation --from-literal=DB_SSLMODE=disable \

kubectl -n shop create secret generic recommendation \

```
`notification` (port 8089, **no database, no Secret** — fully stateless):

```bash
kubectl -n shop create configmap notification \
  --from-literal=PORT=8089 --from-literal=LOG_LEVEL=info \
  --from-literal=KAFKA_BROKERS=kafka.data.svc.cluster.local:9092 \

```
For each: a Deployment + Service on its port using the template (`notification` has only a `configMapRef`,
no `secretRef`). Apply all three and `rollout status` each. Note `notification`'s readiness gates on the

StatefulSet).

### Step 8 — Deploy `order` (the checkout orchestrator)
> What's happening here: `order` is the busiest caller — it synchronously calls `cart`, `payment`, and
> `inventory` during checkout, and it will produce the `order.created` event in `4.2`. Its ConfigMap
> therefore carries three `*_URL` values plus the Kafka coordinates.

```bash
kubectl -n shop create configmap order \
  --from-literal=PORT=8086 --from-literal=LOG_LEVEL=info \
  --from-literal=DB_HOST=postgres-order.data.svc.cluster.local \
  --from-literal=DB_PORT=5432 --from-literal=DB_USER=order \
  --from-literal=DB_NAME=order --from-literal=DB_SSLMODE=disable \
  --from-literal=CART_URL=http://cart.shop.svc.cluster.local:8085 \
  --from-literal=PAYMENT_URL=http://payment.shop.svc.cluster.local:8087 \
  --from-literal=INVENTORY_URL=http://inventory.shop.svc.cluster.local:8088 \
  --from-literal=KAFKA_BROKERS=kafka.data.svc.cluster.local:9092 \
  --from-literal=KAFKA_TOPIC=order.created

kubectl -n shop create secret generic order \
  --from-literal=DB_PASSWORD='<order-db-pw-from-3.1>'
```
Read the three URL lines: this is the **synchronous checkout chain** — `order` reaches `cart`, `payment`,
and `inventory` by their Service DNS names. Deploy `order` *after* those three exist so its calls land.
Deployment + Service on port 8086 (the template), apply, `rollout status`.

### Step 9 — Deploy `api-gateway` (the edge router) WITH an Ingress
> What's happening here: `api-gateway` is the single public entry for the API. It proxies `/api/*` to the
> right internal service and verifies JWTs on protected routes. It has **no secrets** — all config is
> the URLs of everything it fronts. This is the first of the two services that gets an Ingress.

```bash
kubectl -n shop create configmap api-gateway \
  --from-literal=PORT=8080 --from-literal=LOG_LEVEL=info \
  --from-literal=AUTH_URL=http://auth.shop.svc.cluster.local:8081 \
  --from-literal=USER_URL=http://user.shop.svc.cluster.local:8082 \
  --from-literal=CATALOG_URL=http://catalog.shop.svc.cluster.local:8083 \
  --from-literal=SEARCH_URL=http://search.shop.svc.cluster.local:8084 \
  --from-literal=CART_URL=http://cart.shop.svc.cluster.local:8085 \
  --from-literal=ORDER_URL=http://order.shop.svc.cluster.local:8086 \
  --from-literal=RECOMMENDATION_URL=http://recommendation.shop.svc.cluster.local:8090 \
  --from-literal=JWT_ISSUER=auth.ecommerce.local \
  --from-literal=JWT_AUDIENCE=ecommerce
```
Create `api-gateway.yaml` — Deployment + Service (port 8080, `configMapRef` only) **plus** an Ingress:
```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: api-gateway, namespace: shop }
spec:
  replicas: 2
  selector: { matchLabels: { app: api-gateway } }
  template:
    metadata: { labels: { app: api-gateway } }
    spec:
      terminationGracePeriodSeconds: 20
      containers:
      - name: api-gateway
        image: 169424082295.dkr.ecr.ap-south-1.amazonaws.com/ecom-repo:api-gateway-<sha>
        ports: [{ containerPort: 8080 }]
        envFrom:
        - configMapRef: { name: api-gateway }
        livenessProbe:  { httpGet: { path: /healthz, port: 8080 }, periodSeconds: 10 }
        readinessProbe: { httpGet: { path: /readyz,  port: 8080 }, periodSeconds: 5 }   # 503 until auth's JWKS is reachable
        resources:
          requests: { cpu: 50m,  memory: 64Mi }
          limits:   { cpu: 250m, memory: 128Mi }
---
apiVersion: v1
kind: Service
metadata: { name: api-gateway, namespace: shop }
spec:
  selector: { app: api-gateway }
  ports: [{ port: 8080, targetPort: 8080 }]
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api-gateway
  namespace: shop
  annotations:
    kubernetes.io/ingress.class: alb
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
spec:
  rules:
  - http:
      paths:
      - path: /
        pathType: Prefix
        backend: { service: { name: api-gateway, port: { number: 8080 } } }
```
```bash
kubectl apply -f api-gateway.yaml
kubectl -n shop rollout status deploy/api-gateway
```
Its `/readyz` returns 503 until it has fetched `auth`'s JWKS, so deploy it *after* `auth` is green. If it
stays `0/1`, check `AUTH_URL` and that `auth` is up.

### Step 10 — Deploy `frontend` (the UI) WITH an Ingress
> What's happening here: `frontend` serves the single-page UI. The crucial subtlety: it tells the
> **browser** where the gateway is, and the browser is *outside* the cluster — so `API_GATEWAY_URL` must
> be the gateway's **public** ALB host, NOT `http://api-gateway:8080` (which only resolves in-cluster).

First get the gateway's public host from Step 9's Ingress:
```bash
GW=$(kubectl -n shop get ingress api-gateway -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
echo "$GW"     # e.g. k8s-shop-apigatew-abc123.ap-south-1.elb.amazonaws.com
```
```bash
kubectl -n shop create configmap frontend \
  --from-literal=PORT=3000 --from-literal=LOG_LEVEL=info \
  --from-literal=API_GATEWAY_URL="http://$GW"
```
Create `frontend.yaml` — Deployment + Service on port 3000 (`configMapRef` only) plus an Ingress
identical in shape to the gateway's, pointing at `frontend` port 3000. Apply it and `rollout status`.

> Why the gateway URL is the public host, not the Service name: the `frontend` pod just hands the browser
> a config blob saying "call the API here." The code that actually calls `/api/*` runs in the user's
> browser, on the public internet — it cannot resolve `api-gateway.shop.svc.cluster.local`. So that one
> URL is the exception to "always use Service DNS": it must be the ALB host. Every *server-to-server* URL
> in this whole part stays the in-cluster DNS name.

## Verify
- `kubectl -n shop get deploy` shows all 12 deployments (the 11 here + `catalog`) with full READY counts
  (e.g. `2/2`). READY means each service's `/readyz` passed — they reached their datastores.
- `kubectl -n shop get svc` lists a Service per app on the right port.
- Service discovery works end to end: hit the gateway's public host and run a real flow —
  ```bash
  GW=$(kubectl -n shop get ingress api-gateway -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
  curl -s -X POST http://$GW/api/auth/register -H 'Content-Type: application/json' \
       -d '{"email":"a@b.com","password":"pw123456"}'
  TOKEN=$(curl -s -X POST http://$GW/api/auth/login -H 'Content-Type: application/json' \
       -d '{"email":"a@b.com","password":"pw123456"}' | python3 -c 'import sys,json;print(json.load(sys.stdin)["access_token"])')
  curl -s http://$GW/api/products                       # gateway -> catalog
  ```
  Register/login hits `api-gateway → auth → user`; the product list hits `api-gateway → catalog`. If any
  hop 502s, that callee's `*_URL` is wrong or that pod isn't ready.
- Prove the shared JWT key: `kubectl -n shop delete pod -l app=auth` (kill both replicas), wait for new
  ones, then reuse `$TOKEN` on `curl -s http://$GW/api/orders -H "Authorization: Bearer $TOKEN"`. It still
  verifies — because the new pods loaded the **same** `auth-jwt` Secret, not a fresh random key.

## Concept deep-dive — how one service finds another (Service DNS → ClusterIP → kube-proxy)
When `order` calls `http://payment.shop.svc.cluster.local:8087`, three pieces cooperate, and naming them
makes Kubernetes networking click:

```
   order pod
     │  1. DNS: "payment.shop.svc.cluster.local?"
     ▼
   CoreDNS (kube-system) ──► returns the Service's ClusterIP, e.g. 10.96.31.7
     │  2. connect to 10.96.31.7:8087
     ▼
   kube-proxy / iptables (or IPVS) on the node
     │  3. rewrites the dest to ONE ready payment pod IP, load-balanced
     ▼
   a ready payment pod (only pods in the Service's Endpoints — i.e. readiness passed)
```

1. **DNS resolution.** The Service name resolves via CoreDNS to a **stable virtual IP** — the ClusterIP.
   That IP never changes for the life of the Service, even as pods churn.
2. **The ClusterIP is virtual.** No single machine owns it. It's a load-balancing target.
3. **kube-proxy does the steering.** On every node, kube-proxy programs iptables/IPVS rules that catch
   traffic to the ClusterIP and DNAT it to one of the Service's current **Endpoints** — and Endpoints only
   contains pods whose readiness probe passes (the same gating you learned in `3.2`). So `order`'s call
   lands on a `payment` pod that has declared itself able to serve, with zero retry logic in `order`.

Why this beats the alternatives: hardcoding pod IPs is impossible (they change constantly); running a
separate service registry adds a moving part your apps must integrate with; a client-side load balancer
pushes routing logic into every service. Native Service DNS + ClusterIP + kube-proxy gives you stable
names, automatic load balancing, and readiness-gated routing for free, with no application code.
*Interview line: "Service discovery in Kubernetes is just DNS to a stable ClusterIP, which kube-proxy
load-balances across the Service's ready Endpoints — so callers use a name, never an IP, and only ever
reach pods that passed readiness."*
