# 4.1 — Deploy the rest of the fleet (the other 5 services)

## Goal
By the end of this part every service in the `shop` namespace is running: `api-gateway`, `auth`, `order`,
`inventory`, and `frontend` (plus `catalog`, already up from `3.2`). They can all **find and call each
other** by name, and the JWT that `auth` mints will verify everywhere because every replica shares one
fixed signing key. You will not wire up Kafka events yet (that's `4.2`) or lock down traffic (that's `4.3`)
— this part is purely "bring the services up and let them talk."

## Why this part exists (read this first)
In `3.2` you proved the **five-object deploy recipe** on exactly one service (`catalog`): ConfigMap +
Secret + Deployment + Service + Ingress. That was deliberate — nail the shape once, and the rest are the
same shape with different names. This part cashes in that investment.

Two things become real only once there is more than one service, and they're the whole point of this part:

- **Service-to-service discovery.** `catalog` talked to a *database*. Now `order` has to talk to
  `inventory`, and `api-gateway` has to talk to `auth`, `catalog`, and `order`. How does one pod find
  another when pods come and go and their IPs change? The answer is **cluster DNS**, wired through `*_URL`
  environment variables.
- **A shared signing key for auth.** `auth` signs JWTs; `api-gateway` verifies them. If `auth` runs 2
  replicas and each signs with a *different* key, half your logins break at random. So `auth` needs **one
  fixed key**, shared by every replica, that survives restarts.

> NEW CONCEPT — cluster DNS service discovery. Inside the cluster there is a built-in DNS server
> (**CoreDNS**, in `kube-system`). Every `Service` object automatically gets a DNS name of the form
> `<service>.<namespace>.svc.cluster.local`. So a Service named `inventory` in `shop` is reachable at
> `inventory.shop.svc.cluster.local` — and from *within* `shop`, the short name `inventory` resolves too.
> **How:** the Service has a stable virtual IP (its ClusterIP); CoreDNS maps the name to that IP, which
> load-balances across the ready pods. **Why:** pod IPs are ephemeral and change on every restart — the
> Service name is the *one* stable handle. **Why not alternatives:** you could run Consul/Eureka, but
> Kubernetes gives DNS discovery for free with zero app code, so we use the native thing.

## Prerequisites
- [`3.1`](./3.1-datastores.md) — datastores up in `data`: `postgres-auth`, `postgres-order`,
  `postgres-inventory`, and **Kafka** (KRaft) as `kafka`. (`postgres-catalog` is already up from `3.2`.)
- [`3.2`](./3.2-deploy-catalog.md) — `catalog` already running; you know the five-object recipe cold.
- The 6 images in ECR as `ecom-repo:<svc>-<sha>` (built by Jenkins in Phase 01).

> NEW CONCEPT — database-per-service (why each service gets its OWN ConfigMap + Secret). We don't make one
> big shared ConfigMap, on purpose. Each microservice owns **its own datastore** — `auth` has
> `postgres-auth`, `order` has `postgres-order` — and neither can read the other's tables. Each service
> gets its own ConfigMap (port, `DB_HOST`, the URLs of services it calls) and Secret (its DB password).
> This keeps services decoupled: you can change `order`'s schema without touching `auth`, and a leaked
> Secret can't unlock another service's database. It's the standard microservice pattern this project
> teaches.

## The repeatable per-service recipe (memorize this once)
Every service below is the **identical five objects from `3.2`**, varying only by name, port, env keys,
and which other services it calls:

```
   ConfigMap  (non-secret config: PORT, LOG_LEVEL, DB_HOST..., and *_URL of callees)
   Secret     (DB_PASSWORD / JWT key — the sensitive bits)
   Deployment (2 replicas, envFrom the ConfigMap + Secret, liveness /healthz, readiness /readyz)
   Service    (stable ClusterIP + DNS name on the service's port)
   Ingress    (ONLY for the two public edges: api-gateway and frontend)
```

Most services are **internal** (ConfigMap + Secret + Deployment + Service, no Ingress). Only `api-gateway`
and `frontend` face the internet, so only those two get an Ingress. The port + dependency map:

```
   service      port   datastore            calls (set these *_URL)
   ────────────────────────────────────────────────────────────────────
   auth         8081   postgres-auth        (none — self-contained)
   catalog      8083   postgres-catalog     (none — done in 3.2)
   inventory    8088   postgres-inventory   (none — async consumer in 4.2)
   order        8086   postgres-order       inventory
   api-gateway  8080   (none)               auth, catalog, order
   frontend     3000   (none)               api-gateway (via the BROWSER, not in-cluster)
```

## Steps

### Step 1 — Mint the one shared `auth` signing key (do this FIRST, once)
> What's happening here: `auth` signs every JWT with an RSA private key. If you don't give it a fixed key,
> it invents a throwaway one on each pod start — so a token signed by replica A won't verify against
> replica B, and tokens break on every restart. Generate **one** key now and store it in a Secret all
> `auth` replicas share.

```bash
# generate a 2048-bit RSA private key in PEM format
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out auth-jwt.pem

# store it in a Secret in the shop namespace, keyed exactly as the service expects
kubectl -n shop create secret generic auth-jwt --from-file=JWT_PRIVATE_KEY_PEM=auth-jwt.pem
```
`--from-file=JWT_PRIVATE_KEY_PEM=auth-jwt.pem` makes a Secret whose **key** is exactly the env var the
service reads and whose **value** is the file's contents. All `auth` pods mount this same Secret, so they
all sign with the same key — and `api-gateway` (which fetches `auth`'s JWKS) can verify any of them. Expect
`secret/auth-jwt created`. Keep `auth-jwt.pem` out of git.

### Step 2 — Deploy `auth`
> What's happening here: `auth` is self-contained in the trimmed build — it owns registration, login, and
> JWT signing against `postgres-auth`, and mints the `user_id` itself (no separate user service). It has
> TWO secrets: its DB password and the JWT key from Step 1.

```bash
kubectl -n shop create configmap auth \
  --from-literal=PORT=8081 --from-literal=LOG_LEVEL=info \
  --from-literal=DB_HOST=postgres-auth.data.svc.cluster.local \
  --from-literal=DB_PORT=5432 --from-literal=DB_USER=auth \
  --from-literal=DB_NAME=auth --from-literal=DB_SSLMODE=disable \
  --from-literal=JWT_ISSUER=auth.ecommerce.local \
  --from-literal=JWT_AUDIENCE=ecommerce \
  --from-literal=JWT_TTL_MINUTES=60

kubectl -n shop create secret generic auth-db --from-literal=DB_PASSWORD='<auth-db-pw-from-3.1>'
```
Now `auth.yaml` — note it pulls env from THREE sources (ConfigMap, DB Secret, JWT Secret):
```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: auth, namespace: shop }
spec:
  replicas: 2
  selector: { matchLabels: { app: auth } }
  template:
    metadata: { labels: { app: auth } }
    spec:
      terminationGracePeriodSeconds: 20
      containers:
      - name: auth
        image: 169424082295.dkr.ecr.ap-south-1.amazonaws.com/ecom-repo:auth-<sha>
        ports: [{ containerPort: 8081 }]
        envFrom:
        - configMapRef: { name: auth }       # PORT, DB_HOST, JWT_ISSUER...
        - secretRef:    { name: auth-db }     # DB_PASSWORD
        - secretRef:    { name: auth-jwt }    # JWT_PRIVATE_KEY_PEM (the shared key from Step 1)
        livenessProbe:  { httpGet: { path: /healthz, port: 8081 }, periodSeconds: 10 }
        readinessProbe: { httpGet: { path: /readyz,  port: 8081 }, periodSeconds: 5 }
        resources:
          requests: { cpu: 50m,  memory: 64Mi }
          limits:   { cpu: 250m, memory: 128Mi }
---
apiVersion: v1
kind: Service
metadata: { name: auth, namespace: shop }
spec:
  selector: { app: auth }
  ports: [{ port: 8081, targetPort: 8081 }]
```
```bash
kubectl apply -f auth.yaml
kubectl -n shop rollout status deploy/auth
```
Expect `READY 1/1` (which means `/readyz` passed — `auth` reached `postgres-auth`). A `0/1` usually means
it can't reach its DB — check `DB_HOST` and the Secret password. Logs: `kubectl -n shop logs deploy/auth`.

> Why the key MUST be one fixed shared Secret: `api-gateway` verifies a JWT against `auth`'s public keys
> from its JWKS endpoint. If every `auth` replica had its own random key, tokens minted seconds ago would
> fail to verify. One key, shared, stable across restarts = stable trust.

### Step 3 — Deploy `inventory`
> What's happening here: `inventory` owns stock in `postgres-inventory`. `order` calls it synchronously to
> reserve stock; in `4.2` it also becomes the `order.created` consumer. Set the Kafka keys now (harmless
> until `4.2`).

```bash
kubectl -n shop create configmap inventory \
  --from-literal=PORT=8088 --from-literal=LOG_LEVEL=info \
  --from-literal=DB_HOST=postgres-inventory.data.svc.cluster.local \
  --from-literal=DB_PORT=5432 --from-literal=DB_USER=inventory \
  --from-literal=DB_NAME=inventory --from-literal=DB_SSLMODE=disable \
  --from-literal=KAFKA_BROKERS=kafka.data.svc.cluster.local:9092 \
  --from-literal=KAFKA_TOPIC=order.created --from-literal=KAFKA_GROUP=inventory

kubectl -n shop create secret generic inventory --from-literal=DB_PASSWORD='<inventory-db-pw-from-3.1>'
```
Deployment + Service on port 8088 (the standard template, `envFrom` the `inventory` ConfigMap + Secret).
Apply and `kubectl -n shop rollout status deploy/inventory`. Seed some stock so checkout can succeed later:
```bash
kubectl -n shop exec deploy/inventory -- sh -c 'true'   # (placeholder) — seed via the API once api-gateway is up
```

### Step 4 — Deploy `order` (the checkout orchestrator)
> What's happening here: in the trimmed build `order` takes the line items directly in the request and
> calls **only `inventory`** to reserve stock (no cart/payment service), then produces `order.created` in
> `4.2`. Its ConfigMap carries `INVENTORY_URL` plus the Kafka coordinates.

```bash
kubectl -n shop create configmap order \
  --from-literal=PORT=8086 --from-literal=LOG_LEVEL=info \
  --from-literal=DB_HOST=postgres-order.data.svc.cluster.local \
  --from-literal=DB_PORT=5432 --from-literal=DB_USER=order \
  --from-literal=DB_NAME=order --from-literal=DB_SSLMODE=disable \
  --from-literal=INVENTORY_URL=http://inventory.shop.svc.cluster.local:8088 \
  --from-literal=KAFKA_BROKERS=kafka.data.svc.cluster.local:9092 \
  --from-literal=KAFKA_TOPIC=order.created

kubectl -n shop create secret generic order --from-literal=DB_PASSWORD='<order-db-pw-from-3.1>'
```
`INVENTORY_URL` is the **synchronous reserve hop** — `order` reaches `inventory` by its Service DNS name.
Deploy `order` *after* `inventory` exists so its call lands. Deployment + Service on port 8086 (the
template), apply, `rollout status`.

### Step 5 — Deploy `api-gateway` (the edge router) WITH an Ingress
> What's happening here: `api-gateway` is the single public entry for the API. It proxies `/api/*` to the
> right internal service and verifies JWTs on protected routes (`/api/orders`). It has **no secrets** — its
> config is just the URLs of what it fronts. First of the two Ingress services.

```bash
kubectl -n shop create configmap api-gateway \
  --from-literal=PORT=8080 --from-literal=LOG_LEVEL=info \
  --from-literal=AUTH_URL=http://auth.shop.svc.cluster.local:8081 \
  --from-literal=CATALOG_URL=http://catalog.shop.svc.cluster.local:8083 \
  --from-literal=ORDER_URL=http://order.shop.svc.cluster.local:8086 \
  --from-literal=JWT_ISSUER=auth.ecommerce.local \
  --from-literal=JWT_AUDIENCE=ecommerce
```
Create `api-gateway.yaml` — Deployment + Service (port 8080, `configMapRef` only) **plus** an Ingress:
```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: api-gateway, namespace: shop }
spec:
  replicas: 2
  selector: { matchLabels: { app: api-gateway } }
  template:
    metadata: { labels: { app: api-gateway } }
    spec:
      terminationGracePeriodSeconds: 20
      containers:
      - name: api-gateway
        image: 169424082295.dkr.ecr.ap-south-1.amazonaws.com/ecom-repo:api-gateway-<sha>
        ports: [{ containerPort: 8080 }]
        envFrom:
        - configMapRef: { name: api-gateway }
        livenessProbe:  { httpGet: { path: /healthz, port: 8080 }, periodSeconds: 10 }
        readinessProbe: { httpGet: { path: /readyz,  port: 8080 }, periodSeconds: 5 }   # 503 until auth's JWKS is reachable
        resources:
          requests: { cpu: 50m,  memory: 64Mi }
          limits:   { cpu: 250m, memory: 128Mi }
---
apiVersion: v1
kind: Service
metadata: { name: api-gateway, namespace: shop }
spec:
  selector: { app: api-gateway }
  ports: [{ port: 8080, targetPort: 8080 }]
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api-gateway
  namespace: shop
  annotations:
    kubernetes.io/ingress.class: alb
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
spec:
  rules:
  - http:
      paths:
      - path: /
        pathType: Prefix
        backend: { service: { name: api-gateway, port: { number: 8080 } } }
```
```bash
kubectl apply -f api-gateway.yaml
kubectl -n shop rollout status deploy/api-gateway
```
Its `/readyz` returns 503 until it has fetched `auth`'s JWKS, so deploy it *after* `auth` is green. If it
stays `0/1`, check `AUTH_URL` and that `auth` is up.

### Step 6 — Deploy `frontend` (the UI) WITH an Ingress
> What's happening here: `frontend` serves the single-page UI. The crucial subtlety: it tells the
> **browser** where the gateway is, and the browser is *outside* the cluster — so `API_GATEWAY_URL` must
> be the gateway's **public** ALB host, NOT the in-cluster Service name.

```bash
GW=$(kubectl -n shop get ingress api-gateway -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
echo "$GW"     # e.g. k8s-shop-apigatew-abc123.ap-south-1.elb.amazonaws.com

kubectl -n shop create configmap frontend \
  --from-literal=PORT=3000 --from-literal=LOG_LEVEL=info \
  --from-literal=API_GATEWAY_URL="http://$GW"
```
Create `frontend.yaml` — Deployment + Service on port 3000 (`configMapRef` only) plus an Ingress identical
in shape to the gateway's, pointing at `frontend` port 3000. Apply it and `rollout status`.

> Why the gateway URL is the public host, not the Service name: the code that calls `/api/*` runs in the
> user's browser, on the public internet — it cannot resolve `api-gateway.shop.svc.cluster.local`. That one
> URL is the exception to "always use Service DNS"; every *server-to-server* URL stays the in-cluster name.

## Verify
- `kubectl -n shop get deploy` shows **6** deployments (the 5 here + `catalog`) with full READY counts
  (`2/2`). READY means each `/readyz` passed — they reached their datastores.
- `kubectl -n shop get svc` lists a Service per app on the right port.
- Run a real flow through the public gateway:
  ```bash
  GW=$(kubectl -n shop get ingress api-gateway -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
  # register + login (api-gateway -> auth)
  curl -s -X POST http://$GW/api/auth/register -H 'Content-Type: application/json' \
       -d '{"email":"a@b.com","password":"pw123456"}'
  TOKEN=$(curl -s -X POST http://$GW/api/auth/login -H 'Content-Type: application/json' \
       -d '{"email":"a@b.com","password":"pw123456"}' | python3 -c 'import sys,json;print(json.load(sys.stdin)["access_token"])')
  # browse products (api-gateway -> catalog)
  curl -s http://$GW/api/products
  # place an order (api-gateway -> order -> inventory); items are sent directly
  curl -s -X POST http://$GW/api/orders -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
       -d '{"user_id":1,"items":[{"product_id":1,"name":"Coffee Mug","price_cents":1299,"quantity":2}]}'
  ```
  Register/login hits `api-gateway → auth`; products hit `api-gateway → catalog`; the order hits
  `api-gateway → order → inventory`. If a hop 502s, that callee's `*_URL` is wrong or the pod isn't ready.
  (Seed stock first via `PUT /inventory/{product_id}` or the order will 409 on the reservation.)
- Prove the shared JWT key: `kubectl -n shop delete pod -l app=auth` (kill both replicas), wait for new
  ones, then reuse `$TOKEN` on `curl -s http://$GW/api/orders -H "Authorization: Bearer $TOKEN"`. It still
  verifies — because the new pods loaded the **same** `auth-jwt` Secret, not a fresh random key.
