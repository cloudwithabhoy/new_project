# 2.2 — Cluster add-ons (Load Balancer Controller · ExternalDNS · Karpenter)

## Goal
Right now (after `2.1`) you have a cluster that can *run* pods but can't **expose** them to the internet,
can't manage **DNS**, and can't **grow** beyond the 3 nodes you created. In this part you install three
small programs *into* the cluster that add exactly those three abilities.

## Why this part exists (read this before touching anything)
Think of the cluster from `2.1` as an empty building with power and rooms, but no front door, no street
address, and no way to add floors. These three add-ons fix that:

- **AWS Load Balancer Controller** = the front door. When you later say "expose `catalog` to the internet"
  (an `Ingress` object), *something* has to actually go to AWS and create a real load balancer. That
  something is this controller.
- **ExternalDNS** = the street address. When a service gets a load balancer, this writes the matching
  **Route 53** DNS record automatically, so `shop.example.com` points at it without you editing DNS by hand.
- **Karpenter** = the ability to add floors. When pods can't fit on the current nodes, Karpenter notices
  and launches new (cheap, spot) EC2 nodes within about a minute, then removes them when they're idle.

You install all three the same disciplined way — using **IRSA** (the OIDC/IAM mechanism you set up in
`2.1`). Re-read the IRSA deep-dive at the bottom of `2.1` if it's fuzzy; you're about to use it three times.

> NEW CONCEPT — what is an "add-on" / "controller"?
> These aren't part of Kubernetes itself. Each is a small program that you install **as pods running inside
> your own cluster**. Each one sits in a loop: "look at what the user asked for, look at what exists in AWS,
> and make AWS match." That loop is called a **controller** (or **operator**). You'll see the same shape
> three times today — that repetition is the point: once you understand one controller, you understand all
> of them.

## Before you start — where you run these commands
Run everything below from the machine where `kubectl` already talks to `ecom-cluster` (the Jenkins EC2
instance, or your laptop). Quick sanity check that you're pointed at the right cluster:

```bash
kubectl config current-context     # should name ecom-cluster / ap-south-1
kubectl get nodes                  # your 3 nodes, all "Ready"
```
If that doesn't work, reconnect first:
```bash
aws eks update-kubeconfig --region ap-south-1 --name ecom-cluster
```

> NEW CONCEPT — what is Helm, and why are we using it?
> Each add-on is made of many Kubernetes objects (a Deployment, a ServiceAccount, RBAC roles, config…).
> Writing all that YAML by hand is error-prone. **Helm** is the package manager for Kubernetes — like
> `apt` or `npm`, but for clusters. You add a "repo" (a catalog), then `helm install <name> <chart>` and
> Helm applies all the objects for you, with values you choose. We use it here because these add-ons are
> *official, packaged, and updated often* — exactly what a package manager is for. Install Helm once:
> `curl https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3 | bash`.

You'll also reuse these two values a lot, so keep them handy: account id `169424082295`, region
`ap-south-1`.

## Step 1 — Install the AWS Load Balancer Controller (the front door)

> What is this controller, in one picture? Inside Kubernetes you'll write a short note that says "please
> expose `catalog` to the internet" (an `Ingress` object). But Kubernetes can't build an AWS load balancer
> by itself — it needs a worker who reads that note and actually goes to AWS and builds the load balancer.
> The AWS Load Balancer Controller is that worker: it watches for your Ingress notes and provisions a real
> **ALB** to match. Without it, your Ingress note just sits there and nobody answers the door.

### 1a. Give it permission to talk to AWS (create the IAM policy)
The controller needs to call AWS APIs (create load balancers, target groups, etc.). First create an IAM
**policy** that lists exactly those permissions. AWS publishes the correct policy document, so you just
download it and create it — you don't write it yourself.

```bash
# download AWS's official permission list for this controller
curl -o alb-iam-policy.json \
  https://raw.githubusercontent.com/kubernetes-sigs/aws-load-balancer-controller/main/docs/install/iam_policy.json

# create it in your account (run once; if it already exists, skip)
aws iam create-policy --policy-name AWSLoadBalancerControllerIAMPolicy \
  --policy-document file://alb-iam-policy.json
```
What just happened: you created a named bundle of permissions in IAM. It isn't attached to anything yet —
the next step attaches it to a Kubernetes identity.

### 1b. Wire that policy to a Kubernetes ServiceAccount (this is IRSA)
```bash
eksctl create iamserviceaccount \
  --cluster ecom-cluster --region ap-south-1 \
  --namespace kube-system --name aws-load-balancer-controller \
  --attach-policy-arn arn:aws:iam::169424082295:policy/AWSLoadBalancerControllerIAMPolicy \
  --approve
```
Read this command in plain English: "Create a Kubernetes **ServiceAccount** called
`aws-load-balancer-controller` in the `kube-system` namespace, and behind the scenes create an IAM role
that trusts the cluster's OIDC provider and carries the policy from 1a." After this, any pod that uses
this ServiceAccount automatically gets short-lived AWS credentials — **no access keys stored anywhere**.
That is IRSA doing its job.

> Why `kube-system`? It's the namespace Kubernetes uses for cluster-infrastructure pods (DNS, networking,
> controllers). These add-ons are infrastructure, not your app, so they live here — not in `shop`/`data`.

### 1c. Install the controller itself with Helm
```bash
helm repo add eks https://aws.github.io/eks-charts     # add AWS's chart catalog
helm repo update                                       # refresh it

helm install aws-load-balancer-controller eks/aws-load-balancer-controller \
  -n kube-system \
  --set clusterName=ecom-cluster \
  --set serviceAccount.create=false \
  --set serviceAccount.name=aws-load-balancer-controller
```
The `--set serviceAccount.create=false` matters: you already created the ServiceAccount (with its IAM
role) in 1b, so you tell Helm "don't make a new one, reuse mine." `clusterName` tells the controller which
cluster's VPC/subnets to provision load balancers in.

### 1d. Check it came up
```bash
kubectl -n kube-system get deploy aws-load-balancer-controller   # want READY 1/1 (or 2/2)
```
If it's `0/1`, look at why: `kubectl -n kube-system logs deploy/aws-load-balancer-controller`. The usual
cause is an IRSA mistake in 1b (wrong policy ARN) — the logs will say "access denied".

## Step 2 — Install ExternalDNS (the street address)

> What is ExternalDNS, in one picture? Imagine you open a new shop. The Load Balancer Controller built you
> a building (the ALB) — but it only has GPS coordinates, an ugly auto-generated hostname like
> `k8s-shop-abc123.ap-south-1.elb.amazonaws.com`. Nobody types that. ExternalDNS is the clerk who goes to
> the city registry (Route 53) and registers a human name — `shop.example.com` — pointing at that building,
> and keeps it updated if the building ever moves. You declare the name once on your Service/Ingress;
> ExternalDNS does the registry paperwork for you.

Same three moves as Step 1, so it should already feel familiar: give it AWS permission via IRSA, then
install it with Helm.

### 2a. ServiceAccount + Route 53 permission (IRSA again)
```bash
eksctl create iamserviceaccount \
  --cluster ecom-cluster --region ap-south-1 \
  --namespace kube-system --name external-dns \
  --attach-policy-arn arn:aws:iam::aws:policy/AmazonRoute53FullAccess \
  --approve
```
Here we attach an AWS-managed policy (`AmazonRoute53FullAccess`) instead of a custom one, because the
permission ExternalDNS needs — write DNS records — already exists as a ready-made policy. (In production
you'd narrow this to just your hosted zone; full access is fine while learning.)

### 2b. Install with Helm
```bash
helm repo add external-dns https://kubernetes-sigs.github.io/external-dns/
helm repo update
helm install external-dns external-dns/external-dns -n kube-system \
  --set provider=aws \
  --set serviceAccount.create=false \
  --set serviceAccount.name=external-dns \
  --set policy=sync \
  --set txtOwnerId=ecom-cluster
```
Two flags worth understanding: `policy=sync` means "if I delete a Service, also delete its DNS record"
(keep DNS exactly in sync). `txtOwnerId=ecom-cluster` makes ExternalDNS write a little marker record so it
only ever edits records **it** created — so two clusters sharing a domain don't fight.

### 2c. Check
```bash
kubectl -n kube-system logs deploy/external-dns | tail -20   # should connect to Route 53, no auth errors
```

## Step 3 — Install Karpenter (the ability to add nodes)

> NEW CONCEPT — why Karpenter and not just "more nodes"?
> Your `2.1` node group is a **fixed** size. If a traffic spike needs more pods than fit, those pods just
> sit `Pending` forever. Karpenter watches for exactly that — `Pending` pods — and launches new EC2
> instances sized to fit them, then deletes those instances when they go idle. We choose **spot**
> instances (spare AWS capacity, up to ~70% cheaper) because this is a learning platform and Karpenter
> can gracefully replace a spot node if AWS reclaims it. It's faster and smarter than the older Cluster
> Autoscaler, which is why it's the modern default.

### 3a. Install Karpenter (Helm)
Karpenter needs a couple of IAM roles and an SQS queue for spot-interruption notices. The official
getting-started guide has the exact CloudFormation for those (create them once); after they exist, the
install is:
```bash
helm registry login public.ecr.aws
helm upgrade --install karpenter oci://public.ecr.aws/karpenter/karpenter \
  -n karpenter --create-namespace \
  --set settings.clusterName=ecom-cluster \
  --set settings.interruptionQueue=ecom-cluster
```

### 3b. Tell Karpenter what it's allowed to launch
Installing Karpenter doesn't launch anything yet — you have to give it a **policy of what kinds of nodes
to create**. You do that with two objects: a `NodePool` (the rules) and an `EC2NodeClass` (the AWS
specifics). First create a file:
```bash
nano nodepool.yaml      # or use your editor of choice
```
Paste this in:
```yaml
apiVersion: karpenter.sh/v1
kind: NodePool
metadata: { name: default }
spec:
  template:
    spec:
      requirements:
      - { key: karpenter.sh/capacity-type, operator: In, values: ["spot"] }   # prefer spot
      - { key: kubernetes.io/arch,          operator: In, values: ["amd64"] }
      nodeClassRef: { group: karpenter.k8s.aws, kind: EC2NodeClass, name: default }
  limits: { cpu: "32" }                                    # never grow past 32 vCPU total (cost guard)
  disruption: { consolidationPolicy: WhenEmptyOrUnderutilized }   # pack pods + remove idle nodes
```
Then apply it (this is how you turn a YAML file into live cluster state):
```bash
kubectl apply -f nodepool.yaml
```
> NEW CONCEPT — `kubectl apply -f <file>`: this is the command you'll run hundreds of times. It reads a
> YAML file and tells Kubernetes "make reality match what's written here." Run it again after editing the
> file and Kubernetes changes only what differs. This declarative "describe the end state, let the cluster
> reconcile" model is the heart of Kubernetes.

### 3c. Prove it works (the satisfying part)
Create a throwaway Deployment bigger than your current nodes can hold, and watch a node appear:
```bash
kubectl create deployment inflate --image=public.ecr.aws/eks-distro/kubernetes/pause:3.9 --replicas=20
kubectl get nodes -w        # within ~1 min a new node joins; Ctrl-C to stop watching
kubectl delete deployment inflate    # remove the test; Karpenter will later remove the idle node
```

## Concept deep-dive — the controller / reconcile loop (one idea behind all three)
Everything you installed today is the **same pattern**, and naming it once makes Kubernetes click:

A **controller** runs a never-ending loop:
```
   loop forever:
     desired = what the user declared   (an Ingress exists / a hostname is set / pods are Pending)
     actual  = what really exists in AWS (an ALB / a Route 53 record / EC2 capacity)
     if desired != actual:  call AWS to fix the difference
```
- ALB Controller: desired = "an Ingress exists" → actual = "an ALB exists" → it creates/updates/deletes ALBs.
- ExternalDNS: desired = "this hostname" → actual = "this Route 53 record" → it writes DNS.
- Karpenter: desired = "these pods can run" → actual = "enough nodes exist" → it launches/removes EC2.

This is why each one gets its **own** IRSA role: separate controllers with separate, least-privilege AWS
permissions mean a bug or compromise in ExternalDNS can touch Route 53 but can't launch EC2. *Interview
line: "These add-ons are operators — control loops that continuously reconcile a Kubernetes spec against
external AWS state — and isolating each behind its own IRSA role keeps the blast radius small."*
