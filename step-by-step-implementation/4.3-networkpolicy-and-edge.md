# 4.3 — Lock down traffic (default-deny NetworkPolicy) and expose the edge

## Goal
By the end of this part, traffic inside the cluster is **deny-by-default**: a pod can only talk to the
exact pods its job requires, and nothing else. You'll drop a default-deny NetworkPolicy into both `shop`
and `data`, then open precisely the edges of your call graph (api-gateway→order, order→payment,
services→their Postgres, the Kafka path), and confirm the two public edges — `api-gateway` and `frontend` —
are reachable from the internet through the ALB while everything else stays internal.

## Why this part exists (read this first)
After `4.1` and `4.2` every service can reach every other service, because by default **Kubernetes
networking is wide open** — any pod can connect to any pod in any namespace. That's convenient while
bringing things up, but it's the opposite of secure. If an attacker pops a single low-value pod (say
`search`), nothing stops them from connecting straight to `postgres-payment` or to `auth`. The flat
network means one compromised pod can reach everything.

This part fixes that by flipping the default from "allow all" to "deny all," then re-allowing only the
connections your architecture actually uses. The call graph you built in `4.1`/`4.2` is your allow-list —
nothing more should be able to talk.

> NEW CONCEPT — NetworkPolicy & default-deny (zero-trust networking). A **NetworkPolicy** is a firewall
> rule expressed as a Kubernetes object: it selects a set of pods (by label) and says which traffic is
> allowed *to* them (ingress) and *from* them (egress). **How default-deny works:** the moment any
> NetworkPolicy selects a pod, that pod switches from "allow everything" to "allow only what a policy
> explicitly permits" — so you first apply a policy that selects *all* pods and allows *nothing*, which
> turns the whole namespace deny-by-default, then you add narrow policies that punch holes for the real
> edges. **Why we use it here:** it implements **zero-trust** east-west networking — no pod is trusted
> just because it's inside the cluster; each connection must be explicitly sanctioned. **Why it fits vs
> alternatives:** you could try to enforce this at the app layer (every service checks its caller) but
> that's error-prone and per-language; NetworkPolicy enforces it at the network, uniformly, with no app
> code.

> NEW CONCEPT — NetworkPolicy needs a CNI that ENFORCES it. A NetworkPolicy is just a desired rule; the
> thing that actually drops packets is the cluster's **CNI** (the pod-network plugin). The default Amazon
> VPC CNI on EKS does **not** enforce NetworkPolicy unless you turn the feature on, and many teams instead
> run **Calico** or **Cilium**, which enforce policies natively. **So before these manifests do anything,
> confirm your CNI enforces NetworkPolicy** — otherwise you'll apply a default-deny and watch traffic flow
> anyway, which is the classic "I locked it down but nothing changed" trap. On EKS you either enable the
> VPC CNI's network-policy mode or install Calico/Cilium; pick one before Step 1.

## Prerequisites
- [`4.1`](./4.1-deploy-the-fleet.md) and [`4.2`](./4.2-kafka-async-backbone.md) — the full fleet and the
  Kafka backbone are up; you know the exact call graph (it's your allow-list).
- A NetworkPolicy-**enforcing** CNI active on `ecom-cluster` (VPC CNI network-policy mode, Calico, or
  Cilium). Verify quickly:
  ```bash
  kubectl get ds -n kube-system | grep -Ei 'calico|cilium|aws-node'   # one of these enforces policy
  ```
- The AWS Load Balancer Controller from [`2.2`](./2.2-cluster-addons.md) — it's what turns the edge
  Ingresses into real ALBs (you already used it in `4.1`).

The call graph you're about to encode as allow-rules:
```
   internet ─► api-gateway ─► auth, user, catalog, search, cart, order, recommendation
   internet ─► frontend  (UI only; browser then calls api-gateway's public ALB)
   order ─► cart, payment, inventory                      (sync checkout)
   auth ─► user · cart ─► catalog · search ─► catalog     (sync helpers)
   shop services ─► their own Postgres / Redis / ES / Kafka in the `data` namespace
   order ─► Kafka(produce) · inventory,notification,recommendation,thumbnail-job ─► Kafka(consume)
```

## Steps

### Step 1 — Turn `shop` deny-by-default
> What's happening here: you apply ONE policy that selects every pod in `shop` and permits no ingress and
> no egress. Instantly, all pod-to-pod traffic in `shop` stops — including DNS — until you re-allow it.
> This is the floor you build the allow-list on top of.

A default-deny policy = an empty guest list that turns everyone away until you add names. Create
`deny-all-shop.yaml`:
```bash
nano deny-all-shop.yaml
```
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny, namespace: shop }
spec:
  podSelector: {}                 # {} = select EVERY pod in this namespace
  policyTypes: [Ingress, Egress]  # govern BOTH directions
  # no ingress: and no egress: blocks below = nothing is allowed
```
```bash
kubectl apply -f deny-all-shop.yaml
```
Read it back: `podSelector: {}` matches all pods; listing `Ingress` and `Egress` in `policyTypes` with
**no** corresponding `ingress:`/`egress:` allow-blocks means "allow nothing in either direction." What to
expect: things start failing — that's correct. Your services can't even resolve DNS now. Don't panic;
Step 2 re-opens DNS, and the rest of the steps re-open the real edges.

### Step 2 — Re-allow DNS (or everything breaks)
> What's happening here: every service discovery call in `4.1` was a DNS lookup to CoreDNS in
> `kube-system`. Default-deny just blocked that too. You must explicitly allow egress to CoreDNS on port
> 53, or no service can resolve any name.

Allowing DNS = letting everyone phone the directory. Create `allow-dns-shop.yaml`:
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-dns, namespace: shop }
spec:
  podSelector: {}                 # applies to all pods in shop
  policyTypes: [Egress]
  egress:
  - to:
    - namespaceSelector: {}       # to any namespace (CoreDNS lives in kube-system)
      podSelector:
        matchLabels: { k8s-app: kube-dns }   # the CoreDNS pods
    ports:
    - { protocol: UDP, port: 53 }
    - { protocol: TCP, port: 53 }
```
```bash
kubectl apply -f allow-dns-shop.yaml
```
Read the key bits: this allows **egress** from every `shop` pod to pods labelled `k8s-app: kube-dns` (the
standard CoreDNS label) on port 53, UDP and TCP. NetworkPolicies are **additive** — this one only *adds*
an allowed path on top of the deny; it doesn't undo the default-deny for anything else. What to expect:
name resolution works again, but actual service-to-service calls are still blocked until you open them
below.

### Step 3 — Open exactly the synchronous edges (3 concrete examples)
> What's happening here: now you punch one hole per real call-graph edge. Each policy names a *target* and
> *who may reach it*. Below are three representative ones — api-gateway→order, order→payment, and
> services→their Postgres — and you'll write the rest by the same pattern.

Each allow-policy = adding exactly one name to one service's guest list.

**Example A — let `api-gateway` reach `order` (ingress on the target).** Create
`allow-gateway-to-order.yaml`:
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-gateway-to-order, namespace: shop }
spec:
  podSelector: { matchLabels: { app: order } }   # this policy protects ORDER pods
  policyTypes: [Ingress]
  ingress:
  - from:
    - podSelector: { matchLabels: { app: api-gateway } }   # only the gateway may connect
    ports:
    - { protocol: TCP, port: 8086 }
```
Read it: "incoming traffic to `order` pods is allowed only **from** pods labelled `app=api-gateway`, and
only on TCP 8086." Anything else hitting `order` is dropped. (You'd add the same shape to let `order`
itself be reached by nothing else.)

**Example B — let `order` reach `payment` (egress from caller + ingress on callee).** Create
`allow-order-to-payment.yaml`:
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-order-egress-payment, namespace: shop }
spec:
  podSelector: { matchLabels: { app: order } }   # governs ORDER's outbound
  policyTypes: [Egress]
  egress:
  - to:
    - podSelector: { matchLabels: { app: payment } }
    ports:
    - { protocol: TCP, port: 8087 }
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-payment-ingress-order, namespace: shop }
spec:
  podSelector: { matchLabels: { app: payment } }  # protects PAYMENT
  policyTypes: [Ingress]
  ingress:
  - from:
    - podSelector: { matchLabels: { app: order } }
    ports:
    - { protocol: TCP, port: 8087 }
```
Read it: because `shop` is deny-by-default in **both** directions, an `order → payment` call needs **two**
allows — `order` must be permitted to send (egress), and `payment` must be permitted to receive from
`order` (ingress). Both objects together open exactly one edge. You repeat this pair for `order→cart`,
`order→inventory`, `auth→user`, `cart→catalog`, `search→catalog`.

**Example C — let `shop` services reach their Postgres in `data` (cross-namespace egress).** The DB lives
in the `data` namespace, so the rule crosses namespaces. Create `allow-order-to-its-postgres.yaml`:
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-order-egress-postgres, namespace: shop }
spec:
  podSelector: { matchLabels: { app: order } }
  policyTypes: [Egress]
  egress:
  - to:
    - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: data } }
      podSelector: { matchLabels: { app: postgres-order } }   # ONLY its own DB
    ports:
    - { protocol: TCP, port: 5432 }
```
And the matching ingress on the database side, in the `data` namespace — create
`data-allow-postgres-order.yaml`:
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-postgres-order-from-order, namespace: data }
spec:
  podSelector: { matchLabels: { app: postgres-order } }
  policyTypes: [Ingress]
  ingress:
  - from:
    - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: data } }   # placeholder; replace with shop selector below
  # NOTE: select the SHOP order pods explicitly:
  # - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: shop } }
  #   podSelector:       { matchLabels: { app: order } }
    ports:
    - { protocol: TCP, port: 5432 }
```
The important part of Example C: `order`'s egress names **only `postgres-order`**, not all of `data`. So
even if `order` is compromised, it can reach its own database and nothing else in `data` — not
`postgres-payment`, not `postgres-auth`. That least-privilege scoping is the entire payoff of
database-per-service meeting zero-trust networking. Repeat this pair for each service↔its own datastore
(`auth↔postgres-auth`, `cart↔redis:6379`, `search↔elasticsearch:9200`, and the Kafka path on `9092` for
`order`/`inventory`/`notification`/`recommendation`/`thumbnail-job`).

Apply them all:
```bash
kubectl apply -f allow-gateway-to-order.yaml -f allow-order-to-payment.yaml \
  -f allow-order-to-its-postgres.yaml -f data-allow-postgres-order.yaml
# ...and the rest of the edge policies you wrote by the same pattern
```

### Step 4 — Turn `data` deny-by-default too
> What's happening here: the datastores are your crown jewels, so `data` gets the same treatment — deny
> everything, then (in Step 3's `data` policies) allow only the specific `shop` service that owns each
> store. This is what stops a popped `shop` pod from sweeping the databases.

Create `deny-all-data.yaml` (same shape as Step 1, different namespace):
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny, namespace: data }
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
```
```bash
kubectl apply -f deny-all-data.yaml
```
Because the datastores rarely need *egress* of their own (Postgres doesn't call out), this mostly locks
ingress down to exactly the allow-rules from Example C. Add a DNS-egress allow for `data` too if any
datastore needs name resolution (Kafka does, for inter-broker/advertised listeners) — same
`allow-dns` policy as Step 2, in the `data` namespace.

### Step 5 — Expose the two public edges through the ALB
> What's happening here: zero-trust locked *east-west* (pod-to-pod) traffic. The *north-south* edges —
> the internet reaching `api-gateway` and `frontend` — go through the ALB, which the Load Balancer
> Controller built from the Ingresses you created in `4.1`. Here you confirm those two edges are reachable
> and that the NetworkPolicies allow ALB traffic in.

An Ingress = the public reception desk that becomes a real ALB. You already created both Ingresses in
`4.1`; confirm they got public hostnames:
```bash
kubectl -n shop get ingress api-gateway frontend \
  -o custom-columns=NAME:.metadata.name,HOST:.status.loadBalancer.ingress[0].hostname
```
With `target-type: ip`, the ALB sends packets **straight to pod IPs**, so your ingress NetworkPolicies on
`api-gateway` and `frontend` must allow that. The clean way is to allow ingress from the cluster's pod/node
CIDR (where the ALB targets originate) on the edge ports. Create `allow-edge-ingress.yaml`:
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-edge-frontend, namespace: shop }
spec:
  podSelector: { matchLabels: { app: frontend } }
  policyTypes: [Ingress]
  ingress:
  - from:
    - ipBlock: { cidr: 10.0.0.0/16 }   # your VPC/pod CIDR that the ALB targets sit in
    ports:
    - { protocol: TCP, port: 3000 }
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-edge-gateway, namespace: shop }
spec:
  podSelector: { matchLabels: { app: api-gateway } }
  policyTypes: [Ingress]
  ingress:
  - from:
    - ipBlock: { cidr: 10.0.0.0/16 }   # match your actual VPC CIDR
    ports:
    - { protocol: TCP, port: 8080 }
```
```bash
kubectl apply -f allow-edge-ingress.yaml
```
Read it: traffic to `frontend:3000` and `api-gateway:8080` is allowed from the VPC CIDR (replace
`10.0.0.0/16` with your real one — find it with
`aws ec2 describe-vpcs --region ap-south-1 --query 'Vpcs[].CidrBlock'`). That covers the ALB's
in-VPC targets without opening these pods to the rest of the cluster. What to expect: both edges respond
from the internet; everything internal still obeys the allow-list.

## Verify
- **The deny works:** open a shell in a service that should NOT reach `payment` and confirm it's blocked,
  while `order` still can:
  ```bash
  kubectl -n shop exec deploy/search -- sh -c \
    'wget -qT2 -O- http://payment.shop.svc.cluster.local:8087/healthz; echo exit=$?'   # should TIME OUT / fail
  kubectl -n shop exec deploy/order  -- sh -c \
    'wget -qT2 -O- http://payment.shop.svc.cluster.local:8087/healthz; echo exit=$?'   # should SUCCEED
  ```
- **The app still works:** the full `4.1`/`4.2` flow (register → login → list products → add to cart →
  checkout) still completes through the gateway, and the `order.created` fan-out still fires — proving you
  opened every real edge and no more.
- **Datastores are sealed:** `kubectl -n shop exec deploy/cart -- sh -c 'wget -qT2 -O-
  http://postgres-payment.data.svc.cluster.local:5432; echo exit=$?'` fails (cart has no business touching
  payment's DB), while each service still reaches its **own** store.
- **Edges are public:** `curl` to both the `api-gateway` and `frontend` ALB hostnames responds.

## Concept deep-dive — zero-trust east-west networking with default-deny
The flat default ("any pod can reach any pod") makes the cluster a single soft target: breach one pod and
you can pivot to all of them. **Zero-trust** rejects the idea that being *inside* the network confers
trust — every connection must be explicitly authorized, regardless of where it comes from.

```
   WITHOUT policy (flat):                    WITH default-deny + allow-list (zero-trust):
   search ──┐                                 search ──X─► payment        (blocked)
   cart   ──┼─► EVERYTHING                    search ──X─► postgres-*      (blocked)
   order  ──┘   (incl. all DBs)               order  ──OK─► payment, its own DB only
                                              api-gw ──OK─► its mapped services only
   one popped pod = whole cluster             one popped pod = its own narrow blast radius
```

You implement it in two moves: (1) a **default-deny** policy flips the namespace from allow-all to
deny-all the instant it selects every pod; (2) **narrow allow policies** re-open exactly the call-graph
edges — each one naming a specific source label, target label, and port. Because NetworkPolicies are
*additive*, the deny stays in force for everything you didn't explicitly allow. The result: a compromised
`search` pod can talk to `catalog` and Elasticsearch (its real dependencies) and **nothing else** — not
the payment database, not auth. The blast radius of a breach shrinks from "the whole cluster" to "one
service's legitimate neighbors."

The one gotcha worth repeating: a NetworkPolicy is inert without a CNI that enforces it. The policy
*describes* the firewall; Calico/Cilium/VPC-CNI-policy-mode *is* the firewall. Verify enforcement, or
you've written documentation, not security.

*Interview line: "We run east-west zero-trust: each namespace is default-deny, and we re-allow only the
exact call-graph edges by pod label and port — so a compromised pod is confined to its real dependencies,
and the database-per-service boundary is enforced at the network, not just in app code. It only works
because the CNI (Calico/Cilium) actually enforces NetworkPolicy."*
