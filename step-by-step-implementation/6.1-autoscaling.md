# 6.1 — Autoscaling (pods & requests: HPA · KEDA · VPA · Karpenter)

## Goal
Right now your fleet runs a **fixed** number of replicas — whatever you typed in `replicas: 2` back in
Phase 03. That's wrong both ways: at 3am you're paying for idle pods, and at a Friday-sale spike those 2
pods fall over while a third never appears. In this part you make the *pods* scale themselves to load —
on CPU, then on real request-rate, then on Kafka lag, then all the way down to zero — and you right-size
the requests each pod asks for. Node scaling (Karpenter) is already done; here you feed it work.

## Why this part exists (read this first)
Phase 02 (`2.2`) gave you **Karpenter** — it adds *nodes* when *pods* don't fit. But Karpenter only ever
reacts to **Pending pods**. Nothing in your cluster yet *creates* those extra pods. That's the missing
half: a node autoscaler with no pod autoscaler in front of it never does anything, because the replica
count never changes, so pods never go Pending, so Karpenter sleeps.

This part installs the **pod-level** autoscalers that sit *above* Karpenter and actually change replica
counts in response to load. Picture a restaurant:

- **HPA** = the floor manager who hires more waiters when the queue at the door gets long, and sends them
  home when it's quiet. It changes how many *pods* you run.
- **KEDA** = a smarter floor manager for the *kitchen* — it watches the ticket rail (the Kafka backlog)
  and can scale the line cooks all the way to **zero** when there are no tickets at all.
- **VPA** = the manager who notices each waiter is actually doing the work of half a waiter, and rewrites
  their job description (CPU/memory **requests**) so you stop over-booking the building.
- **Karpenter** (already installed) = the landlord who adds floors when all those new staff don't fit.

The order matters: HPA/KEDA make more pods → pods don't fit → Karpenter adds nodes. You're building the
top of that chain today.

> NEW CONCEPT — what is an HPA, and why does it need a "metrics source"?
> A **HorizontalPodAutoscaler** is a controller (same reconcile-loop shape as everything in `2.2`) that
> watches some number — "average CPU across the catalog pods" — and changes `replicas` to keep that
> number near a target you pick. *Horizontal* = more **copies** of the pod (vs *vertical* = a bigger
> pod, which is VPA's job). The catch: Kubernetes has **no idea** what your pods' CPU usage is on its
> own. The HPA has to ask something. That something is the **metrics-server** (for CPU/memory) or a
> **metrics adapter** (for anything fancier). No metrics source installed → the HPA shows `<unknown>` for
> the current value and refuses to scale. So step one is always: install the thing that supplies numbers.

## Step 1 — Install metrics-server (the thing that supplies CPU numbers)

> A metrics-server = the cluster's bathroom scale. Without it, nobody knows what any pod weighs (CPU/mem),
> so nobody can decide to scale. An HPA on CPU is **blind** until this is running.

> What's happening here: most EKS clusters don't ship metrics-server by default. You install it once; it
> scrapes the kubelet on every node and exposes "how much CPU/memory is each pod using right now" through
> the Kubernetes metrics API. Every CPU-based HPA reads from it.

```bash
helm repo add metrics-server https://kubernetes-sigs.github.io/metrics-server/
helm repo update
helm upgrade --install metrics-server metrics-server/metrics-server -n kube-system
```
Read it back: add the official chart catalog, refresh it, install (or upgrade if it already exists)
metrics-server into `kube-system` — it's cluster infrastructure, same as the add-ons in `2.2`, so it
lives there, not in `shop`. After ~30s, prove it works:
```bash
kubectl top nodes        # prints CPU/mem per node
kubectl top pods -n shop # prints CPU/mem per pod
```
If `kubectl top` says "Metrics API not available", wait a minute (first scrape) or check
`kubectl -n kube-system logs deploy/metrics-server` — on some EKS setups you must add
`--set args={--kubelet-insecure-tls}` to the Helm command.

## Step 2 — HPA on catalog/search/api-gateway, on CPU first (the simple, always-works baseline)

> What's happening here: you start with the *boring, reliable* signal — CPU. You tell Kubernetes "keep
> average CPU at 60%; if it climbs, add replicas; if it drops, remove them, between 2 and 10 pods." CPU
> first because it needs nothing but metrics-server, and it proves the whole HPA wiring before you reach
> for fancier signals.

One prerequisite the HPA *quietly depends on*: every targeted pod must declare a **CPU request** (you set
`requests.cpu` back in `3.2`). "60% CPU" means 60% **of the request** — no request, no percentage, no
scaling. Make `catalog.yaml`'s HPA file:
```bash
nano catalog-hpa.yaml
```
Paste (this is the shape; repeat it for `search` and `api-gateway` by changing the name and `targetRef`):
```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: catalog, namespace: shop }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: catalog }
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target: { type: Utilization, averageUtilization: 60 }   # keep avg CPU at 60% of the request
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300    # wait 5 min of calm before removing pods (no flapping)
```
Apply it (and the two siblings once you've made them):
```bash
kubectl apply -f catalog-hpa.yaml
kubectl -n shop get hpa
```
Read the output: the `TARGETS` column should show something like `12%/60%` — current vs target. If it
shows `<unknown>/60%`, the HPA can't read CPU: either metrics-server isn't up (Step 1) or the Deployment
has no `requests.cpu`. The `behavior.scaleDown` window matters — without it the HPA yo-yos, adding and
removing pods every minute; 5 minutes of calm before scaling down keeps things stable.

## Step 3 — Scale on *real requests per second*, not CPU (Prometheus adapter + custom metric)

> NEW CONCEPT — custom/external metrics vs CPU.
> CPU is a **proxy** for load, and a bad one for I/O-bound web services: `api-gateway` can be drowning in
> requests while its CPU sits at 20% (it spends its life *waiting* on downstream calls). What you actually
> care about is **requests per second per pod**. That's a **custom metric** — a number that lives in
> **Prometheus** (you have it, via the Istio mesh from Phase 05, which records RPS for every service).
> To let an HPA read a Prometheus number, you install a **metrics adapter**: a translator that exposes
> Prometheus queries through the Kubernetes `custom.metrics.k8s.io` API the HPA already knows how to read.
> *Custom* metrics describe a pod (RPS per pod); *external* metrics describe something outside the cluster
> (a queue length) — same adapter, two API surfaces.

### 3a. Install the Prometheus adapter (the translator)
> A metrics adapter = an interpreter standing between the HPA (speaks "Kubernetes metrics API") and
> Prometheus (speaks "PromQL"). The HPA asks "RPS for catalog?"; the adapter runs a PromQL query and hands
> back a number.

```bash
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update
helm upgrade --install prometheus-adapter prometheus-community/prometheus-adapter \
  -n monitoring --create-namespace \
  --set prometheus.url=http://prometheus-server.monitoring.svc \
  --set prometheus.port=80
```
Point `prometheus.url` at wherever your Phase 05 Prometheus actually lives (`kubectl get svc -A | grep
prometheus` to find it). The adapter needs a **rule** telling it which PromQL to run for the metric named
`http_requests_per_second`. Put that in a values file:
```bash
nano adapter-values.yaml
```
```yaml
rules:
  custom:
  - seriesQuery: 'istio_requests_total{namespace="shop",pod!=""}'
    resources: { overrides: { namespace: {resource: "namespace"}, pod: {resource: "pod"} } }
    name: { matches: "istio_requests_total", as: "http_requests_per_second" }
    metricsQuery: 'sum(rate(istio_requests_total{<<.LabelMatchers>>}[1m])) by (<<.GroupBy>>)'
```
Read it back: "take Istio's `istio_requests_total` counter, turn it into a per-second **rate** over a
1-minute window, group it by pod, and expose it to Kubernetes under the friendly name
`http_requests_per_second`." Re-apply the adapter with these values:
```bash
helm upgrade prometheus-adapter prometheus-community/prometheus-adapter \
  -n monitoring -f adapter-values.yaml --reuse-values
```
Prove the custom metric is now visible to Kubernetes:
```bash
kubectl get --raw "/apis/custom.metrics.k8s.io/v1beta1/namespaces/shop/pods/*/http_requests_per_second" | jq
```
If that returns JSON with a value, the HPA can use it. If it 404s, the adapter rule didn't match — check
the metric name and namespace in `seriesQuery`.

### 3b. Point api-gateway's HPA at RPS instead of CPU
```bash
nano api-gateway-hpa.yaml
```
```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: api-gateway, namespace: shop }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: api-gateway }
  minReplicas: 2
  maxReplicas: 20
  metrics:
  - type: Pods
    pods:
      metric: { name: http_requests_per_second }
      target: { type: AverageValue, averageValue: "50" }   # aim for ~50 RPS per pod
```
```bash
kubectl apply -f api-gateway-hpa.yaml
kubectl -n shop get hpa api-gateway
```
`type: AverageValue, averageValue: "50"` means "keep each pod handling about 50 requests/sec; cross that
and add a pod." Now `api-gateway` scales on the thing that actually hurts it — traffic — not a CPU number
that lies. You can list *multiple* metrics in one HPA (CPU **and** RPS); the HPA scales on whichever
demands the most pods, which is a sensible safety net.

## Step 4 — KEDA on the Kafka consumers (scale on lag) and thumbnail-job (scale to zero)

> NEW CONCEPT — KEDA & scale-to-zero.
> An HPA's floor is **1** — it can never scale a Deployment to **0**, and it only understands CPU/memory
> or metrics-API numbers. Your async workers (`inventory`, `notification`, `recommendation`) shouldn't
> scale on CPU at all — they should scale on **how far behind they are**, i.e. the **consumer-group lag**
> on their Kafka topic. And `thumbnail-job` does nothing 95% of the day; running even one idle pod for it
> is waste. **KEDA** (Kubernetes Event-Driven Autoscaler) solves both: it's an add-on that scales
> Deployments based on **event sources** (Kafka lag, SQS depth, cron, 60+ others) and, crucially, can scale
> **to zero** and wake back up when the first event arrives. Under the hood KEDA *creates and manages an
> HPA for you* for the 1→N range, and handles the 0↔1 transition itself. We use it here because "scale on
> queue backlog, down to zero" is exactly its job and an HPA simply can't do it.

### 4a. Install KEDA (Helm)
```bash
helm repo add kedacore https://kedacore.github.io/charts
helm repo update
helm upgrade --install keda kedacore/keda -n keda --create-namespace
kubectl -n keda get pods    # keda-operator + metrics-apiserver should be Running
```

### 4b. Scale `inventory` on Kafka consumer-group lag
> What's happening here: instead of an HPA, you write a KEDA **ScaledObject**. It names the Deployment to
> scale and a **trigger** — here, "watch the lag of consumer group `inventory` on the `inventory-events`
> topic; if it grows, add consumers." Repeat with different names for `notification` and `recommendation`.

```bash
nano inventory-scaledobject.yaml
```
```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata: { name: inventory, namespace: shop }
spec:
  scaleTargetRef: { name: inventory }       # the Deployment to scale
  minReplicaCount: 1                         # keep 1 so latency stays low for steady traffic
  maxReplicaCount: 12
  triggers:
  - type: kafka
    metadata:
      bootstrapServers: kafka.data.svc.cluster.local:9092
      consumerGroup: inventory
      topic: inventory-events
      lagThreshold: "100"                    # ~100 unprocessed messages per replica → add a replica
```
```bash
kubectl apply -f inventory-scaledobject.yaml
kubectl -n shop get scaledobject
kubectl -n shop get hpa                      # note: KEDA auto-created an HPA named keda-hpa-inventory
```
Read it back: keep at least 1 consumer; if the backlog grows past ~100 messages per running pod, add
pods up to 12; as the group catches up, scale back down. `lagThreshold` is the dial — lower = more
aggressive scaling.

### 4c. Scale `thumbnail-job` to zero
> What's happening here: same ScaledObject, but `minReplicaCount: 0`. When its topic is empty, KEDA runs
> **zero** pods — you pay nothing. The instant a message lands, KEDA spins the first pod up.

```bash
nano thumbnail-job-scaledobject.yaml
```
```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata: { name: thumbnail-job, namespace: shop }
spec:
  scaleTargetRef: { name: thumbnail-job }
  minReplicaCount: 0                         # scale-to-zero when idle
  maxReplicaCount: 8
  cooldownPeriod: 120                        # wait 2 min of empty queue before going to zero
  triggers:
  - type: kafka
    metadata:
      bootstrapServers: kafka.data.svc.cluster.local:9092
      consumerGroup: thumbnail-job
      topic: thumbnail-requests
      lagThreshold: "20"
```
```bash
kubectl apply -f thumbnail-job-scaledobject.yaml
kubectl -n shop get deploy thumbnail-job     # READY 0/0 when idle — that's correct, not broken
```
`0/0` is the success state here, not a failure. `cooldownPeriod: 120` stops it thrashing to zero between
two messages that arrive 30 seconds apart.

## Step 5 — VPA in *recommend* mode to right-size requests

> NEW CONCEPT — VPA vs HPA (and the one rule you must not break).
> **HPA scales out** (more pods); **VPA scales up** (bigger pods — it rewrites each pod's CPU/memory
> **requests**). You set those requests in `3.2` by *guessing* (`cpu: 50m`). Guesses are usually wrong:
> too low and pods get throttled/OOM-killed; too high and you waste capacity and make Karpenter buy nodes
> you didn't need. VPA watches real usage and tells you the *right* numbers.
> THE RULE: never run VPA and HPA **on the same CPU/memory signal for the same workload** — they fight
> (HPA adds pods to lower per-pod CPU; VPA shrinks requests so per-pod CPU looks higher; loop). The clean
> pattern: VPA in **recommend-only** ("Off") mode — it *suggests* requests, it doesn't change them — and
> you apply its numbers by hand. That coexists with HPA perfectly because VPA never touches anything.

> A VPA in recommend mode = a fitness coach who measures you and writes down your ideal portion sizes on a
> notepad, but never reaches over and changes your plate. You read the notepad and adjust yourself.

### 5a. Install the VPA components
VPA isn't a single Helm chart on EKS by default; install it via the Fairwinds chart (recommender only is
enough for our purpose):
```bash
helm repo add fairwinds-stable https://charts.fairwinds.com/stable
helm repo update
helm upgrade --install vpa fairwinds-stable/vpa -n vpa --create-namespace \
  --set updater.enabled=false \
  --set recommender.enabled=true
```
`updater.enabled=false` is deliberate — we only want recommendations, never automatic eviction/resizing.

### 5b. Ask for recommendations on catalog
```bash
nano catalog-vpa.yaml
```
```yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata: { name: catalog, namespace: shop }
spec:
  targetRef: { apiVersion: apps/v1, kind: Deployment, name: catalog }
  updatePolicy: { updateMode: "Off" }        # recommend ONLY — never auto-change the pod
```
```bash
kubectl apply -f catalog-vpa.yaml
```
After it's watched real traffic for a while (give it 10-15 minutes minimum), read its homework:
```bash
kubectl -n shop describe vpa catalog
```
Look at the `Recommendation` block — `Target` is VPA's suggested `requests`, `Lower/Upper Bound` the
range. If it says target CPU is `120m` but your Deployment requests `50m`, you've been under-provisioning;
edit `catalog.yaml`'s `requests` to match and re-apply. You did the change by hand, so HPA never got
surprised.

> Why "Off" and not "Auto"? In `Auto` mode VPA **evicts and recreates** pods to resize them, which both
> causes disruption and collides with your HPA. For a service that already has an HPA, recommend-only is
> the safe, senior choice — you get the data without the fight.

## Step 6 — Let Karpenter catch the overflow (already installed, just confirm)

> What's happening here: nothing to install — this is the payoff. When Steps 2-4 push replica counts up
> and the new pods don't fit on existing nodes, they go `Pending`, and **Karpenter** (from `2.2`) launches
> nodes to hold them. You're just confirming the whole chain composes.

Generate load (or use a `kubectl scale` on a test deployment) and watch all three layers move at once:
```bash
kubectl -n shop get hpa -w &           # pods rising on the HPAs
kubectl get nodes -w                    # within ~1 min Karpenter adds a node for the overflow pods
```
When the load drops: HPAs scale pods down → nodes go idle → Karpenter consolidates them away. Ctrl-C the
watches when you've seen it.

## Verify (the part is done when…)
- `kubectl top pods -n shop` returns numbers (metrics-server live).
- `kubectl -n shop get hpa` shows real `TARGETS` (e.g. `12%/60%`, `30/50`), not `<unknown>`.
- `kubectl get --raw ".../http_requests_per_second"` returns a value (custom metric wired).
- `kubectl -n shop get scaledobject` shows `inventory`/`notification`/`recommendation` `READY=True`, and
  `thumbnail-job` sits at `0/0` when idle and wakes on a message.
- `kubectl -n shop describe vpa catalog` shows a `Recommendation` you can act on.
- Under load, replica counts rise **and** Karpenter adds a node; under calm, both unwind.

## Concept deep-dive — the autoscaling stack (who scales what, and how they compose)
Four autoscalers, four jobs, and they only work because each owns a *different* axis:

```
        ┌──────────────────────────────────────────────────────────┐
  load  │  HPA / KEDA  → change REPLICAS (how many pods)            │  horizontal
  ───►  │      │                                                    │
        │      ▼  new pods don't fit                                │
        │  Karpenter   → change NODES   (how much hardware)         │  cluster
        └──────────────────────────────────────────────────────────┘
   VPA  → change REQUESTS (how big each pod claims to be)              vertical / sizing
```

- **HPA** (and **KEDA**, which is an HPA-plus-scale-to-zero for event sources) answers *"how many copies?"*
  It reacts to a live signal — CPU, RPS, Kafka lag — and edits `replicas`. KEDA's extra trick is the
  0↔1 edge an HPA can't cross.
- **Karpenter** answers *"is there room?"* It never looks at CPU targets or queues; it only sees
  **Pending pods** and buys EC2 to fit them (then removes idle nodes). It is *downstream* of HPA/KEDA —
  it can only react after a pod autoscaler has created demand.
- **VPA** answers *"is each pod the right size?"* It tunes the **requests** that both the scheduler and
  Karpenter use for bin-packing. Wrong requests poison everything above it: too-high requests make
  Karpenter over-buy; too-low requests make HPA's CPU percentages meaningless. We keep VPA in
  recommend-only mode so it informs without fighting the HPA.

The composition rule that keeps them from fighting: **HPA/KEDA and VPA must not both act on the same
resource signal for the same workload.** Horizontal scaling on CPU + vertical scaling on CPU is a feedback
loop. Horizontal on CPU/RPS + vertical *recommendations* you apply manually is harmony.

*Interview line: "HPA and KEDA scale pods horizontally on load and queue depth, KEDA adding scale-to-zero
for event-driven work; Karpenter scales nodes by reacting to Pending pods downstream of them; and VPA
right-sizes the per-pod requests everything else bin-packs against — kept in recommend mode so it never
fights the horizontal autoscaler on the same metric."*
