# 9.1 — Provision the second region (UK foundation: cluster + add-ons + namespaces)

## Goal
Stand up a **complete, empty foundation** in a second AWS region — London (`eu-west-2`) — that is the exact
twin of what you built in Mumbai across Phases 02. By the end you'll have a new EKS cluster
`ecom-cluster-uk`, its OIDC provider, a node group, the same three add-ons (AWS Load Balancer Controller,
ExternalDNS, Karpenter), and the `shop` / `data` namespaces with quotas — all running in London, all empty,
ready for the app to land on in `9.2`.

## Why this part exists (read this first)
Everything you've built so far (Phases 01–08) lives in **one** region, Mumbai. A user in London still has
their packets fly to Mumbai and back on every click — that's ~120–150 ms of round-trip you can't optimise
away with more pods, because it's the speed of light over a long cable. And if Mumbai has a bad day, your
*entire* shop is down, worldwide. The fix is a **second, independent regional stack** close to your UK
users, with a global router (built in `9.3`) deciding who goes where.

This part builds only the **foundation** of that second stack — the cluster and its plumbing, no app yet.
Think of it as redoing `2.1` + `2.2` + `2.3`, but in London with London values. You already proved every
one of these steps in Mumbai, so this part is deliberately thin: it mostly points back at those parts and
calls out **exactly what changes per region**.

> NEW CONCEPT — regional isolation: each region is its own everything.
> A "region" in AWS is not a setting you flip — it's a separate copy of the whole world. `eu-west-2` has its
> own **VPC** (network), its own **EKS control plane** (a brand-new Kubernetes brain), its own EC2 instances,
> its own Route 53 *records* (the hosted zone is global, but you add region-specific records), its own ECR
> registry endpoint, its own IAM **OIDC provider**. Nothing in London talks to Mumbai automatically. That
> isolation is the **feature**: a London control-plane outage, a bad deploy in London, an AZ failure in
> London — none of it can reach Mumbai. The price of that isolation is that you must **build the foundation
> twice**. This part is the second build.

> NEW CONCEPT — why you *template* the region instead of copy-pasting it.
> It's tempting to copy your Mumbai commands and hand-edit `ap-south-1` → `eu-west-2` in each one. Don't do
> it ad-hoc — that's how `region` ends up right in nine commands and wrong in the tenth (the one that then
> silently provisions in the wrong place). Instead, declare the per-region values **once** at the top as
> shell variables, and let every command read from them. Same script, swap the variable block, get an
> identical region. The variables you'll set below are the *entire* difference between Mumbai and London:
> region, the two zones, cluster name, account id (same), and the ECR endpoint host.

## Prerequisites
- The full single-region stack is **proven and in Git** — Mumbai's `ecom-cluster` ran Phases 01–08 and all
  its manifests are committed. A second region is "re-apply the same manifests in a new cluster", which is
  the whole point of `9.2`. This part just makes the cluster they'll land on.
- An EC2 **key pair** existing **in eu-west-2** (key pairs are regional — your Mumbai
  `eks-jenkins-pipeline` key does **not** exist in London). Create one named `eks-jenkins-pipeline` in
  eu-west-2 first, or drop the `--ssh-access` flags below.
- The same tools from [`1.4-install-aws-tools.md`](./1.4-install-aws-tools.md): `eksctl`, current
  `kubectl`, `awscli`, `helm`.

> Heads-up on what this part is NOT: this brings up a *running stack's foundation* in London. It does **not**
> replicate any data. Postgres rows and Kafka messages in Mumbai are **not** in London. Cross-region data
> replication is Phases 10 (databases) and 12 (Kafka) — separate, harder problems. For now each region's
> data is its own island; we're only solving **routing to a running stack** in `9.1`–`9.3`.

## Before you start — set the per-region variable block
> What's happening here: you set the five values that define "London" once, in your shell. Every command
> below reads them, so there's nothing to hand-edit per command. To rebuild *any* region later, you change
> only this block.

Run this in your terminal (the Jenkins instance, or your laptop):
```bash
export REGION=eu-west-2                        # London
export ZONES=eu-west-2a,eu-west-2b             # two AZs in London (HA, same as Mumbai's two)
export CLUSTER=ecom-cluster-uk                 # the UK cluster's name — DIFFERENT from Mumbai's
export ACCOUNT=169424082295                    # same AWS account (account is global)
export ECR=$ACCOUNT.dkr.ecr.$REGION.amazonaws.com   # London's ECR endpoint host
```
Read it back: London, zones `a`+`b`, a cluster called `ecom-cluster-uk`, same account, and an ECR host that
points at **London's** registry endpoint (`...eu-west-2.amazonaws.com`, not `ap-south-1`). That ECR host is
the one per-region value that bites people — an image reference baked with the Mumbai host won't pull in
London (more on that in `9.2`).

> The Mumbai equivalent of this block was `REGION=ap-south-1`, `ZONES=ap-south-1a,ap-south-1b`,
> `CLUSTER=ecom-cluster`. That two-line diff is *literally* the difference between the regions.

## Step 1 — Create the London control plane + OIDC + node group (re-do `2.1` with London values)
> What's happening here: this is exactly [`2.1-create-eks-cluster.md`](./2.1-create-eks-cluster.md) — brain
> first with no workers, turn on OIDC, then add the workers — but every region/zone/name now comes from your
> variable block instead of being typed as `ap-south-1` / `ecom-cluster`. Re-read `2.1` if any single command
> is fuzzy; here we just feed it London.

### 1a. Control plane, no workers yet
```bash
eksctl create cluster \
  --name="$CLUSTER" \
  --region="$REGION" \
  --zones="$ZONES" \
  --without-nodegroup
```
Same slow (~15–20 min) step as Mumbai: eksctl builds London a fresh VPC, subnets across `eu-west-2a/b`, and
IAM roles via CloudFormation, then writes your kubeconfig pointed at `ecom-cluster-uk`. The only thing that
changed from `2.1` is that the values came from `$CLUSTER` / `$REGION` / `$ZONES`.

### 1b. Turn on the OIDC provider (London gets its OWN one)
```bash
eksctl utils associate-iam-oidc-provider \
  --region "$REGION" \
  --cluster "$CLUSTER" \
  --approve
```
> This registers a **new, separate** IAM OIDC Identity Provider for the London cluster. Mumbai's OIDC
> provider is a different cluster's endpoint and can't vouch for London's pods — that's regional isolation
> again. Every IRSA role you make below trusts *this* London provider. (Re-read the OIDC/IRSA deep-dive for `2.1` in `project_learning.md`
> if it's hazy — you're about to use IRSA three more times.)

### 1c. Add the worker nodes
```bash
eksctl create nodegroup \
  --cluster="$CLUSTER" \
  --region="$REGION" \
  --name=node2 \
  --node-type=t3.medium \
  --nodes=3 --nodes-min=2 --nodes-max=4 \
  --node-volume-size=20 \
  --ssh-access --ssh-public-key=eks-jenkins-pipeline \
  --managed \
  --asg-access --external-dns-access --full-ecr-access --appmesh-access --alb-ingress-access
```
Identical to `2.1` Step 3. `--full-ecr-access` lets London's nodes pull from **London's** ECR;
`--alb-ingress-access` / `--external-dns-access` pre-grant what the add-ons in Step 2 want. Remember
`--ssh-public-key=eks-jenkins-pipeline` requires that key pair to exist **in eu-west-2** — that's the
prerequisite above. Drop the two `--ssh*` flags if you skipped it.

### 1d. Point kubectl at London and confirm
```bash
aws eks update-kubeconfig --region "$REGION" --name "$CLUSTER"
kubectl config current-context     # should now name ecom-cluster-uk / eu-west-2
kubectl get nodes                  # 3 London workers, each "Ready"
```
Three `Ready` London nodes = the second region's brain and muscle are alive. (You now have **two** clusters
in your kubeconfig; switching cleanly between them is the whole topic of `9.2` — for the rest of *this* part
you stay pointed at London.)

If it fails: the usual culprit is the missing eu-west-2 key pair in 1c, or an old `kubectl`. The error text
names which.

## Step 2 — Install the same three add-ons (re-do `2.2` with London values)
> What's happening here: this is exactly [`2.2-cluster-addons.md`](./2.2-cluster-addons.md) — the front door
> (ALB Controller), the street address (ExternalDNS), and the ability to add floors (Karpenter) — installed
> the same disciplined IRSA way, into London. The commands below are `2.2`'s commands with `$CLUSTER` /
> `$REGION` swapped in. The deep "what is a controller / reconcile loop" explanation lives in `2.2`; don't
> repeat it in your head, just install.

> One-liner reminder of what each is: **ALB Controller** = the worker who reads your Ingress note and builds
> a real AWS load balancer. **ExternalDNS** = the clerk who registers a human DNS name in Route 53 pointing
> at it. **Karpenter** = the crew boss who launches cheap spot nodes when pods can't fit.

### 2a. AWS Load Balancer Controller
The IAM **policy** `AWSLoadBalancerControllerIAMPolicy` is account-wide and you already created it for
Mumbai — IAM policies are global, so **skip re-creating it** (it'll error "already exists", which is fine).
The IRSA ServiceAccount and the Helm release, though, are **per-cluster** and must be made again for London:
```bash
eksctl create iamserviceaccount \
  --cluster "$CLUSTER" --region "$REGION" \
  --namespace kube-system --name aws-load-balancer-controller \
  --attach-policy-arn arn:aws:iam::$ACCOUNT:policy/AWSLoadBalancerControllerIAMPolicy \
  --approve

helm repo add eks https://aws.github.io/eks-charts
helm repo update
helm install aws-load-balancer-controller eks/aws-load-balancer-controller \
  -n kube-system \
  --set clusterName="$CLUSTER" \
  --set serviceAccount.create=false \
  --set serviceAccount.name=aws-load-balancer-controller
```
The IRSA step builds a **new** IAM role in London that trusts **London's** OIDC provider — even though the
*policy* it attaches is the shared one. `--set clusterName="$CLUSTER"` is what makes this controller build
its ALBs in London's VPC, not Mumbai's. Check it: `kubectl -n kube-system get deploy
aws-load-balancer-controller` should read `READY 1/1`.

### 2b. ExternalDNS
```bash
eksctl create iamserviceaccount \
  --cluster "$CLUSTER" --region "$REGION" \
  --namespace kube-system --name external-dns \
  --attach-policy-arn arn:aws:iam::aws:policy/AmazonRoute53FullAccess \
  --approve

helm repo add external-dns https://kubernetes-sigs.github.io/external-dns/
helm repo update
helm install external-dns external-dns/external-dns -n kube-system \
  --set provider=aws \
  --set serviceAccount.create=false \
  --set serviceAccount.name=external-dns \
  --set policy=sync \
  --set txtOwnerId="$CLUSTER"
```
> Critical per-region change: `txtOwnerId="$CLUSTER"` is `ecom-cluster-uk` here, **not** `ecom-cluster`.
> Both regions' ExternalDNS instances write into the **same global Route 53 hosted zone**, so they'd happily
> stomp each other's records. The `txtOwnerId` marker is what makes London's ExternalDNS only ever touch the
> records *it* created and leave Mumbai's alone. Get this wrong (both set to the same owner id) and the two
> regions will fight over DNS — a genuinely nasty bug. This is also exactly why `9.3`'s global records are
> created **by hand**, not by ExternalDNS: a record that points at *both* regions can't be owned by one.

### 2c. Karpenter
Karpenter's IAM roles + the SQS spot-interruption queue are per-cluster; create them for London from the
official getting-started CloudFormation (same as you did for Mumbai), then:
```bash
helm registry login public.ecr.aws
helm upgrade --install karpenter oci://public.ecr.aws/karpenter/karpenter \
  -n karpenter --create-namespace \
  --set settings.clusterName="$CLUSTER" \
  --set settings.interruptionQueue="$CLUSTER"
```
Then give London's Karpenter its launch policy — the **same** `NodePool` + `EC2NodeClass` from `2.2`
Step 3b. The `NodePool` YAML is region-agnostic (it talks about spot/amd64/cpu limits, not regions), so you
can apply the *identical* file:
```bash
nano nodepool.yaml      # paste the SAME NodePool + EC2NodeClass from 2.2 Step 3b
kubectl apply -f nodepool.yaml
```
> That the NodePool file is byte-for-byte identical across regions is the templating idea paying off: the
> region-specific bits live in Karpenter's `settings.clusterName` (a Helm value), not in the manifest.

## Step 3 — Namespaces + quotas (re-do `2.3`, unchanged)
> What's happening here: carve London into the same two floors — `shop` and `data` — with the same guardrails.
> The manifests from [`2.3-namespaces-and-quotas.md`](./2.3-namespaces-and-quotas.md) have **zero**
> region-specific content (namespaces, labels, CPU/memory budgets — none of it mentions a region), so this
> is a pure re-apply.

```bash
kubectl create namespace shop
kubectl create namespace data
kubectl label namespace shop tier=app
kubectl label namespace data tier=data

# the SAME quotas.yaml + limits.yaml from 2.3 — no edits needed
kubectl apply -f quotas.yaml -f limits.yaml
```
> Make sure your context is still London before you run this (`kubectl config current-context` →
> `ecom-cluster-uk`). Applying these to the wrong cluster is harmless here, but it's the exact mistake that
> wrecks a real deploy in `9.2` — start building the "check the context first" reflex now.

## Verify (the whole part is done when…)
- `kubectl config current-context` names `ecom-cluster-uk` / `eu-west-2`, and `kubectl get nodes` shows 3
  `Ready` London nodes.
- `kubectl -n kube-system get deploy aws-load-balancer-controller external-dns` → both `READY 1/1`.
- A Karpenter `inflate` test (the one from `2.2` Step 3c) adds a London node within ~1 min, and removing the
  test deployment lets the node go away.
- `kubectl get ns shop data` lists both, and `kubectl -n shop describe resourcequota shop-quota` shows the
  budget — London's floors and guardrails exist.
- London is a perfect **empty twin** of Mumbai's foundation. No app, no data — that's `9.2`.
