# 01 — Set up the EC2 instance (Jenkins + EKS bastion host)

## Goal
A single always-on Ubuntu EC2 instance that (a) runs **Jenkins** for CI and (b) acts as the workstation
from which we create and manage the **EKS** cluster.

## Why
- Jenkins needs a persistent Linux host; a plain EC2 instance is the simplest way to get one.
- The same instance doubles as our "bastion": we install awscli/kubectl/eksctl on it and drive EKS from
  here, so we don't juggle local tooling.
- Region: **ap-south-1 (Mumbai)** — same region as ECR (`ecom-repo`) and the EKS cluster.

## Prerequisites
- The **`eks-user`** IAM user from [`00-create-iam-user.md`](./1.1-create-iam-user) (with an access key).
- An EC2 **key pair** named **`eks-jenkins-pipeline`** (used for SSH now, and for the EKS node group later).

## Steps

### 1. Launch the instance (AWS console)
- **AMI:** Ubuntu 22.04 / 24.04 LTS
- **Instance type:** **t3.medium** (2 vCPU / 4 GB) — see the note; pick this from the start.
- **Key pair:** `eks-jenkins-pipeline`
- **Storage:** **30 GB gp3** (Docker images for 13 services need room)
- **Security group inbound (restrict the source — do NOT use `0.0.0.0/0`):**
  - **22 (SSH)** — from *your* IP only
  - **8080 (Jenkins)** — from *your* IP (the UI) **and** GitHub's webhook ranges (webhook delivery) — see the "Security group hardening" note

### 2. SSH in and update package lists
```bash
ssh -i eks-jenkins-pipeline.pem ubuntu@<public-ip>
sudo apt update
```

That's it for the host — move on to Jenkins.

## Notes
- **Use `t3.medium` (4 GB) from the very beginning.** Don't start on `t2.micro`/`t3.micro` (1 GB).
  On a 1 GB instance you *will* hit:
  - Go builds **OOM-killed** during compile,
  - Jenkins built-in node going **offline** on low `/tmp` (Free Temp Space < 1 GiB),
  - `containerd` "failed to create diff tar stream" errors under load.

  All of those forced us to add swap and resize mid-stream. **t3.medium avoids every one of them** —
  4 GB RAM and a `/tmp` (tmpfs) large enough that the monitor never trips. No swap needed.

  > If you're ever stuck on a small instance, add swap as a stop-gap:
  > ```bash
  > sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile
  > sudo mkswap /swapfile && sudo swapon /swapfile
  > echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab   # persists across reboot
  > ```

- **Public IP changes on stop/start** unless you allocate an **Elastic IP**. A changing IP breaks the
  GitHub webhook and the Jenkins URL every time. Allocate an Elastic IP (free while attached to a
  running instance) and associate it once for a permanent IP — then you never re-fix the webhook.
  - Current public IP from the instance: `curl -s http://169.254.169.254/latest/meta-data/public-ipv4; echo`

- **Resizing keeps your data** — it lives on the EBS root volume. Stop → Change instance type → Start.
  (Only needed if you didn't start on t3.medium.)

- **Security group hardening — restrict port 8080 (we use this).** Don't expose the Jenkins UI to the
  whole internet. Allow `8080` only from:
  - **your IP** (to reach the UI), and
  - **GitHub's webhook ranges** (so pushes can trigger jobs):
    `192.30.252.0/22`, `185.199.108.0/22`, `140.82.112.0/20`, `143.55.64.0/20`

  Remove any `0.0.0.0/0` rule on 8080, and keep **22 (SSH)** to your IP only.
  (Current GitHub ranges: `https://api.github.com/meta` → `hooks`. Note: a home/ISP IP can change —
  if you lose UI/SSH access, re-add your new IP.)
  > Production-shaped version: put Jenkins behind nginx/ALB with **HTTPS on 443** and stop exposing raw 8080.

## Verify
```bash
free -h     # RAM ~3.7Gi
nproc       # 2 vCPU
```

## Concept deep-dive — Security Groups & EC2 networking

**Security Group = a stateful virtual firewall** attached to the instance's network interface (ENI).
- **Stateful:** if you allow an inbound request, the **response is automatically allowed back out** — you
  only manage inbound rules; no matching outbound rule is needed for replies.
- **Allow-only:** SGs have no `Deny` rules; anything not explicitly allowed is denied (default-deny inbound).
- Contrast a **NACL** (Network ACL): **stateless**, at the **subnet** level, has allow *and* deny, and you'd
  have to open **ephemeral return ports** yourself. SGs = per-instance access; NACLs = coarse subnet backstop.

**Public vs private IP (why the IP changed on resize).**
- **Private IP** (e.g. `172.31.14.89`) — inside the VPC, **stable** for the instance's life.
- **Public IP** — auto-assigned, **NAT-mapped** by the Internet Gateway, and **ephemeral**: released on stop,
  a new one assigned on start.
- **Elastic IP** — a static public IPv4 you allocate + associate, so it survives stop/start.
```
internet --> [IGW: NAT public<->private] --> [Security Group: stateful] --> instance ENI (private IP)
```

**Why an SG fits here.** We need "let my IP + GitHub reach 8080, and me reach 22" at the **instance** level —
exactly an SG's job, statefully and simply. **Why not a NACL:** it's subnet-wide (hits every instance in the
subnet) and stateless (you'd also open return ports) — wrong granularity for per-instance access.
