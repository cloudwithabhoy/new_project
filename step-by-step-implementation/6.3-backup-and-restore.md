# 6.3 — Backup and restore (Velero · S3 · IRSA · a real restore drill)

## Goal
Your cluster now scales (`6.1`) and survives node operations (`6.2`). But there's a failure mode neither
covers: someone runs `kubectl delete ns shop` at 2am, a bad `helm upgrade` wipes objects, or an EBS volume
gets corrupted. There's no replica to fall back on — the *declaration itself* is gone. In this part you
install **Velero**, point it at an **S3 bucket** (authenticated cleanly via **IRSA**, no stored keys),
schedule automatic backups of the `shop`/`data` namespaces *and* their persistent volumes, and then — the
part everyone skips and regrets — you **delete something and restore it**, so you actually know the
backups work.

## Why this part exists (read this first)
`6.1` and `6.2` keep the app **running**. This part is about getting it **back** after it's gone. Those are
different categories: an HPA can't recover a namespace someone deleted, and a PDB can't un-corrupt a
database volume. Backup is the floor under everything else — the last line when scaling and disruption
protection weren't the problem.

Picture your cluster's state as two things that can be lost:
- The **cluster objects** — every Deployment, ConfigMap, Secret, Service, PVC. These live in etcd. Lose
  them and the app's *blueprint* is gone.
- The **volume data** — what's actually *inside* the Postgres/Kafka EBS volumes. The blueprint is useless
  if the data's gone.

Velero backs up **both**: it exports the cluster objects to S3 *and* triggers **EBS volume snapshots** for
the persistent data, in one operation.

> NEW CONCEPT — what Velero backs up, and why an untested backup isn't a backup.
> **Velero** is a backup controller you run *inside* the cluster. On a backup it does two things at once:
> (1) it reads the Kubernetes API and writes every selected object (Deployments, Secrets, PVCs…) as files
> into an **S3 bucket**; (2) for each PersistentVolume, it asks AWS to take an **EBS snapshot** of the
> underlying disk. A restore replays both — re-creates the objects and provisions new volumes from the
> snapshots. Now the hard truth: **a backup you have never restored is not a backup — it's a hope.**
> Backups fail silently all the time: wrong IAM permission so snapshots never happened, an excluded
> namespace, a Secret that didn't round-trip. You only find out at the exact moment you can least afford
> to. That's why this part *ends with a restore drill*, not with "backups are scheduled."

## Before you start
Run from the machine whose `kubectl` talks to `ecom-cluster`:
```bash
kubectl config current-context     # ecom-cluster / ap-south-1
```
Constants you'll reuse: account `169424082295`, region `ap-south-1`, cluster `ecom-cluster`, namespaces
`shop` and `data`. Pick a globally-unique bucket name now — we'll use `ecom-velero-backups-169424082295`.

## Step 1 — Create the S3 bucket Velero stores backups in

> An S3 bucket here = Velero's filing cabinet. The cluster-object exports (and metadata pointing at the EBS
> snapshots) get written here; the actual volume data lives in EBS snapshots that the bucket *references*.

> What's happening here: one bucket, in the same region as the cluster, that Velero will own. Same-region
> matters — cross-region snapshot/restore adds cost and latency you don't want.

```bash
aws s3api create-bucket \
  --bucket ecom-velero-backups-169424082295 \
  --region ap-south-1 \
  --create-bucket-configuration LocationConstraint=ap-south-1
```
The `LocationConstraint` is required for every region except us-east-1; without it the call fails. If the
name's taken, pick another (bucket names are globally unique). You don't need to configure anything else on
the bucket — Velero writes its own folder structure inside it.

---

## Step 2 — Give Velero permission via IRSA (no access keys, ever)

> What's happening here: same disciplined pattern as every add-on in `2.2` — an IAM **policy** listing
> exactly what Velero may do (write that bucket, create/delete EBS snapshots), wired to a Kubernetes
> ServiceAccount through **IRSA**. Velero pods then get short-lived AWS credentials automatically; you
> store no keys anywhere.

### 2a. Create the IAM policy
Write the permission document:
```bash
nano velero-policy.json
```
```json
{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow",
      "Action": ["ec2:CreateSnapshot","ec2:DeleteSnapshot","ec2:DescribeSnapshots",
                 "ec2:DescribeVolumes","ec2:CreateTags","ec2:CreateVolume"],
      "Resource": "*" },
    { "Effect": "Allow",
      "Action": ["s3:GetObject","s3:DeleteObject","s3:PutObject","s3:ListMultipartUploadParts","s3:AbortMultipartUpload"],
      "Resource": "arn:aws:s3:::ecom-velero-backups-169424082295/*" },
    { "Effect": "Allow",
      "Action": ["s3:ListBucket"],
      "Resource": "arn:aws:s3:::ecom-velero-backups-169424082295" }
  ]
}
```
Read it back: the first block lets Velero create/delete the **EBS snapshots** (the volume data); the second
and third let it read/write **objects** inside the bucket and list it (the cluster-object exports). Create
the policy:
```bash
aws iam create-policy --policy-name VeleroBackupPolicy \
  --policy-document file://velero-policy.json
```

### 2b. Wire it to a ServiceAccount with IRSA
```bash
eksctl create iamserviceaccount \
  --cluster ecom-cluster --region ap-south-1 \
  --namespace velero --name velero \
  --attach-policy-arn arn:aws:iam::169424082295:policy/VeleroBackupPolicy \
  --approve
```
Plain English: "create a ServiceAccount named `velero` in the (soon-to-exist) `velero` namespace, backed by
an IAM role that trusts the cluster's OIDC provider and carries the policy from 2a." Exactly the IRSA move
from `2.2` — re-read that deep-dive in `project_learning.md` if it's fuzzy. (If the `velero` namespace doesn't exist yet, eksctl
creates it.)

## Step 3 — Install Velero pointed at the bucket and the EBS snapshotter

> What's happening here: install the Velero controller via Helm, telling it (a) which S3 bucket is its
> backup store, (b) to use the AWS plugin for EBS volume snapshots, and (c) to reuse the IRSA
> ServiceAccount from Step 2 instead of any stored credentials.

```bash
helm repo add vmware-tanzu https://vmware-tanzu.github.io/helm-charts
helm repo update
```
Put the install settings in a values file (cleaner than a wall of `--set`):
```bash
nano velero-values.yaml
```
```yaml
serviceAccount:
  server:
    create: false              # reuse the IRSA ServiceAccount from Step 2
    name: velero
credentials:
  useSecret: false             # no static keys — IRSA supplies credentials
initContainers:
- name: velero-plugin-for-aws
  image: velero/velero-plugin-for-aws:v1.10.0
  volumeMounts:
  - { mountPath: /target, name: plugins }
configuration:
  backupStorageLocation:
  - name: default
    provider: aws
    bucket: ecom-velero-backups-169424082295
    config: { region: ap-south-1 }
  volumeSnapshotLocation:
  - name: default
    provider: aws
    config: { region: ap-south-1 }
```
```bash
helm install velero vmware-tanzu/velero -n velero -f velero-values.yaml
kubectl -n velero get pods       # the velero deployment should reach Running 1/1
```
Read the load-bearing bits: `useSecret: false` + `serviceAccount...create: false, name: velero` is what
makes this **keyless** — Velero authenticates through the IRSA role, not a stored AWS secret. The
`velero-plugin-for-aws` init container is what teaches Velero to talk to **S3 and EBS** (Velero's core has
no cloud knowledge; the plugin adds it). `backupStorageLocation` = where objects go; `volumeSnapshotLocation`
= where volume snapshots go.

If the pod is `CrashLoopBackOff`, check `kubectl -n velero logs deploy/velero` — the usual cause is an IRSA
permission mistake in Step 2 (it'll log S3 `AccessDenied`) or a bucket name typo.

## Step 4 — Schedule automatic backups of the namespaces + their volumes

> A Velero `Schedule` = a recurring alarm clock that fires a backup on a cron. Set it once; Velero takes a
> fresh backup every night without you touching it.

> What's happening here: you create a `Schedule` that, nightly, backs up everything in `shop` and `data`
> **and** snapshots their PVs. You also set a TTL so old backups expire (and stop costing money) on their
> own.

You can do it with the Velero CLI (install it from the Velero releases page) — it's the cleanest way:
```bash
velero schedule create ecom-nightly \
  --schedule="0 2 * * *" \
  --include-namespaces shop,data \
  --snapshot-volumes=true \
  --ttl 168h0m0s
```
Read it back: "every day at 02:00, back up the `shop` and `data` namespaces, **snapshot their persistent
volumes** (`--snapshot-volumes=true` is what captures the Postgres/Kafka disk data), and keep each backup
for 7 days (`168h`) before deleting it." Prefer YAML? It's the same object:
```yaml
apiVersion: velero.io/v1
kind: Schedule
metadata: { name: ecom-nightly, namespace: velero }
spec:
  schedule: "0 2 * * *"
  template:
    includedNamespaces: [shop, data]
    snapshotVolumes: true
    ttl: 168h0m0s
```
Don't wait until 2am to test it — fire one immediately from the schedule and watch it finish:
```bash
velero backup create --from-schedule ecom-nightly manual-test-1
velero backup describe manual-test-1 --details      # watch Phase go InProgress → Completed
velero backup get                                   # lists backups + their phase
```
What to expect: `Phase: Completed`, a non-zero count of items backed up, and snapshot entries for your
PVs. If `Phase: PartiallyFailed`, run `velero backup logs manual-test-1` — a common cause is a PV whose
EBS volume the IAM policy couldn't snapshot (revisit Step 2a's `ec2:CreateSnapshot`).

## Step 5 — THE RESTORE DRILL (delete something real, bring it back)

> What's happening here: this is the whole point of the part. A backup is only proven by a restore. You'll
> delete a real object, confirm it's gone, restore from the backup you just took, and confirm it came back.
> Do this on something safe-to-lose first (a ConfigMap), then trust the same mechanism for the scary stuff.

### 5a. Break something on purpose
```bash
kubectl -n shop get configmap catalog       # confirm it exists (you made it in 3.2)
kubectl -n shop delete configmap catalog     # delete it — simulate the 2am mistake
kubectl -n shop get configmap catalog        # confirm it's gone (NotFound)
```

### 5b. Restore just that namespace from your backup
> What's happening here: you tell Velero "recreate everything from backup `manual-test-1`, but only the
> `shop` namespace." Velero replays the stored objects (and, for a full-namespace loss, re-provisions
> volumes from the snapshots).

```bash
velero restore create restore-drill-1 \
  --from-backup manual-test-1 \
  --include-namespaces shop
velero restore describe restore-drill-1      # watch Phase → Completed
```
Confirm the deleted object is back:
```bash
kubectl -n shop get configmap catalog        # it exists again
```
Read it back: `--from-backup manual-test-1` picks which backup to replay; `--include-namespaces shop`
scopes the restore so you don't disturb `data`. By default Velero **won't overwrite** objects that still
exist — it only recreates what's missing — so a restore is safe to run even when most of the namespace is
healthy.

### 5c. (When you're confident) rehearse the scary one
The same mechanism restores a wiped database volume: a restore of `data` re-creates the PVCs and
**provisions fresh EBS volumes from the snapshots**, so Postgres comes back with its data as of the last
backup. Practice it in a throwaway namespace before you ever need it for real — `velero restore create
... --namespace-mappings data:data-restore-test` restores into a *copy* namespace so you can verify the
data without touching production.

> What to expect on a volume restore: pods come up bound to brand-new PVCs whose volumes were created from
> the EBS snapshots. The data is current as of the backup, not the moment of deletion — which is exactly
> why backup *frequency* (your nightly schedule) sets your worst-case data-loss window.

---

## Verify (the part is done when…)
- `kubectl -n velero get pods` → Velero `Running 1/1` (IRSA working, no stored keys).
- `velero backup get` shows `manual-test-1` (and soon the nightly ones) as `Completed`, with volume
  snapshots recorded.
- `aws s3 ls s3://ecom-velero-backups-169424082295/` shows backup data written.
- The **restore drill** worked end to end: you deleted the `catalog` ConfigMap and `velero restore`
  brought it back. That — not the scheduled job existing — is what proves the backups are real.
