# 3.1 — Deploy the datastores (StatefulSets)

## Goal
Get the data layer running inside the cluster — starting with one database (`postgres-catalog`) and then
stamping out the rest. Each database gets its **own disk that survives** even when its pod is killed.

## Why this part exists (read this first)
Your microservices store things — products, orders, users. Those things have to live in a database, and the
database has to exist **before** the service that uses it. So the very first thing you deploy into your
clean cluster is the data layer. You'll deploy *one* database carefully, learn the key idea (stateful vs
stateless), and then repeat the same recipe for the others.

> NEW CONCEPT — "stateful" vs "stateless", and why databases are special.
> Most of your services are **stateless**: they keep nothing important on disk, so Kubernetes can kill a
> pod and start a fresh one anywhere — no harm done. A **database is stateful**: it *is* its data on disk.
> If Kubernetes killed it and started a blank replacement, you'd lose everything. So databases need two
> things ordinary pods don't: a **stable identity** (a fixed name + address) and a **disk that re-attaches
> to the new pod** when the old one dies. The Kubernetes object that provides both is a **StatefulSet**.

> NEW CONCEPT — database-per-service.
> Each microservice owns its **own** database; services never share a database or reach into each other's
> tables. That's why you'll see `postgres-catalog`, `postgres-order`, `postgres-auth`… — one per service.
> It keeps services independent: you can change `catalog`'s schema without breaking `order`.

## Prerequisites
- The EKS cluster from [`2.1-create-eks-cluster.md`](./2.1-create-eks-cluster.md), with the `data`
  namespace created in [`2.3-namespaces-and-quotas.md`](./2.3-namespaces-and-quotas.md).
- `kubectl` pointed at `ecom-cluster` (run `kubectl get nodes` to confirm).

## Steps

### Step 1 — Make the cluster able to hand out disks (EBS CSI + a gp3 StorageClass)
> What's happening here: a pod can't create an AWS disk on its own. You need (a) a driver that knows how to
> talk to AWS EBS, and (b) a "menu" telling Kubernetes what kind of disk to order. The driver is the **EBS
> CSI driver**; the menu is a **StorageClass**.

```bash
# 1. give the driver an IAM role so it can actually call AWS to create EBS volumes (IRSA)
eksctl create iamserviceaccount --name ebs-csi-controller-sa --namespace kube-system \
  --cluster ecom-cluster --region ap-south-1 \
  --attach-policy-arn arn:aws:iam::aws:policy/service-role/AmazonEBSCSIDriverPolicy \
  --approve --role-only --role-name AmazonEKS_EBS_CSI_DriverRole

# 2. install the driver, wired to that role
eksctl create addon --name aws-ebs-csi-driver --cluster ecom-cluster --region ap-south-1 \
  --service-account-role-arn arn:aws:iam::169424082295:role/AmazonEKS_EBS_CSI_DriverRole --force

# define a disk "menu item" called gp3
kubectl apply -f - <<'EOF'
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata: { name: gp3 }
provisioner: ebs.csi.aws.com
parameters: { type: gp3 }
volumeBindingMode: WaitForFirstConsumer
EOF
```
Why the IAM role (step 1): the driver's controller pod calls the AWS EC2 API (`CreateVolume`, `AttachVolume`)
on your behalf — an AWS call, so it needs IRSA creds just like the ALB controller did. **Skip it and your
PVCs hang in `Pending` forever** with no error on the pod. `AmazonEBSCSIDriverPolicy` grants exactly those
EBS actions.

Two things to understand about the StorageClass:
- `provisioner: ebs.csi.aws.com` → "when someone orders this disk, use the EBS driver to create it."
- `volumeBindingMode: WaitForFirstConsumer` → don't create the disk until a pod is actually scheduled, so
  the disk is made **in the same availability zone as the pod** (an EBS disk can only attach within its own
  AZ — get this wrong and the pod can never mount it).

> NEW CONCEPT — the `kubectl apply -f - <<'EOF' … EOF` trick: instead of saving a file first, you're piping
> the YAML straight into `kubectl apply` from the terminal. `-f -` means "read from standard input." Handy
> for small one-off objects; for anything you'll edit again, save a real `.yaml` file instead.

### Step 2 — Store the database password as a Secret
> What's happening here: the database needs a password, and you must not hardcode it in a YAML file. A
> **Secret** is Kubernetes' place for sensitive values; the pod reads it at runtime.

```bash
kubectl -n data create secret generic postgres-catalog --from-literal=POSTGRES_PASSWORD='<strong-pw>'
```
Note the `-n data` — you're putting this on the data floor. Pick a real strong password and remember it;
the `catalog` service will need the **same** value in `3.2`.

### Step 3 — Deploy the database itself (the StatefulSet + a headless Service)
> What's happening here: this is the actual database. You write one file describing two objects: the
> **StatefulSet** (the database pod + its disk) and a **headless Service** (its stable network name).

Create the file:
```bash
nano postgres-catalog.yaml
```
Paste this in:
```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata: { name: postgres-catalog, namespace: data }
spec:
  serviceName: postgres-catalog        # ties it to the headless Service below
  replicas: 1
  selector: { matchLabels: { app: postgres-catalog } }
  template:
    metadata: { labels: { app: postgres-catalog } }
    spec:
      containers:
      - name: postgres
        image: postgres:16
        ports: [{ containerPort: 5432 }]
        env:
        - { name: POSTGRES_DB,   value: catalog }
        - { name: POSTGRES_USER, value: catalog }
        - { name: PGDATA,        value: /var/lib/postgresql/data/pgdata }
        - name: POSTGRES_PASSWORD
          valueFrom: { secretKeyRef: { name: postgres-catalog, key: POSTGRES_PASSWORD } }   # from Step 2
        volumeMounts: [{ name: data, mountPath: /var/lib/postgresql/data }]
  volumeClaimTemplates:                 # THIS is what gives the pod its own surviving disk
  - metadata: { name: data }
    spec:
      accessModes: [ReadWriteOnce]
      storageClassName: gp3             # orders the disk from the menu you made in Step 1
      resources: { requests: { storage: 5Gi } }
---
apiVersion: v1
kind: Service
metadata: { name: postgres-catalog, namespace: data }
spec:
  clusterIP: None                       # "headless" — gives a stable DNS name, not a load-balanced IP
  selector: { app: postgres-catalog }
  ports: [{ port: 5432 }]
```
Then bring it to life and watch it come up:
```bash
kubectl apply -f postgres-catalog.yaml
kubectl -n data rollout status statefulset/postgres-catalog
kubectl -n data get pods,pvc            # expect pod postgres-catalog-0 Running + a PVC that is "Bound"
```
> NEW CONCEPT — PVC / PV / StorageClass (how the pod gets a real disk).
> Three objects work together: the **StorageClass** (`gp3`) is the *menu* — how to make a disk; a
> **PVC** (PersistentVolumeClaim) is the *order* — "I need 5Gi of gp3"; a **PV** (PersistentVolume) is the
> *actual disk* (a real EBS volume). You didn't write a PVC by hand — the StatefulSet's
> `volumeClaimTemplates` auto-creates one per pod (`data-postgres-catalog-0`). When the pod is scheduled,
> the **EBS CSI driver** sees the PVC, calls AWS `CreateVolume` to make the PV, binds them, and mounts it.
> Crucially the **PVC outlives the pod** — `delete pod` and the new one re-binds the *same* PV (same disk),
> which is exactly why your data survives. Check with `kubectl -n data get pvc,pv` (`Bound` = provisioned).

> NEW CONCEPT — what is a "headless" Service (`clusterIP: None`)?
> A normal Service gives you one shared IP that load-balances across many identical pods. A database isn't
> interchangeable like that — you want to reach *this specific* database by a stable name. A **headless**
> Service skips the shared IP and instead gives a stable DNS name: `postgres-catalog.data.svc.cluster.local`.
> That's the address your `catalog` service will use to connect.

### Step 4 — Prove the disk really survives (the whole point of a StatefulSet)
> What's happening here: you'll write data, then deliberately kill the database pod, and confirm the data is
> still there when Kubernetes restarts it. This is the lesson — the disk re-attaches.

```bash
# log into the running database and create a row
kubectl -n data exec -it postgres-catalog-0 -- psql -U catalog -d catalog \
  -c "CREATE TABLE t(x int); INSERT INTO t VALUES (1);"

# kill the pod — Kubernetes reschedules it AND re-attaches the same disk
kubectl -n data delete pod postgres-catalog-0

# read again after it restarts — the row is still there
kubectl -n data exec -it postgres-catalog-0 -- psql -U catalog -d catalog -c "SELECT * FROM t;"
```
> NEW CONCEPT — `kubectl exec -it <pod> -- <command>`: this runs a command *inside* a running pod, like
> SSHing into it. `-it` gives you an interactive terminal. Here you use it to run `psql` (the Postgres
> client) inside the database pod. Great for poking at a live pod to debug.

### Step 5 — Stamp out the rest of the datastores
You now know the recipe. Repeat Steps 2–3 for the other six Postgres databases (`postgres-auth`,
`postgres-user`, `postgres-order`, `postgres-payment`, `postgres-inventory`, `postgres-recommendation`),
and for **Redis**, **Elasticsearch**, and **Kafka** (KRaft mode) — each one is the same
StatefulSet + headless-Service + Secret pattern, just different names and images.
> You only need `postgres-catalog` alive to finish [`3.2`](./3.2-deploy-catalog.md); deploy the rest when
> the full fleet goes up.

## Verify
- `postgres-catalog-0` is `Running`, its PVC shows `Bound`, and the row you inserted **survived** a
  `delete pod`. If all three are true, you've got durable, stateful storage working.
