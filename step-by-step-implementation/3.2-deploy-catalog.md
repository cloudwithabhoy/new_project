# 3.2 — Deploy the first service (catalog)

## Goal
Get one real microservice — `catalog` — running in the `shop` namespace, talking to its database, and
reachable from the public internet through a load balancer. This is the first time the whole chain works
end to end.

## Why this part exists (read this first)
You have a database (`3.1`) but nothing using it yet. Before you deploy all 6 services, you prove the
**deploy recipe** on exactly one. Every service uses the identical shape — pull an image, give it config,
give it secrets, health-check it, expose it. Nail it once with `catalog` and the other twelve are just
copy-paste with different names.

> NEW CONCEPT — the five objects every service needs. A running, reachable service is made of five small
> pieces. Picture hiring a new worker:
> - **ConfigMap** = the non-secret instructions you hand them (which port, log level, the database's address).
> - **Secret** = the sensitive stuff (the database password) handed over privately.
> - **Deployment** = the worker themselves — runs your container, keeps 2 copies alive, restarts on crash.
> - **Service** = the worker's internal phone extension — a stable address other pods can call.
> - **Ingress** = the public reception desk — turns into a real AWS load balancer so the outside world can reach in.

## Prerequisites
- [`3.1`](./3.1-datastores.md) — `postgres-catalog` is running.
- The `catalog` image already in ECR (`ecom-repo:catalog-<sha>`, built by Jenkins in Phase 01).
- The AWS Load Balancer Controller installed (from [`2.2-cluster-addons.md`](./2.2-cluster-addons.md)) —
  it's what turns your Ingress into a real ALB.

Use the exact env-var keys from `services/catalog/README.md` ("DevOps handoff") — they're listed below.

## Steps

### Step 1 — Hand the service its non-secret config (ConfigMap)
> What's happening here: `catalog` needs to know what port to listen on and, crucially, the address of its
> database (the headless Service name from `3.1`). None of this is secret, so it goes in a ConfigMap.

```bash
kubectl -n shop create configmap catalog \
  --from-literal=PORT=8083 --from-literal=LOG_LEVEL=info \
  --from-literal=DB_HOST=postgres-catalog.data.svc.cluster.local \
  --from-literal=DB_PORT=5432 --from-literal=DB_USER=catalog \
  --from-literal=DB_NAME=catalog --from-literal=DB_SSLMODE=disable
```
Notice `DB_HOST=postgres-catalog.data.svc.cluster.local` — that's the stable DNS name the headless Service
gave the database in `3.1`. This is how one pod finds another across namespaces.

### Step 2 — Hand it the database password privately (Secret)
> What's happening here: same password you set in `3.1` Step 2, but now in the `shop` namespace so the
> `catalog` pod can read it. Secrets don't cross namespaces, so you create it again here.

```bash
kubectl -n shop create secret generic catalog --from-literal=DB_PASSWORD='<same-strong-pw-from-3.1>'
```

### Step 3 — Run the service and give it an internal address (Deployment + Service)
> What's happening here: this file has two objects. The **Deployment** runs your container (2 copies for
> resilience) and wires in the ConfigMap + Secret. The **Service** gives those pods one stable internal
> address so other services can call `catalog`.

Create `catalog.yaml`:
```bash
nano catalog.yaml
```
Paste:
```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: catalog, namespace: shop }
spec:
  replicas: 2
  selector: { matchLabels: { app: catalog } }
  template:
    metadata: { labels: { app: catalog } }
    spec:
      terminationGracePeriodSeconds: 20
      containers:
      - name: catalog
        image: 169424082295.dkr.ecr.ap-south-1.amazonaws.com/ecom-repo:catalog-<sha>   # your built image
        ports: [{ containerPort: 8083 }]
        envFrom:                              # pull in ALL keys from the ConfigMap + Secret at once
        - configMapRef: { name: catalog }
        - secretRef:    { name: catalog }
        livenessProbe:  { httpGet: { path: /healthz, port: 8083 }, periodSeconds: 10 }  # "are you alive?"
        readinessProbe: { httpGet: { path: /readyz,  port: 8083 }, periodSeconds: 5 }   # "ready for traffic?"
        resources:
          requests: { cpu: 50m,  memory: 64Mi }
          limits:   { cpu: 250m, memory: 128Mi }
---
apiVersion: v1
kind: Service
metadata: { name: catalog, namespace: shop }
spec:
  selector: { app: catalog }                 # routes to the pods labelled app=catalog
  ports: [{ port: 8083, targetPort: 8083 }]
```
> Replace `catalog-<sha>` with the real tag Jenkins pushed (e.g. `catalog-fd7ea04`). Find it in ECR or in
> the Jenkins build log.

> NEW CONCEPT — liveness vs readiness probes. Two health checks that sound the same but do opposite things.
> **Liveness** (`/healthz`) asks "is the process alive?" — if it fails, Kubernetes **restarts** the pod.
> **Readiness** (`/readyz`) asks "are you ready to serve?" — if it fails, Kubernetes **stops sending traffic**
> but leaves the pod running. `catalog`'s `/readyz` returns OK only when it can reach Postgres, so a pod
> that can't reach its database is quietly kept out of rotation instead of serving errors.

### Step 4 — Open a public door (Ingress)
> What's happening here: a Service is only reachable *inside* the cluster. To let the outside world in, you
> create an **Ingress**. The Load Balancer Controller from `2.2` sees it and builds a real AWS **ALB**
> pointing at your pods.

Create `catalog-ingress.yaml`:
```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: catalog
  namespace: shop
  annotations:
    kubernetes.io/ingress.class: alb
    alb.ingress.kubernetes.io/scheme: internet-facing      # public, not internal-only
    alb.ingress.kubernetes.io/target-type: ip              # send traffic straight to pod IPs
spec:
  rules:
  - http:
      paths:
      - path: /
        pathType: Prefix
        backend: { service: { name: catalog, port: { number: 8083 } } }
```

### Step 5 — Apply everything and watch it roll out
```bash
kubectl apply -f catalog.yaml -f catalog-ingress.yaml
kubectl -n shop rollout status deploy/catalog
kubectl -n shop get pods           # READY 1/1 means /readyz passed = it reached Postgres successfully
```
If a pod is stuck `0/1`, it usually can't reach the database — check the ConfigMap `DB_HOST` and that the
Secret password matches `3.1`. See logs with `kubectl -n shop logs deploy/catalog`.

### Step 6 — Prove it works from the internet (and that data persists)
> What's happening here: you grab the public ALB address, create a product through it, then kill the app
> pod and confirm the product is still there — because it lives in Postgres, not the pod.

```bash
# get the public hostname the ALB was given (may take a minute to appear)
ALB=$(kubectl -n shop get ingress catalog -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')

curl -X POST http://$ALB/products -H 'Content-Type: application/json' \
     -d '{"name":"Coffee Mug","price_cents":1299,"stock":42}'
curl http://$ALB/products                   # the product you just created comes back

kubectl -n shop delete pod -l app=catalog   # kill the app pods
curl http://$ALB/products                   # still there — data lived in Postgres, not the pod
```

## Verify
- `curl` to the ALB returns the product, and it **persists** across a `catalog` pod restart, and pods show
  `READY 1/1`. That's the full path — image → config → database → load balancer — working end to end.
