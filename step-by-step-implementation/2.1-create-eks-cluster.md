# 2.1 — Create the EKS cluster

## Goal
By the end of this part you'll have a real, running Kubernetes cluster on AWS — a control plane plus three
worker machines — that you can deploy your microservices onto.

## Why this part exists (read this first)
Everything you've built so far (Jenkins, ECR images) produces **containers**. But a container is just a
zipped-up app sitting in a registry; something has to actually *run* it, restart it if it crashes, give it
a network, and place it on a machine. That "something" is **Kubernetes**. In this part you create the
Kubernetes cluster that will run all 13 services.

> NEW CONCEPT — what is EKS, and what is a "control plane" vs "nodes"?
> A Kubernetes cluster has two halves:
> - The **control plane** = the brain. It decides what runs where, watches health, and stores the cluster's
>   desired state. Running this brain yourself is hard, so AWS runs it *for* you — that managed brain is
>   **EKS** (Elastic Kubernetes Service). You never SSH into it; you just talk to its API.
> - The **nodes** = the muscle. These are ordinary EC2 instances that actually run your containers. A group
>   of them managed together is a **node group**.
> Think of it as hiring a foreman (EKS, AWS-managed) and then giving him a crew of workers (your EC2 nodes).

We deliberately create the brain **first, with no workers** (`--without-nodegroup`), turn on a security
feature called **OIDC**, and only *then* add the workers. Why that order? Because OIDC/IRSA (explained at
the bottom — it's how pods get AWS permissions safely) is cleanest to wire up before any workload exists.
This is the standard, recommended eksctl pattern.

## Prerequisites
- Tools installed in [`1.4-install-aws-tools.md`](./1.4-install-aws-tools.md): `eksctl`, a current
  `kubectl`, and `awscli` configured as the `eks-user` identity.
- An EC2 **key pair named `eks-jenkins-pipeline`** already existing in **ap-south-1** (the node group
  references it so you *could* SSH into a worker if you ever needed to).

## Steps

### Step 1 — Create the control plane (the brain), no workers yet
> What's happening here: you're asking AWS to stand up a managed Kubernetes brain. This is the slow step
> (~15–20 min) because behind the scenes eksctl also builds a whole network for it — a VPC, subnets across
> two availability zones, IAM roles — using CloudFormation. You don't do any of that by hand; the one
> command does it all.

```bash
eksctl create cluster \
  --name=ecom-cluster \
  --region=ap-south-1 \
  --zones=ap-south-1a,ap-south-1b \
  --without-nodegroup
```
Reading the command: "create a cluster called `ecom-cluster` in Mumbai, spread across zones `a` and `b`,
but **don't** add any worker nodes yet." When it finishes, eksctl also writes your **kubeconfig** (the
file `kubectl` reads to know which cluster to talk to), so `kubectl` is already pointed at the new cluster.

> Two AZs on purpose: spreading across `ap-south-1a` and `-1b` means if one AWS data center has a problem,
> your cluster's network still spans another. This is your first taste of high availability.

### Step 2 — Turn on the OIDC provider (the safe-permissions switch)
> What's happening here: later, pods (like the load balancer controller in `2.2`) will need to call AWS.
> You do **not** want to paste AWS access keys into the cluster. OIDC is the mechanism that lets a pod prove
> its identity to AWS and borrow temporary permissions instead. This one command flips that capability on.
> (The full "how does that actually work" is the deep-dive at the bottom — skim it now, it'll pay off.)

```bash
eksctl utils associate-iam-oidc-provider \
  --region ap-south-1 \
  --cluster ecom-cluster \
  --approve
```
> Watch out: use the `--region` / `--cluster` / `--approve` **flags exactly as written**. The bare-word
> form (`... region ap-south-1 cluster ecom-cluster ...`) looks similar but fails.

### Step 3 — Add the worker nodes (the muscle)
> What's happening here: now you give the brain a crew. This creates a **managed node group** of 3 EC2
> instances that will actually run your containers.

```bash
eksctl create nodegroup \
  --cluster=ecom-cluster \
  --region=ap-south-1 \
  --name=node2 \
  --node-type=t3.medium \
  --nodes=3 --nodes-min=2 --nodes-max=4 \
  --node-volume-size=20 \
  --ssh-access --ssh-public-key=eks-jenkins-pipeline \
  --managed \
  --asg-access --external-dns-access --full-ecr-access --appmesh-access --alb-ingress-access
```
Reading the important parts:
- `--node-type=t3.medium --nodes=3` → three medium instances to start.
- `--nodes-min=2 --nodes-max=4` → allowed to shrink to 2 or grow to 4 (basic autoscaling room).
- `--full-ecr-access` → lets the nodes **pull your `ecom-repo` images** from ECR (without this, image
  pulls fail with "access denied").
- `--alb-ingress-access` / `--external-dns-access` → pre-grants the permissions the `2.2` add-ons want.
- `--ssh-public-key=eks-jenkins-pipeline` → the key pair must already exist in ap-south-1, or this fails.

### Step 4 — Point kubectl at the cluster and confirm it's alive
> What's happening here: `kubectl` is your remote control for the cluster. This command (re)writes its
> config to target `ecom-cluster`. Run it any time you switch machines or `kubectl` "forgets" the cluster.

```bash
aws eks update-kubeconfig --region ap-south-1 --name ecom-cluster
kubectl get nodes          # you should see your 3 workers, each "Ready"
kubectl get pods -A        # the cluster's own system pods (coredns, kube-proxy, aws-node) Running
```
Seeing three `Ready` nodes is the moment the cluster is genuinely usable.

> NEW CONCEPT — `kubectl get <thing>`: this is how you *ask the cluster what exists*. `get nodes` lists
> machines; `get pods` lists running containers; `-A` means "across all namespaces." You'll lean on
> `kubectl get` constantly to check your work.

## Gotchas (things that actually bite)
- **OIDC syntax** — flag form (`--region/--cluster/--approve`) only; the bare-word form fails silently-ish.
- **Missing key pair** — `eks-jenkins-pipeline` must exist in ap-south-1 before Step 3.
- **Old kubectl** — a `kubectl` much older than the cluster talks to it badly; install a current one (`1.4`).
- **Lost connection** — if `kubectl` ever says it can't reach the cluster, re-run the
  `aws eks update-kubeconfig` line from Step 4.

## Cost control (important — EKS is not free)
The control plane (~$0.10/hr) **plus** 3× t3.medium nodes run 24/7 — that adds up. When you stop for the
day:
```bash
# park the workers (brain stays, but you stop paying for the 3 instances)
eksctl scale nodegroup --cluster ecom-cluster --region ap-south-1 --name node2 --nodes 0
```
On a long break, tear the whole thing down and rebuild later from these same steps:
```bash
eksctl delete cluster --name ecom-cluster --region ap-south-1
```

## Verify
`kubectl get nodes` shows **Ready** nodes → the cluster's brain and muscle are both up.

Next → [`2.2-cluster-addons.md`](./2.2-cluster-addons.md) (give the cluster a front door, an address, and
the ability to add nodes), then [`2.3-namespaces-and-quotas.md`](./2.3-namespaces-and-quotas.md). After
that the cluster is ready for the datastores + microservices ([`3.1`](./3.1-datastores.md)).

## Concept deep-dive — OIDC & IRSA (IAM Roles for Service Accounts)

**The problem.** Pods (e.g. the AWS Load Balancer Controller, external-dns) need to call AWS APIs. How do
they get AWS credentials **without** hardcoding static keys, and **without** giving *every* pod the node's
permissions?

**The mechanism.** Each EKS cluster exposes an **OIDC provider** — an HTTPS endpoint serving OIDC discovery +
a **JWKS** (public keys). `eksctl utils associate-iam-oidc-provider` registers that endpoint as an **IAM OIDC
Identity Provider** in your account. Then **IRSA**:
1. Create an **IAM role** whose **trust policy** trusts that OIDC provider, scoped to a specific Kubernetes
   **ServiceAccount** (`system:serviceaccount:<ns>:<sa>`).
2. Annotate the pod's ServiceAccount with the role ARN.
3. EKS injects a **projected SA token** (a short-lived, signed **JWT**) into the pod, plus `AWS_ROLE_ARN` +
   `AWS_WEB_IDENTITY_TOKEN_FILE`.
4. The AWS SDK calls **`sts:AssumeRoleWithWebIdentity`** with that JWT. STS verifies the JWT signature against
   the cluster's **OIDC JWKS**, checks the role's trust policy (issuer + `sub` == the SA), and returns
   **temporary, scoped credentials**.

**Communication / flow.**
```
┌── pod (ServiceAccount annotated with role ARN) ──┐
│  reads projected SA token (JWT, ~1h, signed)     │
└───────────────┬──────────────────────────────────┘
                │ sts:AssumeRoleWithWebIdentity(JWT, roleArn)
                ▼
            AWS STS ──fetch JWKS──> cluster OIDC endpoint   (verify JWT signature)
                │  check role trust policy: iss == cluster OIDC, sub == system:serviceaccount:ns:sa
                ▼
        temporary credentials (15 min – 1 h)
                │
                ▼
   pod calls AWS (ECR, ELB, Route 53, ...) — least-privilege, no static keys, auto-rotated
```

**Why it fits.** Per-pod, **least-privilege** AWS access with **no long-lived secrets** and automatic
rotation. We associate the OIDC provider now so IRSA is ready when we add the ALB controller / external-dns.

**Why not the alternatives.**
- **Node instance role** (perms on the node group's role): simple, but **every pod on the node** inherits
  them — over-privileged, big blast radius. (We *do* use `--full-ecr-access` on nodes for *image pull*, which
  is low-risk; but app-level AWS access should be IRSA.)
- **Static AWS keys in a Secret:** long-lived, leak-prone, manual rotation — an anti-pattern.
- **EKS Pod Identity** (newer, 2023): same goal without per-cluster OIDC setup — an on-node agent + a Pod
  Identity Association. Simpler operationally; IRSA is older, more portable, still the most common.

> **Interview one-liner:** *"IRSA maps a Kubernetes ServiceAccount to an IAM role via the cluster's OIDC
> provider. The pod presents a signed SA-token JWT to STS `AssumeRoleWithWebIdentity`; STS verifies it against
> the cluster's JWKS and the role's trust policy and returns short-lived creds — least-privilege, no static keys."*
