# 5.3 — Traffic management (circuit breaking) and distributed tracing

## Goal
By the end of this part, your mesh will automatically **eject a misbehaving instance** of a service before
it can drag down a whole request chain (circuit breaking via a `DestinationRule`), and you'll be able to
*see* your live system: a topology map in **Kiali** with little lock icons proving mTLS is on, and a real
**checkout trace** in Jaeger/Tempo showing exactly how long each hop took (gateway → order → payment →
inventory). You'll have a DestinationRule applied to `payment`, Kiali and a tracing backend running, and the
ability to open both and read them.

## Why this part exists (read this first)
After `5.1` and `5.2` the mesh is secure (mTLS) and governs both directions (edge + internal). But two big
mesh payoffs are still switched off. First, **resilience**: right now if one `payment` pod goes sick —
slow, throwing errors, but not *dead* enough to fail its liveness probe — the mesh keeps sending it traffic,
and slow `payment` calls stall `order`, which stalls the whole checkout. Second, **visibility**: you still
can't *see* what's talking to what or where a slow checkout actually spends its time. You're flying with a
secure plane but no instruments.

This part installs the instruments and the safety system. `DestinationRule`s with **outlier detection** let
the mesh notice a bad instance and pull it out of rotation by itself. **Kiali + Jaeger/Tempo** give you the
live map and the per-request timeline. This is the part where the mesh stops being abstract and you actually
watch your checkout flow light up.

> NEW CONCEPT — what a `DestinationRule` is (and how it differs from a VirtualService).
> A **VirtualService** (from `5.2`) decides *where* a request goes — "send `/` to `api-gateway`." A
> **DestinationRule** decides *how* to talk to a service once the destination is chosen — connection
> limits, load-balancing strategy, and crucially **outlier detection** (circuit breaking). Think of the
> VirtualService as choosing which restaurant; the DestinationRule as the table-management rules once you're
> there (how many guests at once, and "if this waiter keeps dropping plates, stop seating them"). They pair
> up: route with one, tune the connection with the other.

## Prerequisites
- `5.1` + `5.2` complete: mesh installed, `shop` injected with sidecars, STRICT mTLS, edge on the Istio
  gateway.
- `istioctl` on your PATH (from `5.1`).
- Your app already forwards **W3C trace headers** (`traceparent`) between services — this is what makes a
  multi-hop trace stitch together; you'll lean on it in Step 4.

## Step 1 — Add a DestinationRule with outlier detection (circuit breaking) to `payment`

> Circuit breaking = the electrical-panel idea applied to network calls. A breaker "trips" to stop sending
> power down a faulty line so the fault doesn't burn down the house. In a mesh, the breaker trips on a
> failing **instance** and stops sending it requests so its failures don't cascade into the callers.

> Outlier detection = the specific mechanism Istio uses to trip that breaker. Each Envoy watches the
> responses coming back from each destination instance; when one instance returns too many errors in a row,
> Envoy **ejects** it — temporarily removes it from the pool of instances it'll route to — and tries it
> again later. The bad instance is quarantined; the healthy ones carry the load.

> What's happening here: you write a `DestinationRule` for `payment` that (a) caps how many connections pile
> onto it and (b) ejects any `payment` instance that throws 5 consecutive errors. `payment` is the riskiest
> hop in checkout (it talks to an external processor), so it's the right place to start.

Create the file:
```bash
nano payment-dr.yaml
```
Paste:
```yaml
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: payment
  namespace: shop
spec:
  host: payment                       # the Service this rule governs (payment.shop.svc.cluster.local)
  trafficPolicy:
    connectionPool:                    # bound how much load any one caller can pile on
      tcp:
        maxConnections: 100            # at most 100 concurrent TCP connections to payment
      http:
        http1MaxPendingRequests: 50    # at most 50 requests queued waiting for a connection
        maxRequestsPerConnection: 10   # recycle a connection after 10 requests (spreads load)
    outlierDetection:                  # the circuit breaker itself
      consecutive5xxErrors: 5          # 5 server errors in a row from an instance...
      interval: 10s                    # ...checked on this rolling interval...
      baseEjectionTime: 30s            # ...and that instance is ejected for 30s (longer if it keeps failing)
      maxEjectionPercent: 50           # never eject more than half the instances at once (keep some serving)
```
Apply it:
```bash
kubectl apply -f payment-dr.yaml
```
Read the important block back. `outlierDetection` is the breaker: "if a single `payment` pod returns 5
straight 5xx responses (checked every 10s), pull it out of rotation for 30 seconds, then try it again — but
never eject more than 50% of pods, so a bad deploy can't quarantine the entire service." The
`connectionPool` limits are the complementary half — they stop one greedy caller from opening unbounded
connections and exhausting `payment` in the first place. `maxEjectionPercent: 50` is the safety valve that
keeps the breaker from turning a partial outage into a total one.

> NEW CONCEPT — why ejecting an *instance* beats failing the whole call.
> Without this, a half-broken `payment` pod stays in the pool and roughly 1-in-N requests hit it, time out,
> and back up the checkout chain — intermittent, maddening, hard to diagnose. Outlier detection turns that
> into a clean, automatic decision: the *one* bad instance is removed, the request retries land on healthy
> instances, and the chain stays fast. It's resilience the app gets for free, decided locally by each Envoy
> from what it actually observes — no central health-checker, no app code.

## Step 2 — Install Kiali and a tracing backend

> Kiali = the mesh's dashboard/map. It reads Istio's config and metrics and draws a live graph of which
> service calls which, how much traffic flows, error rates, and whether each edge is mTLS-secured (a lock
> icon). It's "the picture of your mesh."

> Jaeger (or Tempo) = the trace store + trace viewer. Where Kiali shows the *graph*, Jaeger shows a single
> *request's journey* as a waterfall of timed spans — one bar per hop, so you can see which hop was slow.

> What's happening here: you install Kiali and a tracing backend plus the metrics/telemetry plumbing they
> rely on (Prometheus for metrics). Istio ships sample manifests for exactly this, which is the fastest way
> to stand them up for learning.

```bash
# from your istio-*/ release folder (the one with istioctl), the addon samples live here:
kubectl apply -f samples/addons/prometheus.yaml      # metrics — Kiali needs this
kubectl apply -f samples/addons/jaeger.yaml          # trace store + UI (use tempo.yaml instead for Tempo)
kubectl apply -f samples/addons/kiali.yaml           # the mesh dashboard

kubectl -n istio-system rollout status deploy/kiali  # wait for Kiali to come up
```
Read that back: you applied three add-ons into `istio-system` — Prometheus (metrics Kiali graphs from),
Jaeger (where traces are stored and viewed), and Kiali (the dashboard). The `rollout status` line just waits
for Kiali to be ready.

You also need to tell Istio to actually **sample traces** and send them to the backend. Enable tracing in
the mesh config (a quick way for a learning cluster is to set a high sampling rate so you don't miss your
own test requests):
```bash
istioctl install --set profile=default \
  --set meshConfig.enableTracing=true \
  --set meshConfig.defaultConfig.tracing.sampling=100 -y
```
Plain English: "Re-apply the install, but turn tracing on and sample 100% of requests." 100% is for
learning only — in production you'd sample 1% so tracing doesn't cost much. If Jaeger pods sit `Pending`,
it's scheduling room again — Karpenter (from `2.2`) should add a node shortly.

> NEW CONCEPT — distributed tracing and trace-header propagation.
> A single checkout touches five services. A **trace** ties all five hops into one record by giving the
> request a shared **trace ID** and one **span** per hop (a span = "this service spent this long on this
> request"). The catch: this only works if every service **forwards** the incoming trace headers onward.
> Istio's Envoys generate and propagate the **W3C `traceparent`** header automatically for the network hop —
> but the app must copy that header from the request it received onto the requests it makes. Your services
> already do this (it's why the prerequisite called it out). That's what lets Jaeger reassemble
> gateway → order → payment → inventory into one connected waterfall instead of four disconnected fragments.

## Step 3 — Open Kiali and read the live topology (with mTLS lock icons)

> What's happening here: you port-forward Kiali to your laptop and open it, generate some traffic so the
> graph has something to draw, and confirm the edges between services show the mTLS padlock — visual proof
> that `5.1`'s STRICT mTLS is actually in force.

```bash
istioctl dashboard kiali       # opens Kiali in your browser via an automatic port-forward
```
That command port-forwards the Kiali Service and opens it (typically `http://localhost:20001`). In another
terminal, drive some traffic so the graph populates:
```bash
for i in $(seq 1 200); do curl -s -o /dev/null http://shop.example.com/ ; done   # 200 requests through the edge
```
In Kiali: choose the **Graph** view, namespace **shop**, and you'll see nodes for your services with arrows
showing real traffic. Two things to look for:
- A **padlock icon** on the edges between services — that's Kiali telling you the connection is mTLS. If you
  see padlocks across `shop`, `5.1` worked.
- Edge colours/error rates — green is healthy; red flags a service returning errors.

If the graph is empty, you sent traffic *after* opening it (Kiali shows a time window) — bump the window to
"Last 5m" and regenerate traffic. If there are no padlocks, recheck the `PeerAuthentication` from `5.1`.

## Step 4 — View a real checkout trace in Jaeger/Tempo

> What's happening here: you make a real checkout request, then open Jaeger and find that exact request as a
> single trace — a waterfall of spans across gateway → api-gateway → order → payment → inventory — and read
> off which hop ate the time.

First, fire a checkout (use your app's real checkout call; this is illustrative):
```bash
curl -X POST http://shop.example.com/checkout \
     -H 'Content-Type: application/json' \
     -d '{"cartId":"demo-1","paymentMethod":"card"}'
```
Now open the trace UI:
```bash
istioctl dashboard jaeger        # port-forwards + opens Jaeger (use the Tempo/Grafana UI if you chose Tempo)
```
In Jaeger: pick **Service** = `istio-ingressgateway` (or `api-gateway`), click **Find Traces**, and open the
most recent one. You'll see a waterfall like:
```
   istio-ingressgateway  ├────────────────────────────────────────────────┤  142ms
     api-gateway           ├──────────────────────────────────────────────┤  138ms
       order                 ├────────────────────────────────────────────┤  120ms
         payment               ├──────────────────────────────────┤          78ms   ◄─ the slow hop
         inventory                                       ├──────────┤          18ms
```
Each bar is one hop; its length is how long that hop took; nesting shows who called whom. This is how you
turn "checkout feels slow" into "checkout is slow *because payment took 78ms*" in about ten seconds. Because
the trace **starts at `istio-ingressgateway`**, you're seeing the journey from the very edge — that's the
payoff of `5.2` routing the edge through the mesh.

If you find no traces: either no traffic matched the time window (widen it and re-fire the checkout), or
tracing/sampling didn't take — recheck the `enableTracing`/`sampling` settings from Step 2. If you see
*broken* traces (each hop a separate trace instead of one waterfall), a service isn't forwarding the
`traceparent` header — that's an app bug, not a mesh one.

## Concept deep-dive — circuit breaking and outlier detection (how the mesh ejects a bad instance)
The mesh's resilience superpower is that **each Envoy makes a local decision from what it actually sees** —
no central coordinator, no app changes. Here's the mechanism for the `payment` rule you wrote:

```
   order's Envoy  ──requests──►  payment pool: [ pod-A  pod-B  pod-C ]
        │                                              ▲
        │ watches responses per pod                    │ pod-B returns 5xx, 5xx, 5xx, 5xx, 5xx
        ▼                                              │
   "pod-B hit consecutive5xxErrors (5)"  ──eject──►  pod-B removed from pool for baseEjectionTime (30s)
        │                                              │
        └─ keeps routing to pod-A, pod-C  ◄────────────┘  (after 30s, probe pod-B again; if still bad, eject longer)
```

1. **Observe.** Every caller's Envoy already proxies the responses, so it counts errors *per destination
   instance* for free — no extra health check.
2. **Trip.** When an instance crosses your threshold (`consecutive5xxErrors: 5`, checked each `interval`),
   that Envoy **ejects** it — stops routing to it — for `baseEjectionTime`. Repeated offenders get ejected
   for multiples of that time (Envoy backs off harder on persistently-bad instances).
3. **Protect the whole.** `maxEjectionPercent: 50` guarantees the breaker can't eject so many instances that
   the service falls over — at worst half are quarantined, half keep serving.
4. **Recover.** After the ejection window, the instance is allowed back; if it's healthy now, it rejoins; if
   not, out it goes again.

Why this over a plain liveness probe? A liveness probe only catches a pod that's *fully* dead — it restarts
it. Outlier detection catches the nastier "alive but failing" instance (a bad dependency, a slow disk, a
poisoned cache) and routes around it **per-caller and instantly**, without waiting for a probe to fail or a
human to notice. The `connectionPool` limits are the front half of the same idea: cap the load *before* a
service is overwhelmed; eject instances *after* they start failing.

*Interview line: "A DestinationRule's outlier detection makes each Envoy eject an instance that returns too
many consecutive errors and route around it for a back-off window — capped by maxEjectionPercent so the
breaker can't cascade — giving automatic, per-caller circuit breaking that catches 'alive but failing'
instances a liveness probe never would."*
