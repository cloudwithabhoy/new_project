# 9.2 — Deploy the whole stack into London (re-apply the same manifests)

## Goal
Bring the **entire application** up in the London cluster from `9.1` — the datastores, all the
microservices, and Istio — by re-applying the **same manifests** you proved in Mumbai, changing only the
handful of per-region values (image registry host, DB hosts, region label). At the end, a checkout completes
**entirely inside London**, with no hop back to Mumbai.

## Why this part exists (read this first)
`9.1` gave you an empty London foundation — a cluster with add-ons and namespaces, but nothing running.
This part fills it. The key idea, and the reason multi-region is even tractable, is that you are **not**
writing anything new: every StatefulSet, Deployment, Service, Ingress, and Istio object already exists in
Git from Phases 03–05. London is "re-apply the same files in a different cluster." The *only* things that
differ between the two regions are a few values — and managing exactly those values, without letting the two
regions drift apart, is the whole skill this part teaches.

> NEW CONCEPT — kubectl contexts: how you hold two clusters at once and switch safely.
> Your kubeconfig now lists **two** clusters (Mumbai and London — `9.1` added the second). Each cluster you
> can talk to is wrapped in a named **context** (cluster + user + default namespace). `kubectl` always acts
> on **one** context — "the current context" — and every `kubectl` command silently targets whatever that
> is. This is the single most dangerous thing in multi-region ops: run the right command against the wrong
> context and you've just redeployed London's app on top of Mumbai. You list contexts with
> `kubectl config get-contexts`, see the current one with `kubectl config current-context`, and switch with
> `kubectl config use-context <name>`. Treat "which context am I on?" like a pilot's pre-flight checklist —
> check it before every apply.

> NEW CONCEPT — config-per-environment: same manifests, different values.
> The professional pattern is **one set of manifests, many sets of values**. The manifest says *what the
> system is* (a catalog Deployment with 2 replicas, a readiness probe, an Ingress); a small per-region
> **values** layer says *where it is* (which ECR host the image comes from, which region label to stamp on
> pods). You never fork the manifests per region — that guarantees they drift. You keep them identical and
> inject the differences. Phases 03–05 were already written this way; here you just supply London's values.

## Prerequisites
- [`9.1`](./9.1-provision-second-region.md) done — `ecom-cluster-uk` exists with add-ons + `shop`/`data`
  namespaces + quotas, all empty.
- The Mumbai manifests (Phases 03–05) are in Git — datastores (`3.x`), the service fleet (`4.x`), Istio
  (`5.x`). You'll re-apply these.
- The service **images exist in London's ECR** (`...eu-west-2.amazonaws.com/ecom-repo:...`). If Jenkins only
  pushed to Mumbai's ECR, replicate the repo to London first (`aws ecr create-repository` in eu-west-2 +
  push, or enable ECR cross-region replication). London's nodes can only pull from London's ECR.

> Reminder of scope: this deploys a **running** stack. The London Postgres comes up **empty** — it does not
> have Mumbai's products/orders. Cross-region **data replication** is Phases 10 (databases) and 12 (Kafka).
> So a London checkout in this part operates on London's own (initially empty) data. That's expected and
> correct for now; we're proving **routing to a live local stack**, not data sharing.

## Before you start — set London's per-region values
> What's happening here: the same variable block from `9.1`, plus the one app-level value that differs per
> region — the **region label** you'll stamp on pods so `9.3` can prove which region served a request.

```bash
export REGION=eu-west-2
export CLUSTER=ecom-cluster-uk
export ACCOUNT=169424082295
export ECR=$ACCOUNT.dkr.ecr.$REGION.amazonaws.com   # London's image registry host
export REGION_LABEL=uk                              # stamped on pods; Mumbai uses 'in'
```
The **three** real per-region differences for the app layer, and nothing else:
- **Image registry host** → `$ECR` (`...eu-west-2...`), so pulls hit London's ECR.
- **DB hosts** → unchanged *strings* (`postgres-catalog.data.svc.cluster.local`) but they now resolve to
  **London's** in-cluster Postgres. Same name, different cluster — that's the magic of in-cluster DNS: the
  manifest doesn't change, it just resolves locally.
- **Region label** → `$REGION_LABEL=uk`, a pod label/env that lets you and the global router tell regions
  apart.

## Step 1 — Switch kubectl to the London context (and confirm, twice)
> What's happening here: before you apply a single thing, you make **absolutely sure** kubectl is pointed at
> London. This is the pre-flight check that prevents the worst multi-region accident.

```bash
kubectl config get-contexts          # list every cluster you can reach; note the exact UK context name
```
The London context name eksctl wrote is long, typically like
`<you>@ecom-cluster-uk.eu-west-2.eksctl.io`. Switch to it:
```bash
kubectl config use-context <your-ecom-cluster-uk-context-name>
kubectl config current-context       # MUST read the UK context — read it out loud
kubectl get nodes                    # MUST show London (eu-west-2) nodes, Ready
```
> If `current-context` ever shows Mumbai (`ecom-cluster`), **stop** — do not apply anything until you've
> switched. A friendlier alternative to remembering the long name is the `kubectx` tool (`kubectx
> ecom-cluster-uk`), or rename the context once: `kubectl config rename-context <long-name> uk` and then just
> `kubectl config use-context uk`. Worth doing — you'll switch a lot.

## Step 2 — Deploy the datastores into London (re-apply the `3.x` recipe)
> What's happening here: stand up London's data layer with the **same** StatefulSet + headless-Service +
> Secret files from [`3.1-datastores.md`](./3.1-datastores.md). These manifests have no region-specific
> content, so they apply unchanged — but first London needs the EBS CSI driver + `gp3` StorageClass, because
> that's per-cluster.

```bash
# per-cluster storage plumbing (3.1 Step 1), now for London
eksctl create addon --name aws-ebs-csi-driver --cluster "$CLUSTER" --region "$REGION" --force
kubectl apply -f - <<'EOF'
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata: { name: gp3 }
provisioner: ebs.csi.aws.com
parameters: { type: gp3 }
volumeBindingMode: WaitForFirstConsumer
EOF
```
Then the database Secrets (per-namespace, so re-create them in London's `data`) and the StatefulSets:
```bash
# pick London's own strong DB passwords; they need not match Mumbai (separate databases)
kubectl -n data create secret generic postgres-catalog --from-literal=POSTGRES_PASSWORD='<uk-strong-pw>'
# ...repeat the secret for each DB...

# the SAME StatefulSet + headless-Service manifests from 3.1 — region-agnostic, apply as-is
kubectl apply -f postgres-catalog.yaml
# ...and the rest of the datastores (postgres-*, redis, elasticsearch, kafka) from 3.1 Step 5...

kubectl -n data get pods,pvc          # each postgres-*-0 Running, each PVC Bound (in London now)
```
> The `volumeBindingMode: WaitForFirstConsumer` you set means each London PVC's EBS disk is created in a
> **London AZ** — exactly the AZ-correctness lesson from `3.1`, now playing out in eu-west-2. London's
> databases are **empty**; that's expected (data replication is Phase 10).

## Step 3 — Deploy the service fleet into London (re-apply the `4.x` recipe), with London values
> What's happening here: bring up all the microservices using the **same** Deployment/Service/Ingress
> manifests from the fleet recipe (`4.x`, which generalises the `catalog` recipe from
> [`3.2-deploy-catalog.md`](./3.2-deploy-catalog.md)). The only edits are the per-region values: the **image
> host** and the **region label**.

The single change inside each service's manifest is the image registry host — everything to the right of it
(`/ecom-repo:catalog-<sha>`) is identical:
```yaml
# Mumbai:  169424082295.dkr.ecr.ap-south-1.amazonaws.com/ecom-repo:catalog-<sha>
# London:  169424082295.dkr.ecr.eu-west-2.amazonaws.com/ecom-repo:catalog-<sha>
        image: 169424082295.dkr.ecr.eu-west-2.amazonaws.com/ecom-repo:catalog-<sha>
```
And stamp the region label so `9.3` can prove which region answered. Add it to the pod template (and have
the app echo it back in a response header — most of these services read a `REGION` env):
```yaml
    metadata:
      labels:
        app: catalog
        region: uk            # $REGION_LABEL — the per-region marker
    spec:
      containers:
      - name: catalog
        env:
        - { name: REGION, value: uk }   # app returns this in an `X-Region` header for verification
```
> The clean way to do this for real is a tiny overlay (Kustomize) or Helm values file that sets the registry
> host and `region` label for *all* services at once, instead of editing 13 manifests by hand. Use whichever
> Phases 03–05 already standardised on — the discipline is the same: **change values, never fork manifests.**

Apply the fleet and watch it roll out (context is London — you confirmed in Step 1):
```bash
kubectl apply -f <fleet-manifests-or-overlay>
kubectl -n shop get pods              # all services READY 1/1 (readiness passes once they reach London DBs)
```
> A pod stuck `0/1` here is almost always one of the two per-region values: an image that won't pull (wrong
> ECR host / image not replicated to London — `kubectl -n shop describe pod ...` shows `ErrImagePull`), or a
> service whose readiness can't reach its London DB (check Step 2 came up). The DB *host strings* are
> unchanged from Mumbai; they just resolve to London's Postgres now.

## Step 4 — Deploy Istio into London (re-apply the `5.x` recipe)
> What's happening here: install Istio and apply the **same** mesh config (Gateway, VirtualServices,
> DestinationRules, mTLS) from the `5.x` recipe — but **into London's cluster only**. This is the decision
> made back in Phase 09's plan: Istio stays **inside** each region. London gets its **own** complete,
> independent mesh; it is not joined to Mumbai's.

```bash
# install Istio into the London cluster (per-cluster control plane), e.g. with istioctl or the Helm charts 5.x used
istioctl install -y            # or the exact 5.x install method
kubectl label namespace shop istio-injection=enabled   # same as 5.x, now in London

# re-apply the SAME mesh manifests from 5.x (Gateway / VirtualService / DestinationRule / PeerAuthentication)
kubectl apply -f <istio-manifests-from-5.x>
```
> Why a separate mesh per region and not one stretched mesh: a stretched Istio mesh would carry mesh
> control-plane and sidecar traffic **across the Atlantic** on the hot path — re-introducing the very
> cross-region latency and shared failure domain you went multi-region to escape. Each region's mesh secures
> and routes traffic **locally**; the **global** layer above (Route 53 / Global Accelerator in `9.3`) is what
> ties the two regions together. The Istio deep-dive in `9.3` revisits this.

This install also gives London its **own** Istio ingress Gateway, which the ALB Controller fronts with a
**London regional ALB** — that London ALB is one of the two backends `9.3` registers in the global router.

## Step 5 — Prove a checkout works UK-locally
> What's happening here: drive a real checkout against London's public entrypoint and confirm (a) it
> succeeds and (b) it was served by **London**, by reading the region label/header back.

```bash
# London's public hostname (its regional ALB fronting the Istio gateway)
UK_ALB=$(kubectl -n shop get ingress <gateway-ingress> \
  -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')

# run a checkout flow against London's entrypoint
curl -i http://$UK_ALB/api/checkout -X POST -H 'Content-Type: application/json' \
  -d '{"items":[{"sku":"mug","qty":1}]}'
```
Look for two things in the response:
- **HTTP 200** (or your checkout's success shape) — the full chain works in London: gateway → service mesh →
  service → London database.
- An **`X-Region: uk`** header (or a `region=uk` field), proving **London** served it, not Mumbai.

```bash
# extra proof it was London's pods:
kubectl -n shop get pods -l region=uk          # the pods that handled it are labelled region=uk
```
> If the checkout 500s but pods are healthy, it's usually a missing per-region Secret/ConfigMap value in
> London (you created Mumbai's by hand in `3.2`; they don't cross regions or clusters — re-create them in
> London's `shop`). If it 200s but data "isn't there" vs Mumbai — correct, London's DB is its own empty
> island until Phase 10.

## Verify
- `kubectl config current-context` is London for everything you did in this part.
- `kubectl -n data get pods` and `kubectl -n shop get pods` → all `Running` / `READY 1/1` in London.
- A `curl` checkout against London's ALB returns success **and** an `X-Region: uk` marker — the whole stack
  runs and serves **entirely within London**.
- You now have **two identical, independent stacks**, each fronted by its **own regional ALB**. Two ALBs,
  two regions — and (next part) one global router above them.

## Concept deep-dive — keeping regions identical with shared manifests + per-region values (drift is the enemy)
You have two clusters that must behave the **same**. The only sustainable way to guarantee that is: **one**
source of manifests, applied to both, with a thin per-region values layer for the genuine differences.

**How it works.** The manifests in Git are the single source of truth — they describe the system
structurally and contain **no** region literals. A small overlay (Kustomize bases+overlays, or Helm
values-per-region) injects the few real differences: the ECR host, the `region` label/env, and any
region-scoped secret values. Deploying a region is: `use-context <region>` → apply the shared base with that
region's overlay. The list of things that differ — registry host, region label, the DB *resolution* (same
string, local cluster) — is short **on purpose**; if that list grows, that's a smell that real structural
divergence is creeping in.

**Why it fits.** Identical manifests mean the regions can't silently diverge: a fix or feature lands in Git
once and both regions get it on the next apply. When `9.3` shifts traffic between regions on failover, you
need the regions to be true twins — a user failed over from London to Mumbai must hit the *same* behaviour.
Shared manifests are what make that promise real.

**Why not the alternatives.** **Copy-paste-and-edit per region** (a `london/` folder forked from `mumbai/`)
feels easy on day one and is a disaster by day thirty: the two copies drift — a bug fixed in one, a flag
added to the other — until "failover to the other region" means failover to *subtly different software*,
which is exactly when you can least afford surprises. **Drift** is the enemy: every region-specific literal
you hand-edit is a future inconsistency. Push every difference into the values layer and keep the manifests
one.

*Interview line: "Both regions deploy from one set of manifests with a per-region values overlay — registry
host, region label, secrets. Identical structure, injected differences. That kills configuration drift, so
when the global router fails traffic from one region to the other, users land on genuinely identical software."*
