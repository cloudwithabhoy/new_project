# 8.2 — Game-day (run the drill, hold the SLO, write the postmortem)

## Goal
Run one full, realistic failure drill from start to finish: pick a scenario, write down the hypothesis and
the exact SLO you're watching, inject the failure, then **watch your autoscaling, PDBs, and outlier
detection hold the SLO live on Grafana** while you follow a runbook — and finish by writing a blameless
postmortem. Passing this drill is the **exit gate** that unlocks Phase 09.

## Why this part exists (read this first)
In `8.1` you tested nets one at a time: kill a pod, add latency, starve CPU. That proves each net works *in
isolation*. But a real incident isn't one clean fault — it's a scenario: traffic spikes *while* a dependency
gets slow *while* a node disappears, and your HPA, PDB, retries, and outlier detection all have to
cooperate, in order, under one clock, against one SLO. A game-day exercises **the whole system as a system**,
the way a real outage would.

This is the last thing standing between you and Phase 09. Phase 09 replicates this region — and you do not
replicate something you haven't proven holds under realistic failure. So a game-day is not a nice-to-have;
it is the **gate**. Pass it and you have *evidence* (a postmortem with a green SLO line) that the single
region is genuinely resilient. Fail it and you've found the work to do *before* you multiply the problem
across regions.

> NEW CONCEPT — game-day vs ad-hoc chaos
> They look similar (both inject failures) but they answer different questions:
> - **Ad-hoc chaos** (`8.1`) = a single component test. "Does outlier detection eject a bad endpoint?"
>   Narrow, fast, run dozens of them, no audience.
> - **A game-day** = a rehearsed, scheduled drill of a *realistic scenario* with humans following a runbook,
>   measured against a *declared SLO*, ending in a *written postmortem*. It tests not just the system but the
>   **runbook and the responders** too. Think: a single fire-alarm test (ad-hoc) versus a full building
>   evacuation drill with the fire marshal timing it (game-day).
> We use game-days because the integration — features cooperating under one realistic scenario — is exactly
> what unit-level chaos can't show you, and it's exactly what a real region outage will demand.

## Before you start — set the stage
A game-day is a *scheduled event*, not a surprise. Before you inject anything:

```bash
kubectl config current-context           # ecom-cluster / ap-south-1
kubectl -n shop get pods,hpa,pdb         # services up; HPAs present; PDBs present
kubectl get nodes                        # all Ready
```
- Announce the window (even to yourself, write the start time down — the postmortem needs a timeline).
- Open the **checkout SLO dashboard** in Grafana. This is your single source of truth for "did it hold?"
- Decide your **abort condition up front** and keep the abort command in your clipboard.
- Have the `8.1` cleanup commands ready (`kubectl -n shop delete podchaos/networkchaos/...`).

Constants you'll reference: account `169424082295`, region `ap-south-1`, namespaces `shop`/`data`, the
`payment` `FAIL_MODE` toggle, and the resilience features being validated — HPA/KEDA, PodDisruptionBudgets,
Istio outlier detection + retries.

---

## Step 1 — Pick the scenario and write the hypothesis + SLO

> What's happening here: before touching the cluster you commit, in writing, to *what* you're testing, *what
> success looks like*, and *when you'll stop*. A game-day with no written hypothesis is just breaking things.

Pick one realistic scenario. A good first game-day:

> **Scenario:** "It's a flash sale. Checkout traffic triples *and* the `payment` service degrades — one
> replica starts returning 5xx (FAIL_MODE), and the network to `payment` gets slow (200 ms latency)."

Write the card. Put it in a file so it lands in the postmortem verbatim:
```bash
nano gameday-card.md
```
```text
GAME-DAY CARD
  Date/owner:   2026-06-19 / <you>
  Scenario:     flash sale — 3x checkout load + payment 5xx (FAIL_MODE) + 200ms payment latency
  Steady state: checkout success rate >= 99.5% AND checkout p99 < 300ms
  SLO watched:  checkout availability SLO (error budget burn rate must stay < 1x)
  Hypothesis:   HPA/KEDA scales checkout+payment to absorb 3x load; outlier detection ejects the
                failing payment endpoint; retries cover in-flight 5xx; the PDB keeps enough replicas
                during any node churn — so the checkout SLO HOLDS for the full 10-minute drill.
  Blast radius: shop namespace only, 10 minutes, off-peak.
  Abort if:     checkout success rate < 98% for 60s  (burn rate > 5x)
  Abort cmd:    kubectl -n shop delete networkchaos --all && kubectl -n shop set env deploy/payment FAIL_MODE=false
```
Read it back: every word is a commitment. The **steady state** is what "healthy" means numerically. The
**SLO watched** is the one line on Grafana you stare at. The **hypothesis** names *which* features must
cooperate and predicts the outcome. The **abort** is non-negotiable and pre-decided so you don't improvise
under stress.

---

## Step 2 — Establish the steady state (the "before" picture)

> What's happening here: you confirm the system is healthy *first*, so that when you inject the fault you can
> attribute any change to the fault and not to some pre-existing problem. No baseline = no experiment.

Drive a little baseline load and look at the dashboard for 2–3 minutes with **nothing broken**:
```bash
# generate steady baseline checkout traffic (use your load tool of choice; example with a simple loop)
ALB=$(kubectl -n shop get ingress checkout -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
while true; do curl -s -o /dev/null http://$ALB/checkout -X POST -d '{"items":[...]}'; sleep 0.2; done
```
On Grafana, confirm: checkout success rate sits at ~100%, p99 is comfortably under 300 ms, error budget
burn is flat. **Screenshot this.** The postmortem needs the "before" to make the "during" meaningful. If the
baseline is already unhealthy, stop — fix that first; you can't run a clean drill on a sick system.

---

## Step 3 — Inject the failure (start the drill, start the clock)

> What's happening here: you apply the scenario's faults and **note the wall-clock time of every action** —
> that timeline is the spine of the postmortem. Inject in the order a real incident would unfold: load
> first, then the degradation.

Note the time, then ramp load to 3x (add more concurrent loops, or bump your load tool's RPS). Then apply
the `payment` degradation — reuse the YAML shapes from `8.1`:
```bash
# t+0:00  ramp checkout load to 3x  (your load generator)
# t+1:00  payment starts failing
kubectl -n shop set env deploy/payment FAIL_MODE=true

# t+1:00  payment network goes slow
kubectl apply -f net-latency.yaml          # the 200ms NetworkChaos from 8.1
```
Write each line's real timestamp down as you run it (e.g. "10:14:30 — FAIL_MODE on"). Read it back: you've
now created the exact scenario from your card — tripled load, a failing payment endpoint, and slow payment
network — all scoped to `shop`, all reversible.

---

## Step 4 — Watch the nets hold the SLO (the whole point)

> What's happening here: this is the payoff. You watch — live, on Grafana — each resilience feature engage
> in sequence and keep the SLO line above its threshold. You are *observing the hypothesis*, not touching
> anything (unless the abort condition fires).

Watch these, roughly in the order they should fire:
```bash
kubectl -n shop get hpa -w                 # HPA: REPLICAS for checkout & payment climb under load
kubectl -n shop get pods -l app=payment -w # failing/over-loaded pods cycle; new ones come up
kubectl -n shop get pdb                    # ALLOWED DISRUPTIONS stays >=0; min availability protected
```
On the dashboard, you should see the sequence:
```
   3x load ─► HPA adds replicas ─► capacity restored, p99 settles back under SLO
   payment 5xx ─► outlier detection ejects the bad endpoint ─► caller error rate drops
   in-flight 5xx ─► retries succeed on a healthy endpoint ─► user never sees the error
   any node churn ─► PDB blocks evicting too many replicas ─► capacity never dips below min
```
The SLO line stays above its threshold; the **error-budget burn rate stays under 1x**. That green line, held
for the full 10 minutes, *is* the pass.

If the burn rate crosses your abort threshold (success < 98% for 60s), **abort immediately** — don't be a
hero:
```bash
kubectl -n shop delete networkchaos --all && kubectl -n shop set env deploy/payment FAIL_MODE=false
```
Aborting is not failing the engineer — it's the experiment doing its job. You found a weakness; that's the
prize. Note the abort time for the timeline.

---

## Step 5 — Follow the runbook

> What's happening here: a game-day also tests the *runbook* — the written "if this breaks, do that" steps —
> and the responder using it. Even if the nets hold automatically, walk the runbook as if they hadn't, to
> prove it's correct and current.

Open your service runbook (the one a 3-a.m. on-caller would follow) and verify each step actually works
against the live, degraded system:
- Does the "how do I see payment's error rate?" link point at the right Grafana panel?
- Does "how do I check if outlier detection ejected an endpoint?" give a command that returns the truth?
- Does "how do I manually scale checkout if HPA is stuck?" command actually work?
```bash
# example runbook step being validated live:
kubectl -n shop get hpa checkout -o wide        # is HPA actually scaling, or stuck at max?
kubectl -n shop scale deploy/checkout --replicas=8   # the documented manual override, if needed
```
Every stale link or wrong command you find here is an **action item** for the postmortem. A runbook that's
never been walked during a real failure is fiction.

---

## Step 6 — End the drill and restore steady state

> What's happening here: you remove every injected fault, return load to baseline, and confirm on Grafana
> that the system fully recovers to the "before" picture. A drill isn't over until the system is provably
> healthy again.

```bash
kubectl -n shop delete networkchaos --all
kubectl -n shop set env deploy/payment FAIL_MODE=false
kubectl -n shop rollout status deploy/payment
# stop your load generator (Ctrl-C the loop / stop the load tool)
```
Watch Grafana return to baseline: success rate back to ~100%, p99 back under 300 ms, HPA scaling **back
down** as load drops, ejected endpoints rejoining the pool. **Screenshot the recovery.** Confirm no chaos
objects linger:
```bash
kubectl -n shop get networkchaos,podchaos,stresschaos,timechaos    # should be empty
```

---

## Step 7 — Write the postmortem

> What's happening here: you turn the drill into durable knowledge — a written record of what held, what
> didn't, and what you'll fix. This document is the artifact that *proves* the game-day happened and the
> region is resilient. It's also the thing you hand to Phase 09 as the green light.

> NEW CONCEPT — blameless postmortem & action items
> A **blameless** postmortem writes the story in terms of *systems and signals*, never *who screwed up*.
> "The runbook's scaling command was stale" — not "Priya ran the wrong command." Why blameless: people hide
> mistakes when blamed, and hidden mistakes can't be fixed; people surface mistakes freely when the system
> is on trial instead of them. Each finding becomes an **action item**: a specific, owned, dated task ("tune
> outlier detection to eject after 3 consecutive 5xx — owner: you — by 2026-06-26"). A postmortem with no
> action items is just a diary; the action items are what make the *next* game-day pass.

Fill in this template:
```bash
nano postmortem-gameday-01.md
```
```text
POSTMORTEM — Game-day 01: flash-sale + payment degradation
  Date / owner:        2026-06-19 / <you>
  Scenario & hypothesis: <paste the game-day card from Step 1, verbatim>
  SLO outcome:         HELD / BREACHED   (attach before / during / after Grafana screenshots)
                       lowest success rate seen: __%   peak p99: __ms   peak burn rate: __x

  TIMELINE (wall-clock, from your notes)
    10:12  baseline confirmed healthy (screenshot)
    10:14  load ramped to 3x
    10:15  FAIL_MODE=true + 200ms latency applied
    10:15  HPA began scaling checkout 3 -> 6
    10:16  outlier detection ejected 1 payment endpoint; caller error rate fell back
    10:24  faults removed; system recovered to baseline by 10:26

  WHAT HELD (evidence)
    - HPA scaled checkout & payment under load; p99 returned under SLO.        [graph]
    - Outlier detection ejected the failing payment endpoint; retries covered it. [graph]
    - PDB kept replicas above min during pod churn.                            [kubectl output]

  WHAT DIDN'T (be specific, be blameless)
    - e.g. retries amplified the 200ms latency for ~20s before settling.
    - e.g. runbook's manual-scale command referenced an old deployment name.

  ACTION ITEMS (specific · owned · dated)
    [ ] Tune outlier detection: eject after 3 consecutive 5xx (was 5).  owner:__  by:__
    [ ] Fix runbook manual-scale command + Grafana link.                owner:__  by:__
    [ ] Add retry budget cap so retries can't amplify latency.          owner:__  by:__

  GATE DECISION
    PASS  -> region proven resilient; Phase 09 (replicate region) may begin.
    FAIL  -> complete action items, then re-run this game-day before Phase 09.
```
Read it back: the **timeline** is your evidence the drill happened; **what held** is the proof of
resilience; **what didn't** plus **action items** is the work; the **gate decision** is the explicit
hand-off to Phase 09.

---

## Verify (the game-day is done — and the gate is decided — when…)
- You ran a *realistic, multi-fault* scenario against a *declared SLO*, watched live on Grafana.
- The error-budget burn rate stayed under your abort threshold the whole window (or you aborted cleanly and
  recorded why).
- You walked the runbook against the live degraded system and logged every stale step as an action item.
- The system fully recovered to baseline and no chaos objects linger.
- A **blameless postmortem** exists with before/during/after screenshots, a timeline, what-held /
  what-didn't, dated action items, and an explicit **PASS/FAIL gate decision**.
- If PASS: Phase 09 is unlocked. If FAIL: action items are scheduled and a re-run is booked.
