# 2.3 — Namespaces, ResourceQuota & LimitRange

## Goal
Carve your one cluster into two labelled areas — **`shop`** (for the microservices) and **`data`** (for the
databases) — and put guardrails around each so no single workload can eat the whole cluster.

## Why this part exists (read this first)
Your cluster is one big shared space. If you just dump all 13 services plus 7 databases into it with no
organisation, two bad things happen: (1) it becomes impossible to tell apart — `kubectl get pods` shows a
wall of 50 pods; and (2) one buggy service that grabs too much memory can starve everything else. This
part fixes both, *before* you deploy anything, so the habit is built in from day one.

> NEW CONCEPT — what is a namespace?
> A **namespace** is a folder inside your cluster. Pods, Services, Secrets — almost everything — live inside
> a namespace. It's not a security wall by itself; it's an *organising* boundary that lets you (a) group
> related things, (b) run the same name twice (a `postgres` in `data` and a different `postgres` elsewhere
> don't clash), and (c) apply rules — quotas, network policies, access control — to a whole group at once.
> Analogy: the cluster is an office building; namespaces are the floors. The "engineering" floor and the
> "data" floor can have different rules and you don't trip over each other.

We make two floors:
- **`shop`** — the stateless microservices (api-gateway, catalog, order, …).
- **`data`** — the stateful databases (Postgres, Redis, …) that need stricter, beefier rules.

## Prerequisites
- [`2.2`](./2.2-cluster-addons.md) done — the cluster is fully wired and nodes are `Ready`.

## Steps

### Step 1 — Create the two namespaces (build the two floors)
> What's happening here: you're just making the two folders and tagging each with a label so you can tell
> at a glance which is which.

```bash
kubectl create namespace shop
kubectl create namespace data
kubectl label namespace shop  tier=app
kubectl label namespace data  tier=data
```
Check they exist:
```bash
kubectl get ns          # you should see shop and data in the list
```

> NEW CONCEPT — `-n` / changing namespace. From now on, almost every command needs to know *which floor*
> you mean. You add `-n shop` (or `-n data`) to target one: `kubectl get pods -n shop`. Without `-n`,
> kubectl uses the `default` namespace, which we don't use — so get into the habit of always passing `-n`.

### Step 2 — Cap each floor's total budget (ResourceQuota)
> What is a ResourceQuota, with an analogy? Give each floor a department budget. The `shop` floor is
> allowed to request *at most* 4 CPUs and 8Gi of memory across **all** its pods combined. Once the floor's
> pods add up to that, the next pod is refused until something frees up. It stops one runaway namespace
> from consuming the entire cluster.

Create a file `quotas.yaml`:
```bash
nano quotas.yaml
```
Paste this in:
```yaml
apiVersion: v1
kind: ResourceQuota
metadata: { name: shop-quota, namespace: shop }
spec:
  hard:
    requests.cpu: "4"          # all shop pods together may REQUEST at most 4 vCPU
    requests.memory: 8Gi
    limits.cpu: "8"            # …and be capped (LIMIT) at 8 vCPU total
    limits.memory: 16Gi
    pods: "60"                 # at most 60 pods on this floor
---
apiVersion: v1
kind: ResourceQuota
metadata: { name: data-quota, namespace: data }
spec:
  hard:
    requests.cpu: "4"
    requests.memory: 12Gi      # databases get more memory headroom
    limits.cpu: "8"
    limits.memory: 24Gi
    persistentvolumeclaims: "20"   # cap how many disks the data floor can claim
```

### Step 3 — Give every pod sane defaults & a ceiling (LimitRange)
> What is a LimitRange, with an analogy? The quota is the *department* budget; the LimitRange is the *rule
> per employee*. It says "if a pod doesn't state how much it needs, give it this sensible default, and
> never let a single container exceed this maximum." This matters because — surprise — once a quota exists,
> Kubernetes **refuses any pod that doesn't declare its CPU/memory**. The LimitRange quietly fills in those
> numbers for you so your manifests don't all break.

Create `limits.yaml`:
```bash
nano limits.yaml
```
Paste:
```yaml
apiVersion: v1
kind: LimitRange
metadata: { name: shop-limits, namespace: shop }
spec:
  limits:
  - type: Container
    default:        { cpu: 250m, memory: 256Mi }   # used if a container sets no limit
    defaultRequest: { cpu: 50m,  memory: 64Mi }    # used if it sets no request
    max:            { cpu: "2",  memory: 2Gi }     # no single container may exceed this
```
> Make a matching one for `data` with bigger numbers (databases need more memory). Same shape, change
> `namespace: data` and raise `default`/`max`.

### Step 4 — Apply both files (turn YAML into live rules)
```bash
kubectl apply -f quotas.yaml -f limits.yaml
```
> Reminder of what `kubectl apply -f` means: "read these YAML files and make the cluster match them." The
> rules are live the instant this returns.

## Verify
```bash
kubectl get ns shop data
kubectl -n shop describe resourcequota shop-quota     # shows Used vs Hard — proof it's counting
kubectl -n shop describe limitrange   shop-limits
```
The real proof comes later: when you deploy a pod **without** resource requests, the LimitRange fills them
in and the quota counts them. If you ever see a pod rejected with "must specify requests", that's the quota
working as designed — add requests (or rely on the LimitRange default).

## Concept deep-dive — ResourceQuota vs LimitRange (the budget vs the per-person rule)
These two are constantly confused; pin the difference once:

- **ResourceQuota = the namespace-wide budget.** "All pods in `shop` together may request at most 4 CPU /
  8Gi." Enforced at admission — the *sum* across the namespace can't exceed `hard`. Important side effect:
  the moment a quota sets `requests.cpu`, **every new pod must declare a request** or it's rejected.
- **LimitRange = the per-container rule.** It *injects* `defaultRequest`/`default` into any container that
  forgot to set them, and *rejects* any container that exceeds `max`. So it both satisfies the quota's
  "you must declare requests" rule (via defaults) and stops one container being pathologically huge.

They're a team: LimitRange makes sure every pod has *sane* numbers; ResourceQuota makes sure the *total*
stays inside budget. *Interview line: "Quota caps the namespace total and forces requests to be set;
LimitRange supplies the per-container defaults and ceilings that make that workable — together they're
guardrails so one workload can't starve the cluster."*
