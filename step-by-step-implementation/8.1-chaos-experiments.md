# 8.1 — Chaos experiments (Chaos Mesh · Istio fault injection · FAIL_MODE)

## Goal
You're going to break things on purpose — kill pods, add network latency, starve CPU, skew the clock,
and inject HTTP delays/errors at the mesh — and **watch your own safety nets catch them**. Everything you
built in Phases 05/06/07 (HPA/KEDA autoscaling, PodDisruptionBudgets, Istio outlier detection, the
Prometheus/Grafana dashboards) was built on a promise: "this will hold under failure." This part makes you
collect on that promise, one controlled experiment at a time.

## Why this part exists (read this first)
Up to now every resilience feature was tested by *hoping*. You set `minReplicas`, a PDB of
`maxUnavailable: 1`, outlier detection that ejects a bad endpoint after 5 consecutive 5xx — and then you
moved on, assuming they work. **Assuming is not knowing.** A safety net you've never dropped weight onto is
just a decoration.

Chaos engineering is the bridge from "should be resilient" to "is resilient." You connect it back to
Phase 07 directly: the observability stack you stood up last phase is the *eyes* that let you SEE whether
the net held. Without dashboards you'd be breaking things blind. So the order was deliberate — observe
first (07), then break (08). This whole phase exists to **prove the single region works before Phase 09
replicates it.** You do not replicate something you haven't proven; you'd just be copying an unknown.

> NEW CONCEPT — what is chaos engineering?
> A chaos experiment = a fire drill — you start the fire on purpose, in daylight, with the extinguisher in
> hand, to check the alarms actually work *before* a real fire at 3 a.m. It is **not** "randomly break prod
> and see what happens." It is a disciplined experiment with five fixed parts:
> 1. **Steady state** — a measurable "healthy" signal (e.g. checkout p99 latency < 300 ms, error rate < 1%).
> 2. **Hypothesis** — "even if I kill a `payment` pod, the steady state holds."
> 3. **Blast radius** — the smallest scope that can prove the hypothesis (one pod, one namespace, 30s).
> 4. **Run** — inject the fault while watching the steady-state metric on Grafana.
> 5. **Learn** — it held (great, you have evidence) or it didn't (great, you found a bug in daylight).
> We use it here because resilience claims that aren't tested are liabilities, and the cheapest place to
> find a weakness is a scheduled experiment you control — not a real outage you don't.

> NEW CONCEPT — blast radius (and why you start small and scoped)
> **Blast radius** = how much can break if the experiment goes worse than expected. Your first run of any
> new fault should have the *smallest possible* blast radius: one pod, not the whole Deployment; one
> namespace selector, not cluster-wide; 30 seconds, not an hour; off-peak, not Black Friday. You widen the
> radius only after a smaller version passed. Why: if your hypothesis is wrong, a small blast radius means
> you learned something cheaply instead of causing the very outage you were trying to prevent. Every Chaos
> Mesh object below has a `selector` and a `duration` — those are your blast-radius controls. Treat them
> as seatbelts, not boilerplate.

## Step 1 — Install Chaos Mesh (the fault-injection engine)

> What is Chaos Mesh, in one picture? It's a fault-injection engine that lives *inside* your cluster as a
> set of pods, plus a few new object kinds (`PodChaos`, `NetworkChaos`, `StressChaos`, `TimeChaos`). You
> write a short YAML that says "for these pods, for this long, cause this specific failure," apply it, and
> Chaos Mesh reaches down to the kernel/network layer and makes that failure real — then cleanly undoes it
> when the duration ends. Think of it as a controller (same reconcile loop from `2.2`) whose job is to
> *create* failures on demand and *remove* them on schedule.

> NEW CONCEPT — Chaos Mesh faults vs Istio fault injection (they are NOT the same)
> Both inject failures, but at different layers, and you need both:
> - **Chaos Mesh** breaks the **infrastructure**: it kills actual pods, drops/delays real packets at the
>   network interface, pins CPU, skews the OS clock. It tests "what if the *platform* misbehaves?"
> - **Istio fault injection** breaks the **application protocol**: it makes a VirtualService return an HTTP
>   503 or add a 5-second delay *as if the upstream service did*. It tests "what if a *dependency* is slow
>   or erroring?" — and it lets you exercise retries/timeouts/circuit breakers precisely, on a percentage
>   of requests, without actually harming the upstream pod.
> Rule of thumb: Chaos Mesh = "the machine/network broke." Istio = "the service answered badly." You'll use
> Chaos Mesh in Steps 2–5 and Istio in Step 6.

### Step 1 — Install Chaos Mesh with Helm
> What's happening here: you add the Chaos Mesh Helm repo, make a namespace for it, and install it. It runs
> as infrastructure (its own pods + the new CRDs), so it lives in its own `chaos-mesh` namespace, not in
> `shop`/`data`.

```bash
helm repo add chaos-mesh https://charts.chaos-mesh.org
helm repo update

kubectl create namespace chaos-mesh

helm install chaos-mesh chaos-mesh/chaos-mesh \
  -n chaos-mesh \
  --set chaosDaemon.runtime=containerd \
  --set chaosDaemon.socketPath=/run/containerd/containerd.sock \
  --version 2.6.3
```
Read this back in plain English: "Install the Chaos Mesh package into the `chaos-mesh` namespace, and tell
its on-every-node agent (`chaosDaemon`) that this cluster uses **containerd** as its container runtime."
That last bit matters: EKS nodes run containerd (not Docker), and the daemon needs the correct socket path
(`/run/containerd/containerd.sock`) to reach into containers and apply faults. Get the runtime wrong and
the daemon pods crash-loop.

What to expect: a handful of pods (`chaos-controller-manager`, `chaos-daemon` as a DaemonSet, `chaos-dashboard`).
Check them:
```bash
kubectl -n chaos-mesh get pods       # all Running; chaos-daemon has one pod per node
```
If `chaos-daemon` pods are `CrashLoopBackOff`, it's almost always the wrong runtime/socket above — re-check
the two `--set` flags. The dashboard UI is optional (port-forward `2333` if you want a GUI); we'll drive
everything from YAML so it's reproducible.

## Step 2 — PodChaos: kill a pod and watch it heal

> What's happening here: a PodChaos `pod-kill` = pulling one worker off the floor mid-shift without warning.
> The hypothesis you're testing: "killing one `payment` pod does not break checkout, because the Deployment
> replaces it and the PDB + remaining replicas absorb the gap." This is the gentlest experiment, so it goes
> first.

Create the file where you run kubectl:
```bash
nano pod-kill.yaml
```
Paste:
```yaml
apiVersion: chaos-mesh.org/v1alpha1
kind: PodChaos
metadata:
  name: payment-pod-kill
  namespace: shop                 # the chaos object lives next to its targets
spec:
  action: pod-kill                # delete the pod outright (k8s recreates it)
  mode: one                       # blast radius: exactly ONE matching pod
  selector:
    namespaces: [shop]
    labelSelectors:
      app: payment                # only pods labelled app=payment are eligible
  duration: "30s"                 # how long the experiment runs
```
Apply it and watch in a second terminal:
```bash
kubectl apply -f pod-kill.yaml
kubectl -n shop get pods -l app=payment -w     # watch one pod die and a new one come up; Ctrl-C to stop
```
Read the key fields: `mode: one` is your blast radius — it kills a single pod even though several match.
`selector` scopes it to `app=payment` in `shop` only. `duration: 30s` means Chaos Mesh stops re-killing
after 30 seconds, then leaves the Deployment to settle.

What to expect on Grafana: a brief blip, then nothing — checkout p99 should stay under your SLO because the
other replicas served traffic while the killed pod was replaced. If checkout latency or errors **spike past
the SLO**, you found something real: maybe `payment` has only 1 replica, or no PDB, or readiness gating is
missing. That's a win — you found it in daylight. Stop the experiment any time by deleting the object:
```bash
kubectl -n shop delete podchaos payment-pod-kill     # this is also your abort button
```

## Step 3 — NetworkChaos: latency, loss, and partition

> What's happening here: NetworkChaos = degrading the phone line between two services instead of cutting it.
> Real failures are rarely "pod gone" — they're "the network got slow/lossy" or "two services can't reach
> each other." You'll test three flavours: latency, packet loss, and a full partition.

### 3a. Latency — make `payment`'s network slow
> The hypothesis: "200 ms of added latency to `payment` is absorbed by timeouts/retries and the SLO holds."
```bash
nano net-latency.yaml
```
```yaml
apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata: { name: payment-latency, namespace: shop }
spec:
  action: delay
  mode: all                        # apply to ALL matching payment pods this time
  selector:
    namespaces: [shop]
    labelSelectors: { app: payment }
  delay:
    latency: "200ms"               # add 200ms to every packet
    jitter: "50ms"                 # +/- randomness, like real networks
    correlation: "50"
  duration: "60s"
```
```bash
kubectl apply -f net-latency.yaml
```
Watch checkout p99 on Grafana climb by ~200 ms — that's expected and fine as long as it stays under your
SLO ceiling. If it blows the SLO, your timeout budget is too tight or retries are amplifying the delay.

### 3b. Loss — drop packets
> The hypothesis: "10% packet loss to `payment` is masked by TCP retransmits + app retries; no user-visible
> errors." Same shape, different `action`:
```yaml
apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata: { name: payment-loss, namespace: shop }
spec:
  action: loss
  mode: all
  selector:
    namespaces: [shop]
    labelSelectors: { app: payment }
  loss:
    loss: "10"                     # drop 10% of packets
    correlation: "25"
  duration: "60s"
```

### 3c. Partition — cut `payment` off from its database
> The hypothesis: "if `payment` can't reach `postgres-payment`, it fails *fast and cleanly* (readiness goes
> false, it's pulled from rotation) rather than hanging and dragging down checkout." This is the harshest of
> the three, so run it last and keep the duration short.
```yaml
apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata: { name: payment-db-partition, namespace: shop }
spec:
  action: partition
  mode: all
  selector:
    namespaces: [shop]
    labelSelectors: { app: payment }
  direction: to                    # block traffic FROM payment TO the target below
  target:
    mode: all
    selector:
      namespaces: [data]
      labelSelectors: { app: postgres-payment }
  duration: "45s"
```
```bash
kubectl apply -f net-partition.yaml
kubectl -n shop get pods -l app=payment -w     # readiness should flip to 0/1, removing them from Endpoints
```
Read the new fields: `direction: to` plus a `target` selector means "block packets going *from* payment
*to* postgres-payment." What to expect: `payment` pods go `READY 0/1` (their `/readyz` can't reach the DB)
and the Service stops sending them traffic — exactly the behaviour you wired in `3.2`. When the duration
ends, the partition lifts and pods recover. Abort early with
`kubectl -n shop delete networkchaos payment-db-partition`.

## Step 4 — StressChaos: starve CPU and memory

> What's happening here: StressChaos = piling extra work onto the worker until they sweat. This is how you
> trigger **autoscaling** — the HPA from Phase 05 watches CPU, so if you pin CPU high, HPA should add
> replicas. Hypothesis: "CPU pressure on `payment` causes HPA to scale out and the SLO holds."

```bash
nano stress-cpu.yaml
```
```yaml
apiVersion: chaos-mesh.org/v1alpha1
kind: StressChaos
metadata: { name: payment-cpu-stress, namespace: shop }
spec:
  mode: all
  selector:
    namespaces: [shop]
    labelSelectors: { app: payment }
  stressors:
    cpu:
      workers: 2                   # 2 busy threads per pod
      load: 90                     # drive each to ~90% of a core
    memory:
      workers: 1
      size: "128MB"                # also grab 128MB to test memory pressure
  duration: "120s"                 # long enough for HPA to react (it polls ~every 15s)
```
```bash
kubectl apply -f stress-cpu.yaml
kubectl -n shop get hpa payment -w     # watch CURRENT cpu% rise, then REPLICAS climb; Ctrl-C to stop
```
What to expect: CPU utilization on the HPA crosses its target, and within a minute or so `REPLICAS` goes up.
On Grafana the checkout SLO should stay green because the new replicas pick up the slack. If REPLICAS never
moves, your HPA target/metrics-server may be misconfigured — another bug found cheaply. Note `duration: 120s`:
HPA reacts on a polling interval, so a 10-second stress proves nothing — give it time to see and respond.

## Step 5 — TimeChaos: skew the clock

> What's happening here: TimeChaos = secretly setting the worker's wristwatch wrong. Distributed systems
> assume clocks are roughly in sync — for token expiry (JWTs), TLS validity, cache TTLs, and "is this
> request too old?" checks. Hypothesis: "a +30s clock skew on `payment` doesn't break auth/token validation
> in a way that errors checkout." This catches bugs that *only* show up when time disagrees.

```yaml
apiVersion: chaos-mesh.org/v1alpha1
kind: TimeChaos
metadata: { name: payment-time-skew, namespace: shop }
spec:
  mode: one                        # small blast radius: one pod's clock
  selector:
    namespaces: [shop]
    labelSelectors: { app: payment }
  timeOffset: "+30s"               # push this pod's clock 30 seconds into the future
  duration: "60s"
```
```bash
kubectl apply -f time-skew.yaml
kubectl -n shop logs -l app=payment --tail=50    # look for token-expiry / clock-related errors
```
What to expect: ideally nothing user-visible. If you see auth tokens rejected or TLS handshake failures, you
just learned your system is brittle to clock skew — a notoriously hard bug to find any other way. Clean up:
`kubectl -n shop delete timechaos payment-time-skew`.

## Step 6 — Istio fault injection: break the *protocol*, not the pod

> What's happening here: this is the other layer from the NEW CONCEPT box. Instead of harming a pod, you
> tell Istio's VirtualService to *pretend* the upstream answered badly — add an HTTP delay or return a 503 —
> on a percentage of requests. Istio fault injection = a stunt double — the real actor (the pod) is unharmed,
> but the scene looks like a crash. This is the cleanest way to exercise **retries, timeouts, and circuit
> breaking** on demand.

> Why a VirtualService and not Chaos Mesh here? Because you want a *protocol-level* failure (HTTP 503) on a
> *controlled fraction* (say 30%) of requests, applied at the mesh, with zero risk to the actual pod. Chaos
> Mesh can't make a healthy pod return a fake 503; Istio can.

Create the fault-injection VirtualService:
```bash
nano payment-fault.yaml
```
```yaml
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata: { name: payment, namespace: shop }
spec:
  hosts: [payment]                 # the in-mesh hostname callers use
  http:
  - fault:
      delay:
        percentage: { value: 30 } # 30% of requests...
        fixedDelay: 5s            # ...get a 5-second delay injected
      abort:
        percentage: { value: 10 } # 10% of requests...
        httpStatus: 503           # ...get an immediate HTTP 503
    route:
    - destination: { host: payment }
```
```bash
kubectl apply -f payment-fault.yaml
```
Read it back: "For traffic to `payment`, delay 30% of requests by 5 s and abort 10% with a 503, then route
the rest normally." What to expect on Grafana/Kiali: callers of `payment` start seeing some 503s and slow
calls. Now the resilience features earn their keep — if the caller has retries with a sane budget, most of
those 10% aborts succeed on retry and never reach the user. **Remove it to end the experiment** (this is an
*added* fault, so deleting the VirtualService restores normal routing):
```bash
kubectl -n shop delete virtualservice payment    # or re-apply your non-fault VirtualService
```

## Step 7 — FAIL_MODE: watch retries + circuit breaking + outlier ejection together

> What's happening here: the `payment` service has a built-in `FAIL_MODE` env toggle that makes it return
> errors on purpose — a fault baked into the app itself. Flipping it on a *subset* of replicas is the
> perfect way to watch **Istio outlier detection** (from Phase 06) do its job: detect the bad endpoint by
> its 5xx rate and eject it from the load-balancing pool, so good replicas keep serving.

> The hypothesis: "if one `payment` replica starts failing, Istio outlier detection ejects it within a few
> consecutive 5xx, retries cover the in-flight requests, and the checkout SLO never breaks."

Toggle FAIL_MODE on and let it ride:
```bash
# turn the whole deployment into a failer briefly, OR scale a separate 'bad' replica set;
# simplest demo: flip the env and immediately watch outlier detection + retries respond
kubectl -n shop set env deploy/payment FAIL_MODE=true
kubectl -n shop get pods -l app=payment -w        # new pods roll with FAIL_MODE on
```
On Grafana watch three things at once:
1. `payment` **5xx rate** rises (the fault is real).
2. Istio **outlier detection** ejects the failing endpoint(s) — in Kiali the host shows ejected hosts; the
   error rate to *callers* drops back down as bad endpoints leave the pool.
3. **Retries** smooth over the brief window before ejection, so checkout's user-facing error rate stays
   under the SLO.

Then turn it back off and confirm recovery:
```bash
kubectl -n shop set env deploy/payment FAIL_MODE=false
kubectl -n shop rollout status deploy/payment      # healthy pods return; ejected endpoints rejoin
```
What to expect: a clean V-shape on the caller error-rate graph — up when FAIL_MODE flips on, back down once
outlier detection ejects the bad endpoint, flat after recovery. If the error rate *stays* high, your outlier
detection thresholds (consecutive 5xx, ejection time) need tuning — exactly the kind of finding this phase
exists to surface.
