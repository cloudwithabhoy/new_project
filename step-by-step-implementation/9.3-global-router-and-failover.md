# 9.3 — Global router & failover (Route 53 latency routing + health-checked failover)

## Goal
Put **one global front door** in front of your two regional stacks so that a single hostname —
`shop.example.com` — automatically sends each user to the **nearest healthy region**, and when a region goes
unhealthy, its traffic moves to the other region on its own. Default path: **Route 53 latency-based routing**
with a **health check per region** and a **low TTL**. Then a note on **AWS Global Accelerator** as the
instant-failover upgrade.

## Why this part exists (read this first)
After `9.2` you have two complete stacks, each with its **own regional ALB** — a Mumbai ALB and a London ALB,
each a different hostname in a different region. But a user doesn't want to know about two hostnames and pick
the right one; they want to type **one** name and be served fast and reliably. Nothing you've built so far
does that, because **an ALB is a regional resource** — there is no such thing as a single ALB spanning both
regions. So you need a **layer above** the two ALBs whose only job is: given a request, choose a region. That
layer is the global router, and this part builds it.

> NEW CONCEPT — why an ALB can't be the global front door.
> An Application Load Balancer lives **inside one region's VPC**. It can spread traffic across pods, AZs, and
> nodes — but only **within its own region**. It has no awareness of, and no path to, the other region's
> cluster. So "send UK users to London and Indian users to Mumbai" is a question an ALB *structurally cannot
> answer*. You need something that sits **in front of both ALBs** and chooses between them. The two standard
> choices are **DNS** (Route 53) and **anycast** (Global Accelerator) — the rest of this part.

> NEW CONCEPT — DNS-based geo/latency routing, health checks, and TTL.
> **DNS** is how `shop.example.com` becomes an IP — and Route 53 can return a **different** answer depending
> on *who's asking from where*. **Latency-based routing**: Route 53 knows the measured network latency from
> the user's location to each AWS region and returns the **lowest-latency** region's ALB. (Analogy: a host
> who seats each guest at the nearest open table.) **Health check**: Route 53 continuously pings each
> region's ALB; if a region's check goes red, Route 53 **stops handing out that region's answer** and serves
> only the healthy one — that's failover. **TTL** (time-to-live): how many seconds a resolver is allowed to
> **cache** the DNS answer before asking again. TTL is the catch — until a cached answer expires, that user
> keeps going to the (possibly now-dead) region. So for failover you set a **low TTL** (60s) to bound how
> long anyone can be stuck on a failed region.

## Prerequisites
- [`9.2`](./9.2-deploy-the-stack.md) done — both regions serve a checkout locally, each behind its own ALB,
  and each response carries an `X-Region` marker (`in` for Mumbai, `uk` for London). You'll lean on that
  marker to *prove* routing.
- A **Route 53 hosted zone** for your domain (e.g. `example.com`) — the same global zone both regions'
  ExternalDNS already write into.
- The two ALB hostnames handy:
  ```bash
  # Mumbai
  kubectl config use-context ecom-cluster        # or your Mumbai context name
  MUM_ALB=$(kubectl -n shop get ingress <gateway-ingress> -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
  # London
  kubectl config use-context ecom-cluster-uk
  UK_ALB=$(kubectl -n shop get ingress <gateway-ingress> -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
  echo "$MUM_ALB"; echo "$UK_ALB"
  ```

> Scope reminder: this part is **routing only**. It sends a user to a healthy nearby region; it does **not**
> make the two regions share data. A user failed over from London to Mumbai hits Mumbai's *own* data (Phase 10
> handles cross-region DB replication; Phase 12 handles Kafka). Build the router now; wire data later.

> One-liner for each tool here: **Route 53 latency routing** = a host who seats each guest at the nearest
> open table, and re-seats them if a table catches fire (health check). **Global Accelerator** = a private
> express lane onto the AWS backbone with a fixed front door, so re-seating is instant (no waiting for a
> guest's cached table number to expire).

## Why these records are created by hand (not ExternalDNS)
In `9.1` you set a different `txtOwnerId` per region precisely so each region's ExternalDNS owns only *its*
records. The **global** record below points at **both** regions — it can't be owned by one region's
ExternalDNS without the other fighting it. So you create the global `shop.example.com` records and health
checks **manually** (console, CLI, or Terraform), once, as a global concern that sits above both regions.

## Step 1 — Create a health check per region
> What's happening here: you tell Route 53 to continuously probe each region's ALB at a real health endpoint.
> These checks are what turn "latency routing" into "latency routing **with failover**" — Route 53 will only
> ever hand out a region whose check is green.

Create one health check per ALB (pointing at a cheap, honest endpoint your gateway serves, e.g. `/healthz`):
```bash
# London health check
aws route53 create-health-check \
  --caller-reference uk-$(date +%s) \
  --health-check-config "Type=HTTPS,FullyQualifiedDomainName=$UK_ALB,ResourcePath=/healthz,RequestInterval=10,FailureThreshold=3"

# Mumbai health check
aws route53 create-health-check \
  --caller-reference in-$(date +%s) \
  --health-check-config "Type=HTTPS,FullyQualifiedDomainName=$MUM_ALB,ResourcePath=/healthz,RequestInterval=10,FailureThreshold=3"
```
Read the key fields: `RequestInterval=10` → probe every 10s; `FailureThreshold=3` → mark unhealthy after 3
straight failures (~30s to detect a dead region). Note each command returns a **health-check Id** — you'll
attach those Ids to the records in Step 2.
> Pick a `ResourcePath` that fails when the region is *actually* unserviceable — ideally one that checks the
> app can reach its database, not just that the ALB answers. A health check that's green while the app is
> broken is worse than none: it keeps sending users into a hole.

---

## Step 2 — Create one latency record per region, each tied to its health check
> What's happening here: under the single name `shop.example.com` you create **two** A-records — one
> "latency" record per region — each aliased to that region's ALB, each carrying that region's health-check
> Id, all with a **60-second TTL**. Route 53 picks the lowest-latency record **among the healthy ones**.

Easiest to do as a change-batch file. Create it:
```bash
nano latency-records.json
```
Paste (fill in your hosted-zone id, the ALB hostnames, the ALBs' hosted-zone ids, and the health-check Ids):
```json
{
  "Comment": "Global latency routing for shop.example.com across Mumbai + London",
  "Changes": [
    {
      "Action": "UPSERT",
      "ResourceRecordSet": {
        "Name": "shop.example.com",
        "Type": "A",
        "SetIdentifier": "mumbai-ap-south-1",
        "Region": "ap-south-1",
        "TTL": 60,
        "HealthCheckId": "<MUMBAI_HEALTH_CHECK_ID>",
        "AliasTarget": {
          "HostedZoneId": "<MUMBAI_ALB_HOSTED_ZONE_ID>",
          "DNSName": "<MUM_ALB hostname>",
          "EvaluateTargetHealth": true
        }
      }
    },
    {
      "Action": "UPSERT",
      "ResourceRecordSet": {
        "Name": "shop.example.com",
        "Type": "A",
        "SetIdentifier": "london-eu-west-2",
        "Region": "eu-west-2",
        "TTL": 60,
        "HealthCheckId": "<LONDON_HEALTH_CHECK_ID>",
        "AliasTarget": {
          "HostedZoneId": "<LONDON_ALB_HOSTED_ZONE_ID>",
          "DNSName": "<UK_ALB hostname>",
          "EvaluateTargetHealth": true
        }
      }
    }
  ]
}
```
Apply it:
```bash
aws route53 change-resource-record-sets \
  --hosted-zone-id <YOUR_HOSTED_ZONE_ID> \
  --change-batch file://latency-records.json
```
The flags that matter:
- `"Type": "A"` + `"AliasTarget"` → an **alias** to an ALB (AWS's free, zone-aware pointer to an AWS
  resource; you don't hardcode IPs because an ALB's IPs change).
- `"Region"` + matching `"SetIdentifier"` → this is the **latency** record for that AWS region; Route 53
  uses the region to compute which is closest to each user.
- `"HealthCheckId"` + `"EvaluateTargetHealth": true` → only serve this region if its health check is green.
- `"TTL": 60` → resolvers cache the answer at most 60s, so a failover propagates within ~a minute.

> Per-region values here are the obvious ones: each record's `Region`, `SetIdentifier`, `DNSName` (its ALB),
> `HostedZoneId` (the ALB's zone id — region-specific), and `HealthCheckId`. Everything else (`Name`, `TTL`,
> the structure) is identical across both records — same shared-structure / per-region-values discipline as
> `9.2`.

## Step 3 — Verify: right region, then watch a failover
> What's happening here: first prove that a UK-ish request lands on London and an India-ish request lands on
> Mumbai (using the `X-Region` marker from `9.2`). Then deliberately **fail** one region's health check and
> watch traffic move to the other.

### 3a. Prove latency routing puts each user on the near region
```bash
# from the UK (or a UK VPN / a London EC2 instance), expect London:
curl -s -D - https://shop.example.com/healthz -o /dev/null | grep -i x-region   # -> X-Region: uk

# from India (or a Mumbai EC2 instance), expect Mumbai:
curl -s -D - https://shop.example.com/healthz -o /dev/null | grep -i x-region   # -> X-Region: in
```
You can also see *which* answer Route 53 hands a given location:
```bash
dig +short shop.example.com           # resolves to the near region's ALB for wherever you run dig
```
> You need to actually be (or appear to be) in each location for this — latency routing keys off the
> **resolver's** location. Run one `curl` from a London EC2 instance and one from a Mumbai EC2 instance and
> compare the `X-Region` headers; that's the clean proof.

### 3b. Fail a region and watch traffic move
Take London's health check red on purpose, then poll the global name and watch it flip to Mumbai:
```bash
# fastest way to fake a failure: point London's health check at a path that 404s, or disable the check
aws route53 update-health-check --health-check-id <LONDON_HEALTH_CHECK_ID> --disabled

# from the UK, keep hitting the GLOBAL name; within ~TTL+detection it stops saying uk and starts saying in
for i in $(seq 1 30); do
  curl -s -D - https://shop.example.com/healthz -o /dev/null | grep -i x-region
  sleep 5
done
# expect: a few `X-Region: uk`, then it flips to `X-Region: in` (Mumbai) once London is marked unhealthy
```
Re-enable London to fail back:
```bash
aws route53 update-health-check --health-check-id <LONDON_HEALTH_CHECK_ID> --no-disabled
# within ~a minute UK requests return to `X-Region: uk`
```
> The flip is not instant: it's (health-check detection ~30s) + (TTL ≤60s of cached answers expiring). So a
> worst-case UK user might see up to ~90s on the dead region before moving. That window is *the* fundamental
> limitation of DNS failover — and the reason for Step 4.

---

## Step 4 — The instant-failover upgrade: AWS Global Accelerator (note)
> What's happening here: a short orientation on the upgrade you reach for when ~90s of DNS failover is too
> slow. You don't have to build it now — but know what it is and when it wins.

> NEW CONCEPT — Global Accelerator vs Route 53 (anycast vs DNS TTL).
> **Global Accelerator** gives you **two fixed anycast IPs** that are advertised from AWS edge locations
> worldwide. A user's packets enter the **AWS private backbone** at the nearest edge and ride it to the
> nearest healthy region's ALB. Two things change versus DNS: (1) failover is **near-instant** — there's
> **no TTL**, because the user always talks to the same fixed anycast IPs; when a region fails, the
> *backbone* simply stops routing to it, no client-side cache to wait out. (2) the long-haul leg runs on
> AWS's network instead of the public internet, which is usually faster and steadier. The trade-off:
> Accelerator is a paid, always-on service, and it's a thinner "pick a region" layer (Route 53 also does rich
> geo/weighted/multi-record DNS policies). The clean mental model: **Route 53 = choose the region by changing
> the DNS answer (cheap, flexible, TTL-bound); Global Accelerator = keep one fixed front door and re-route on
> the backbone (instant failover, premium).** Many setups use Route 53 first and add Accelerator when the
> ~90s DNS window becomes unacceptable.

If you adopt it: create an accelerator, add a listener, and add **two endpoint groups** (one per region)
each pointing at that region's ALB with a health check — then point `shop.example.com` at the accelerator's
anycast IPs (or its DNS name) instead of the latency records.

---

## Verify
- `https://shop.example.com` returns `X-Region: uk` from London and `X-Region: in` from Mumbai — latency
  routing works.
- Disabling London's health check makes UK traffic flip to `X-Region: in` within ~90s, and re-enabling it
  fails back — health-checked failover works.
- The whole thing rides on **two regional ALBs + a global DNS layer**; you can articulate why the ALB can't
  be global and why Istio stays inside each region.

```
                         user types shop.example.com
                                    │
                          ┌─────────▼─────────┐
                          │  Route 53 (global) │  latency pick + health checks, TTL 60s
                          │  (or Global Accel.)│
                          └────┬──────────┬────┘
              nearest+healthy  │          │  nearest+healthy
                  ┌────────────▼──┐    ┌──▼─────────────┐
                  │ Mumbai ALB    │    │ London ALB     │   regional ALBs (can't be global)
                  │ Istio gateway │    │ Istio gateway  │   ← Istio mesh stays INSIDE each region
                  │ services + DB │    │ services + DB  │
                  └───────────────┘    └────────────────┘
                   independent stack     independent stack   (data replication = Phase 10/12)
```

## Concept deep-dive — global traffic management (latency routing + health-checked failover), and why Istio stays inside each region
You've now built a clean two-layer model, and the layering is the whole insight.

**The two layers.** The **global** layer (Route 53 or Global Accelerator) answers exactly one question:
*which region?* — by nearest latency, gated by health. The **regional** layer (each region's Istio mesh +
ALB) answers everything *within* a region: which pod, mTLS, retries, traffic splitting, canaries. The global
layer is deliberately dumb (pick a region); the regional layer is rich (run the mesh).

**How failover works end-to-end.** Health checks continuously grade each region. Route 53 only ever returns
*healthy* regions, and among those, the lowest-latency one. When a region's check goes red, its answer stops
being handed out; cached answers drain within the TTL; users land on the surviving region. Global Accelerator
does the same selection but on the backbone with no TTL, so the drain is instant.

**Why Istio stays inside each region (and is NOT one stretched mesh).** It is tempting to run a single Istio
mesh spanning both regions and let *Istio* do the global routing. We don't, for the same reason an ALB isn't
global: a stretched mesh puts mesh **control-plane and sidecar** traffic on the **cross-region** path — the
Atlantic hop lands back on the hot path, the two regions share a failure domain (a mesh-wide problem takes
both down), and operating one mesh across regions is genuinely hard. Keeping Istio **inside** each region
means each region is a self-contained, independently-failing unit, and the **only** thing crossing regions is
a user being *directed* to one or the other — never live mesh traffic. The thin global router is the right
amount of "global"; the mesh is the right amount of "local".

**Why not skip DNS and only use Accelerator (or vice-versa)?** Route 53 is cheap, does rich routing policies,
and is the natural default — its only weakness is the TTL-bound failover window. Global Accelerator fixes the
window with anycast but costs more and does less policy. The mature answer is layered: Route 53 by default,
Accelerator when the failover window must be sub-second.

*Interview line: "Global traffic management is two layers — a thin global router (Route 53 latency routing
with per-region health checks and a low TTL, or Global Accelerator's anycast for instant failover) that only
picks a region, sitting above independent per-region stacks. ALBs and the Istio mesh are regional by design,
so the only thing that ever crosses regions is the *choice* of region — never live mesh or data-plane
traffic. That keeps each region a clean failure-and-latency domain."*
