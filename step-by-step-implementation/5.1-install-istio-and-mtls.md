# 5.1 — Install Istio and turn on STRICT mTLS

## Goal
By the end of this part, every pod in the `shop` namespace will be running a second, invisible container
next to your app container — an **Envoy proxy** — and all traffic between your 12 services will be
**encrypted and mutually authenticated** automatically. You won't change a single line of application code
to get there. You'll have a running Istio control plane, every `shop` pod redeployed with a sidecar, and a
cluster-wide rule that *rejects* any plaintext traffic between services.

## Why this part exists (read this first)
After Phase 04, all 13 components run and the whole app is reachable through the ALB Ingress. It works —
but it's blind and trusting. When `order` calls `payment`, that call is **plaintext** inside the cluster,
and `payment` has no real proof that the caller is actually `order` and not some pod that sneaked into the
namespace. You also have almost no idea what's talking to what, how slow each hop is, or where a checkout
stalls. Phase 04 gave you *reachability*; it gave you nothing for *security between services*,
*observability*, or *traffic control*.

A **service mesh** fills exactly that gap. Instead of bolting encryption, retries, and tracing into all 12
services by hand (12 times, in whatever language each is written in), you push that job *out* of the app
and *into* a proxy that sits beside every pod. This first part installs the mesh and lights up its single
most valuable feature: automatic mutual TLS. The next two parts (`5.2`, `5.3`) use the same mesh for edge
routing and for traffic control + tracing.

> NEW CONCEPT — what is a service mesh, and what is the "sidecar pattern"?
> A **service mesh** is a layer that handles service-to-service networking *for* your apps instead of *in*
> your apps. The trick that makes it work is the **sidecar pattern**: next to each of your app containers,
> Istio runs a tiny extra container — an **Envoy proxy**. Picture it as a personal translator-and-bodyguard
> who sits next to every worker and handles all their phone calls: your app still thinks it's calling
> `payment` directly, but really it's talking to its own local Envoy, which encrypts the call, proves who it
> is, and forwards it to `payment`'s Envoy on the other end. Because every pod has one, the mesh can enforce
> encryption, collect metrics, and route traffic **without your code knowing**. We use this pattern (rather
> than a shared library you `import` into each service) precisely because it's language-agnostic and you
> upgrade the networking behaviour by upgrading the proxy, not by rebuilding 12 apps.

> NEW CONCEPT — data plane vs control plane (and what `istiod` is).
> The mesh has two halves. The **data plane** is the fleet of Envoy sidecars — they're the ones actually
> carrying your traffic, packet by packet. The **control plane** is a single component called **istiod**
> (Istio Daemon) — it's the brain that configures every Envoy: it hands out the mTLS certificates, pushes
> routing rules, and tells each proxy who it's allowed to talk to. Think air-traffic control (istiod, one
> brain, no planes) vs the pilots (Envoys, many, doing the flying). You'll install istiod once; the Envoys
> appear automatically next to your pods.

## Before you start — where you run these commands
Run everything from the machine where `kubectl` already talks to `ecom-cluster` (your Jenkins EC2 instance
or laptop). Sanity check:

```bash
kubectl config current-context     # should name ecom-cluster / ap-south-1
kubectl -n shop get pods           # your 12 services, all READY, no sidecars yet
```
If kubectl isn't pointed at the cluster, reconnect first:
```bash
aws eks update-kubeconfig --region ap-south-1 --name ecom-cluster
```

You also need the `istioctl` CLI — Istio's own command-line tool (like `kubectl`, but for Istio-specific
tasks: installing the mesh, injecting sidecars, debugging proxies). Install it once:
```bash
curl -L https://istio.io/downloadIstio | sh -      # downloads the latest release into ./istio-*/
cd istio-*/                                          # the folder it just created
export PATH=$PWD/bin:$PATH                           # put istioctl on your PATH for this shell
istioctl version                                     # prints client version; control plane "not found" is fine for now
```
What that did: downloaded the Istio release bundle, then added its `bin/` to your PATH so you can type
`istioctl` anywhere. The "control plane not found" line is expected — you haven't installed it yet.

## Step 1 — Install the Istio control plane (istiod)

> An Istio installation profile = a pre-baked starter pack of "which mesh components to install and how."
> The `demo` profile turns on lots of features for learning; the `default` profile is the lean,
> production-leaning set (istiod + an ingress gateway). We'll use `default` because it matches what you'd
> actually run.

> What's happening here: you're installing the **brain** of the mesh — istiod — plus an ingress gateway
> Deployment (you'll wire that gateway up to traffic in `5.2`; right now it just gets created). Nothing
> about your apps changes yet. This is purely "stand up the control plane."

```bash
istioctl install --set profile=default -y
```
Read that back in plain English: "Install Istio using the `default` profile, and `-y` = don't prompt me for
confirmation." Behind the scenes it creates the `istio-system` namespace and runs istiod and an
`istio-ingressgateway` Deployment there.

After it runs you should see it report each component installed with a green tick and `Installation
complete`. Confirm:
```bash
kubectl -n istio-system get pods      # istiod and istio-ingressgateway should reach READY 1/1
```
If `istiod` is stuck `Pending`, it's almost always no room to schedule — check `kubectl -n istio-system
describe pod` for "Insufficient cpu"; Karpenter (from `2.2`) should add a node within a minute.

## Step 2 — Turn on automatic sidecar injection for the `shop` namespace

> Automatic sidecar injection = a standing instruction that says "any pod created in this namespace, slip an
> Envoy container into it before it starts." It's a label on the namespace; istiod's admission webhook does
> the actual injecting at pod-creation time.

> What's happening here: you label the `shop` namespace so that from now on, **new** pods born there get a
> sidecar automatically. Read that word carefully — **new** pods. This label does nothing to the pods that
> are *already running*. That's why Step 3 exists.

```bash
kubectl label namespace shop istio-injection=enabled
```
Plain English: "Stick the label `istio-injection=enabled` on the `shop` namespace." That label is the flag
istiod's webhook watches for. We label only `shop` (the 12 services), not `data` — we'll keep the
datastores out of the mesh for now to avoid surprises with stateful TLS, and because the app talks to them
over their own DB protocols.

Confirm the label landed:
```bash
kubectl get namespace shop --show-labels      # you should see istio-injection=enabled in the list
```
If you don't see it, you labelled the wrong namespace name — re-run with `shop` spelled exactly.

> NEW CONCEPT — why injection only affects pods created AFTER you label.
> The sidecar is added by a **mutating admission webhook** — a hook istiod registers with the Kubernetes API
> server that fires *as a pod is being created* and rewrites the pod spec to add the Envoy container. It
> only runs at creation time. Your already-running `shop` pods were created **before** the label existed, so
> the webhook never touched them — they have no sidecar. The fix is simple: recreate them. That's Step 3.

---

## Step 3 — Redeploy the `shop` services so every pod gets a sidecar

> What's happening here: you do a rolling restart of every Deployment in `shop`. Kubernetes deletes each old
> (no-sidecar) pod and creates a fresh one — and because the namespace is now labelled, each fresh pod gets
> an Envoy sidecar injected on the way up. Your readiness probes (from `3.2`) mean traffic only shifts to a
> new pod once it's actually ready, so this is a zero-downtime change.

```bash
kubectl -n shop rollout restart deployment      # restarts ALL deployments in the namespace
kubectl -n shop rollout status deployment        # waits and reports each one finishing its rollout
```
Read that back: "For every Deployment in `shop`, do a controlled rolling restart, then wait until each
finishes." `rollout restart` is the clean way to recreate pods — it respects replica counts and readiness,
so the app stays up the whole time.

Now look at a pod and count the containers:
```bash
kubectl -n shop get pods           # the READY column should now read 2/2 instead of 1/1
```
That `2/2` is the whole point: container 1 is your app, container 2 is its Envoy sidecar. To literally see
the sidecar named `istio-proxy`:
```bash
kubectl -n shop get pod -l app=order -o jsonpath='{.items[0].spec.containers[*].name}'
# expect:  order istio-proxy
```
If pods come back `1/1` (no sidecar), the label didn't take or the webhook isn't healthy — re-check Step 2,
then `kubectl -n istio-system get pods` to confirm istiod is `READY`.

## Step 4 — Enforce STRICT mutual TLS across the namespace

> mTLS (mutual TLS) = both ends of a connection present a certificate and verify each other. Plain HTTPS
> proves the *server's* identity to the client; **mutual** TLS also proves the *client's* identity to the
> server. In the mesh, every Envoy has a short-lived certificate issued by istiod that encodes its identity
> (its ServiceAccount), so `payment`'s sidecar can cryptographically confirm a caller really is `order`.

> A `PeerAuthentication` object = the policy that says "how must callers authenticate to pods here?" Its
> `mtls.mode` can be `PERMISSIVE` (accept both plaintext and mTLS — the default, good during migration) or
> `STRICT` (reject anything that isn't mTLS). We're going straight to STRICT because all of `shop` now has
> sidecars, so there's no plaintext caller left to break.

> What's happening here: you write one small object that flips the whole `shop` namespace to STRICT mTLS.
> After this, any pod trying to reach a `shop` service over plain HTTP gets refused at the Envoy.

Create the file:
```bash
nano strict-mtls.yaml
```
Paste:
```yaml
apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata:
  name: default            # "default" name = applies to the whole namespace it lives in
  namespace: shop
spec:
  mtls:
    mode: STRICT           # reject any non-mTLS (plaintext) traffic between shop pods
```
Then apply it (turn the file into live cluster policy):
```bash
kubectl apply -f strict-mtls.yaml
```
Two details worth knowing. The name `default` is special: a `PeerAuthentication` named `default` with no
`selector` applies to **every** pod in its namespace — that's how one tiny file covers all 12 services.
And because you only set the namespace (`shop`), the `data` namespace and its DB connections are untouched.

> NEW CONCEPT — why STRICT and not just leave it PERMISSIVE?
> PERMISSIVE is a *migration* setting: it lets mTLS and plaintext coexist while you're still rolling
> sidecars out, so nothing breaks mid-migration. But "accepts plaintext" also means an attacker who lands a
> pod in `shop` can still talk to `payment` in the clear and impersonate anyone. STRICT closes that door:
> no certificate, no conversation. Since Step 3 gave *every* `shop` pod a sidecar, there are no legitimate
> plaintext callers left — so STRICT costs you nothing and buys you real, enforced, in-cluster encryption
> and identity. That's the whole reason to do `5.1` before anything else: get the security floor in first.

## Verify
- `kubectl -n shop get pods` shows every pod `READY 2/2` (app + `istio-proxy` sidecar).
- The control plane is healthy: `kubectl -n istio-system get pods` shows `istiod` `READY 1/1`.
- mTLS is actually STRICT, proven two ways:
  - `istioctl authn tls-check $(kubectl -n shop get pod -l app=order -o jsonpath='{.items[0].metadata.name}').shop` — the `SERVER` column should read `STRICT`.
  - A negative test: exec into a pod and curl another service *without* a sidecar identity and watch it get refused.
    ```bash
    # a no-sidecar throwaway pod (default namespace, no injection) cannot reach a STRICT shop service:
    kubectl run probe --image=curlimages/curl -it --rm --restart=Never -- \
      curl -s -o /dev/null -w '%{http_code}\n' http://order.shop.svc.cluster.local:8081/healthz
    # expect: a connection reset / 000 — plaintext is rejected. A real shop pod (with a sidecar) CAN reach it.
    ```
- The full app still serves through the ALB exactly as it did in Phase 04 (the mesh is transparent to users).

## Concept deep-dive — the sidecar / data-plane vs control-plane model, and how mTLS happens automatically
The mesh is two cooperating layers, and keeping them straight is what makes Istio click:

```
            ┌──────────────── control plane ────────────────┐
            │                    istiod                       │
            │   issues certs · pushes config · the brain      │
            └───────┬───────────────────────────────┬─────────┘
          config +  │ certs                  config + │ certs
                    ▼                                 ▼
      ┌─ order pod ─────────────┐        ┌─ payment pod ───────────┐
      │  app  ⇄  Envoy sidecar  │=[mTLS]=│  Envoy sidecar  ⇄  app  │   ◄── data plane
      └─────────────────────────┘        └─────────────────────────┘
```

**Data plane (the Envoys):** every pod's sidecar transparently intercepts the pod's inbound and outbound
traffic (Istio sets up iptables rules inside the pod so the app's connections are redirected through Envoy
without the app knowing). The app dials `payment` as usual; its own Envoy actually makes the encrypted call.

**Control plane (istiod):** istiod is the only component that holds the cluster's trust. On startup, each
Envoy proves its identity to istiod and gets issued a short-lived X.509 **certificate** whose identity is
the pod's ServiceAccount (e.g. `spiffe://cluster.local/ns/shop/sa/order`). istiod rotates these certs
automatically — typically every 24h — so you never manage a key.

**How mTLS "just happens":** when `order`'s Envoy connects to `payment`'s Envoy, the two perform a normal
TLS handshake, but **mutual** — each presents its istiod-issued cert and verifies the other's against
istiod's root of trust. `payment`'s Envoy now *knows* the caller's identity is `order`, cryptographically,
not just by a header it could fake. Your `PeerAuthentication: STRICT` then says "and refuse anyone who
*can't* do this handshake." You wrote zero crypto code; the proxies did it all.

Why this design over a TLS library inside each app? A library means re-implementing and re-certifying mTLS
in every language you use, and a security fix means rebuilding and redeploying all 12 services. With the
sidecar model, the security logic lives in one component you upgrade independently of your code.

*Interview line: "Istio splits networking into a data plane of per-pod Envoy sidecars that carry and encrypt
traffic, and a control plane — istiod — that issues each workload a SPIFFE-identity certificate and pushes
config; STRICT PeerAuthentication then enforces that every in-mesh call is mutually authenticated, giving
zero-trust service-to-service security with no application code changes."*

Next → with the mesh in place and traffic encrypted, `5.2` moves the public edge off the ALB Ingress and
onto an Istio Gateway, so even north-south traffic flows through the mesh.
