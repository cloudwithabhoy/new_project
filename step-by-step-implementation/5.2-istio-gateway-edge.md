# 5.2 — Move the public edge into the mesh (Istio Gateway + VirtualService)

## Goal
By the end of this part, public traffic from the internet will enter your cluster through the **Istio
ingress gateway** (its own AWS load balancer) instead of the old ALB Ingress, get routed to `api-gateway`
by an Istio `VirtualService`, and you'll have safely retired the old Ingress. The user-facing URL keeps
working the whole way through. You'll have a Gateway, a VirtualService, and a cleaner edge where the *same*
mesh that secures internal traffic now also governs traffic coming *in*.

## Why this part exists (read this first)
In Phase 04 the front door was a Kubernetes **Ingress** handled by the AWS Load Balancer Controller — it
built an ALB and that ALB forwarded straight to your pods. That worked, but it means your edge and your
internal mesh are two different worlds with two different rule systems: the ALB does its own thing, and the
moment traffic crosses into a pod it falls under Istio. You can't apply mesh routing, mesh retries, or mesh
telemetry to that first hop, because that first hop never went through the mesh.

`5.1` put every service behind an Envoy and encrypted east-west traffic. This part pulls the **north-south**
hop (internet → cluster) into the mesh too, so requests are governed by Istio from the very edge. That
gives you one place and one language (`Gateway` + `VirtualService`) for *all* routing — edge and internal —
and it's the foundation `5.3` builds on to get end-to-end traces that include the public entry point.

> NEW CONCEPT — north-south vs east-west traffic.
> Two directions, and people name them by a compass habit from network diagrams. **North-south** = traffic
> crossing the cluster boundary — the internet coming *in* (or your app calling *out*). **East-west** =
> traffic *between* services already inside the cluster (`order` → `payment`). `5.1`'s mTLS was about
> east-west. This part is about pulling north-south ingress into the same mesh, so both directions obey the
> same control plane.

> NEW CONCEPT — Gateway vs VirtualService vs the old Ingress.
> A Kubernetes **Ingress** was one object that smashed two jobs together: "open a port to the world" *and*
> "route these paths to these services." Istio splits that into two cleaner objects:
> - **Gateway** = the *door and the lock*. It says "the ingress gateway should accept HTTP on port 80 for
>   these hostnames." It opens a port; it does **not** decide where requests go.
> - **VirtualService** = the *signposts inside*. It says "for this host, send `/` to `api-gateway`, send
>   `/admin` somewhere else." It's the routing rules, and you can later add weights, retries, and fault
>   injection here.
> Think of the Gateway as the building's front door, and the VirtualService as the lobby directory that
> tells each visitor which office to go to. We split them because one Gateway (one door) is usually shared
> by many VirtualServices (many apps' routing), and separating "expose a port" from "route requests" lets
> different teams own each without stepping on each other.

## Prerequisites
- `5.1` complete: Istio installed, `shop` injected, STRICT mTLS on.
- The `istio-ingressgateway` Deployment already exists in `istio-system` (the `default` profile installed it
  in `5.1`).
- The AWS Load Balancer Controller from `2.2` is still installed (the ingress gateway will get its load
  balancer through a Kubernetes `Service` of type `LoadBalancer`).
- You know the public hostname the app currently serves on (the one your old Ingress used). We'll call it
  `shop.example.com` below — substitute your real one.

---

## Step 1 — Confirm the Istio ingress gateway is up and find its load balancer

> The Istio ingress gateway = a standalone Envoy that lives at the edge (not a sidecar next to an app). It's
> the single Envoy that *all* inbound internet traffic hits first; it then forwards into the mesh. The
> `default` profile already deployed it; it's exposed by a `Service` of type `LoadBalancer`, which the AWS
> Load Balancer Controller turns into a real AWS load balancer.

> What's happening here: you're just locating the gateway and the AWS address it was given. No changes yet —
> you need this hostname to test against and (later) to point DNS at.

```bash
kubectl -n istio-system get deploy istio-ingressgateway     # want READY 1/1
kubectl -n istio-system get svc  istio-ingressgateway       # type LoadBalancer; note EXTERNAL-IP/hostname
```
Read that back: first command confirms the edge Envoy is running; second shows its `Service`. The
`EXTERNAL-IP` column will show an AWS-generated hostname (e.g. `a1b2…elb.ap-south-1.amazonaws.com`) — that's
your **new** front door. Grab it for testing:
```bash
GW=$(kubectl -n istio-system get svc istio-ingressgateway \
      -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
echo "$GW"
```
If `EXTERNAL-IP` says `<pending>` for more than a minute or two, the Load Balancer Controller didn't
provision it — check `kubectl -n kube-system logs deploy/aws-load-balancer-controller` for access-denied
(an IRSA issue from `2.2`).

---

## Step 2 — Open the door: write the Gateway

> What's happening here: you create a `Gateway` object that tells the ingress gateway Envoy "listen on
> port 80 for host `shop.example.com`." This only opens the listener — it doesn't route anything yet.

Create the file:
```bash
nano shop-gateway.yaml
```
Paste:
```yaml
apiVersion: networking.istio.io/v1
kind: Gateway
metadata:
  name: shop-gateway
  namespace: shop
spec:
  selector:
    istio: ingressgateway          # bind this Gateway to the istio-ingressgateway Envoy (it has label istio=ingressgateway)
  servers:
  - port:
      number: 80
      name: http
      protocol: HTTP
    hosts:
    - "shop.example.com"           # only accept requests for this hostname (use "*" to accept any)
```
Apply it:
```bash
kubectl apply -f shop-gateway.yaml
```
The key line is `selector: istio: ingressgateway`. A Gateway is just *configuration* — `selector` is how it
attaches to the actual edge Envoy from Step 1 (that pod carries the label `istio=ingressgateway`). Without a
matching selector, your Gateway config would have no proxy to apply to. We list a specific `hosts` value so
the gateway only answers for your domain; during early testing you can set it to `"*"` and curl the raw
load-balancer hostname.

---

## Step 3 — Put up the signposts: write the VirtualService

> What's happening here: you create a `VirtualService` that *attaches* to the Gateway from Step 2 and says
> "for host `shop.example.com`, route `/` to the `api-gateway` service." `api-gateway` is the front of your
> checkout chain (frontend → api-gateway → order → payment → inventory), so this is the single entry point.

Create the file:
```bash
nano shop-vs.yaml
```
Paste:
```yaml
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: shop-routes
  namespace: shop
spec:
  hosts:
  - "shop.example.com"             # must match a host the Gateway accepts
  gateways:
  - shop-gateway                   # bind to the Gateway from Step 2 (same namespace, so short name is fine)
  http:
  - match:
    - uri:
        prefix: /                  # everything under "/"
    route:
    - destination:
        host: api-gateway          # the in-cluster Service name (api-gateway.shop.svc.cluster.local)
        port:
          number: 8080             # api-gateway's Service port
```
Apply it:
```bash
kubectl apply -f shop-vs.yaml
```
Read it back: `gateways: [shop-gateway]` is the bolt that joins this routing to the door you opened in
Step 2 — that's what makes these rules apply to *edge* traffic rather than internal traffic. `match` +
`route` is the actual signpost: "URI starting with `/` → send to the `api-gateway` Service on 8080." Replace
`8080` with `api-gateway`'s real Service port if it differs. Because routing now lives in a VirtualService,
adding canary weights or retries later is a small edit to *this* file — no ALB annotations.

---

## Step 4 — Cut traffic over and confirm the new edge serves the app

> What's happening here: you test the full path through the **new** gateway, then (once it works) repoint
> DNS so real users come through it. Test by the raw load-balancer hostname first, faking the Host header so
> the Gateway's host match is satisfied.

```bash
# hit the new gateway's load balancer, pretending to be shop.example.com:
curl -H 'Host: shop.example.com' "http://$GW/"            # should return the app's frontend/home response

# walk the checkout entry to be sure routing reaches api-gateway:
curl -H 'Host: shop.example.com' "http://$GW/healthz"     # api-gateway health, served through the mesh edge
```
If those succeed, flip DNS. The cleanest way: point your `shop.example.com` Route 53 record at the ingress
gateway's load balancer. If you use **ExternalDNS** (from `2.2`), annotate the gateway Service so it manages
the record for you:
```bash
kubectl -n istio-system annotate svc istio-ingressgateway \
  external-dns.alpha.kubernetes.io/hostname=shop.example.com --overwrite
```
That tells ExternalDNS "register `shop.example.com` pointing at this load balancer." Within a minute the DNS
record updates and real traffic starts arriving through Istio. Verify against the real name:
```bash
curl "http://shop.example.com/"          # served through the Istio gateway now, no Host header trick needed
```
If you get a 404 from the gateway, the Host in your request doesn't match the Gateway/VirtualService `hosts`
— recheck both files use the *exact* same hostname. A `503` usually means the VirtualService points at a
`host`/`port` that doesn't exist — confirm `kubectl -n shop get svc api-gateway` and its port.

---

## Step 5 — Retire the old ALB Ingress

> What's happening here: now that the Istio gateway serves real traffic, the old Phase-04 Ingress is dead
> weight — and leaving it up means a second, unmanaged front door (and a second AWS load balancer you're
> paying for). Delete it. The Load Balancer Controller will tear down the ALB it created.

First, double-check you're deleting the right thing (don't guess):
```bash
kubectl -n shop get ingress              # find the old Phase-04 ingress name (e.g. "shop" or "api-gateway")
```
Then delete it:
```bash
kubectl -n shop delete ingress <old-ingress-name>
```
Plain English: "Remove the old Ingress object." The Load Balancer Controller notices the Ingress is gone and
deletes the ALB it had provisioned (the reconcile loop from `2.2`, run in reverse). Confirm the app still
serves — it should, because traffic is already coming through the Istio gateway, not the ALB.

If anything breaks after deletion, you removed the wrong front door or DNS hadn't fully cut over — re-create
the Ingress from your Phase-04 manifest while you recheck Step 4. (This is why we cut over and verified
*before* deleting.)

---

## Verify
- `kubectl -n istio-system get svc istio-ingressgateway` shows a real AWS load-balancer hostname (the new edge).
- `curl http://shop.example.com/` returns the app, served through the Istio gateway, and a checkout works
  end to end (frontend → api-gateway → order → payment → inventory).
- `kubectl -n shop get ingress` is empty (old Ingress gone) and the old ALB no longer exists in the EC2
  console — only the ingress gateway's load balancer remains.
- `istioctl proxy-status` lists `istio-ingressgateway` as `SYNCED`, confirming it received your Gateway +
  VirtualService config.
