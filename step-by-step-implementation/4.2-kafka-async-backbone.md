# 4.2 — Wire the async event backbone (Kafka)

## Goal
By the end of this part, completing a checkout doesn't just return to the user — it also **emits an event**
that three other services react to on their own time. Concretely: `order` PRODUCES an `order.created`
event to Kafka; `inventory`, `notification`, and `recommendation` each CONSUME it independently to
decrement stock, "send" a confirmation, and update recommendations. You'll also run `thumbnail-job` as a
one-shot Kubernetes `Job` to prove the worker path (real autoscaling for it lands in Phase 06 with KEDA).

## Why this part exists (read this first)
In `4.1` every call was **synchronous**: `order` calls `payment`, waits, calls `inventory`, waits. That's
correct for the parts of checkout that must succeed *before* you tell the user "order placed" — you can't
confirm an order if the payment was declined. But three things do **not** need to block the user:
decrementing inventory counters for analytics, sending a confirmation message, and updating
recommendation popularity. If `order` had to synchronously call all three too, then a slow notification
service would make *checkout itself* slow, and a crashed recommendation service would fail orders that
should have succeeded.

The fix is to **decouple** those three from checkout. `order` writes one event and moves on; the three
consumers pick it up whenever they're ready. The datastore for this — the Kafka broker — already exists as
a StatefulSet from `3.1`; this part is purely about wiring producer and consumers on top of it.

> NEW CONCEPT — synchronous vs asynchronous (event-driven). **Synchronous** = "call and wait": the caller
> holds the line until the callee answers, and fails if the callee is down. It's request/response, like a
> phone call. **Asynchronous / event-driven** = "fire and forget": the producer writes a message to a log
> and returns immediately; consumers read it later, on their own schedule. It's like dropping a letter in
> a mailbox — you don't wait at the mailbox for a reply. **Why we use it here:** checkout's *core* (cart →
> payment → inventory reserve) stays synchronous because the user must know the outcome now; the
> *side-effects* (notify, recommend, analytics-decrement) go async so they can't slow down or break
> checkout. **Why it fits vs alternatives:** you could keep everything synchronous and add retries and
> timeouts everywhere, but that couples checkout's reliability to every downstream service. Events
> decouple them — that's the whole point of an event backbone.

## Prerequisites
- [`3.1`](./3.1-datastores.md) — **Kafka** (KRaft mode) running as a StatefulSet, reachable at
  `kafka.data.svc.cluster.local:9092`.
- [`4.1`](./4.1-deploy-the-fleet.md) — `order`, `inventory`, `notification`, `recommendation` all
  deployed and READY. Their ConfigMaps already carry the Kafka keys you set in `4.1`
  (`KAFKA_BROKERS`, `KAFKA_TOPIC=order.created`, and a distinct `KAFKA_GROUP` each). This part confirms and
  proves that wiring; you won't re-create those services.

> NEW CONCEPT — topic, consumer group, offset (the three words that ARE Kafka).
> - A **topic** is a named, append-only log of messages — here `order.created`. Producers append to the
>   end; the log keeps messages for a retention window even after they're read. A topic is split into
>   **partitions** so it can scale and be consumed in parallel.
> - A **consumer group** is a named set of consumers that **share** a topic's partitions. Kafka tracks
>   reading position *per group*. So if `inventory`, `notification`, and `recommendation` use **three
>   different group ids**, each group gets its **own independent copy** of every message — that's how one
>   `order.created` event fans out to all three. Within *one* group, multiple replicas split the
>   partitions between them (that's how a single service scales out).
> - An **offset** is the position of the next message a group will read in a partition. Kafka stores each
>   group's committed offset, so a consumer that restarts resumes exactly where it left off — it doesn't
>   reprocess everything or skip what it missed.
> **Why this fits:** the topic gives durable fan-out, the group ids give per-service independent delivery,
> and offsets give crash-safe resume — exactly the three properties an event backbone needs.

## The mental model before you touch anything
```
                       ┌──────────────────────── Kafka topic: order.created ────────────────────────┐
   checkout (sync):    │  msg ─► msg ─► msg ─► ... (durable append-only log, 3 partitions)           │
   frontend → gateway  └───────┬───────────────────────┬───────────────────────┬───────────────────┘
        → order ──PRODUCES──►  │ group=inventory        │ group=notification    │ group=recommendation
        → payment              ▼                        ▼                       ▼
        → inventory(reserve)  inventory consumer      notification consumer   recommendation consumer
                              (decrement counters)    ("send" confirmation)   (bump popularity)
```
Note `inventory` appears twice on purpose: `order` calls it **synchronously** to *reserve* stock during
checkout (must succeed first), AND it **consumes** `order.created` asynchronously for its analytics
decrement. Same service, two paths — that's a great illustration of when to use each.

## Steps

### Step 1 — Make sure the topic exists
> What's happening here: producers and consumers both reference the topic `order.created`. In dev, Kafka
> can auto-create a topic on first use, but creating it explicitly with the partition count you want is
> cleaner and avoids a 1-partition default that caps your consumer scale-out.

A Kafka topic = the named mailbox everyone agrees to use. Create it by running `kafka-topics` inside the
broker pod:
```bash
kubectl -n data exec -it kafka-0 -- kafka-topics.sh \
  --bootstrap-server localhost:9092 \
  --create --if-not-exists --topic order.created \
  --partitions 3 --replication-factor 1
```
Read this back: you exec into the `kafka-0` pod and ask it to create the `order.created` topic with **3
partitions** (so up to 3 consumers in one group can work in parallel) and **replication-factor 1** (one
copy — fine for a single-broker learning cluster; you'd raise this for HA). `--if-not-exists` makes it
safe to re-run.

What to expect: `Created topic order.created.` (or nothing, if it already existed). List to confirm:
```bash
kubectl -n data exec -it kafka-0 -- kafka-topics.sh --bootstrap-server localhost:9092 --list
```
If `kafka-0` isn't found, check the broker StatefulSet name in `3.1` (it may be `kafka` → pod `kafka-0`).

### Step 2 — Confirm `order` is configured to PRODUCE
> What's happening here: you already gave `order` the Kafka coordinates in `4.1`. Verify they're present
> and that `order`'s readiness gate (which also checks the Kafka writer is initialized) is green.

The producer side = the sender who drops `order.created` letters in the mailbox. Check `order`'s config
and health:
```bash
kubectl -n shop get configmap order -o jsonpath='{.data.KAFKA_BROKERS}{"\n"}{.data.KAFKA_TOPIC}{"\n"}'
kubectl -n shop get pods -l app=order        # READY 1/1 means /readyz passed (DB + Kafka writer ready)
```
You should see `kafka.data.svc.cluster.local:9092` and `order.created`. If `KAFKA_BROKERS` is missing,
patch it and let the deployment restart:
```bash
kubectl -n shop patch configmap order --type merge \
  -p '{"data":{"KAFKA_BROKERS":"kafka.data.svc.cluster.local:9092","KAFKA_TOPIC":"order.created"}}'
kubectl -n shop rollout restart deploy/order
```
What to expect: `order` READY, no Kafka errors in `kubectl -n shop logs deploy/order`. A pod stuck `0/1`
with "kafka" in the logs means the broker DNS name is wrong or Kafka is down.

### Step 3 — Confirm the three CONSUMERS each have a DISTINCT group
> What's happening here: the fan-out only works if `inventory`, `notification`, and `recommendation` use
> **different** `KAFKA_GROUP` values. Same topic, three group ids = each gets its own copy of every event.
> You set these in `4.1`; verify them.

Each consumer = a separate reader holding its own bookmark (offset) in the shared mailbox. Check all
three at once:
```bash
for svc in inventory notification recommendation; do
  echo -n "$svc group = "
  kubectl -n shop get configmap $svc -o jsonpath='{.data.KAFKA_GROUP}{"\n"}'
done
```
You should see exactly:
```
inventory group = inventory
notification group = notification
recommendation group = recommendation
```
If two services accidentally share a group id, they'd **split** the partitions instead of each getting
every message — so one event would go to only one of them. Distinct groups are non-negotiable for
fan-out. Fix a wrong one with the same `patch` + `rollout restart` pattern as Step 2.

> Why distinct groups give fan-out, in one line: Kafka delivers each message **once per consumer group**.
> Three groups → three independent deliveries of the same event. Replicas *inside* one group share the
> work (load-balance partitions); that's how, later, you scale `inventory` to several pods without it
> double-processing.

### Step 4 — Prove the fan-out end to end
> What's happening here: you place a real order through the public gateway, then confirm all three
> consumers reacted — inventory stock dropped, a notification appeared, recommendations updated. One
> produced event, three independent effects.

Place an order (reuse the login flow from `4.1` to get `$TOKEN` and `$GW`):
```bash
GW=$(kubectl -n shop get ingress api-gateway -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
# ... obtain $TOKEN via /api/auth/login as in 4.1, add an item to cart, then:
curl -s -X POST http://$GW/api/orders -H "Authorization: Bearer $TOKEN" \
     -H 'Content-Type: application/json' -d '{}'
```
Now watch each consumer prove it received the event:
```bash
# notification buffered a confirmation for the order
kubectl -n shop logs deploy/notification | grep -i order.created | tail -3
# inventory consumed and processed the event (events_consumed_total ticked up)
kubectl -n shop logs deploy/inventory   | grep -i order.created | tail -3
# recommendation bumped popularity from the event
kubectl -n shop logs deploy/recommendation | grep -i order.created | tail -3
```
What to expect: each of the three logs shows it consumed the same `order.created` event. That's the
fan-out — one produce, three independent consumes. If only one reacted, you almost certainly have two
services sharing a `KAFKA_GROUP` (re-do Step 3).

You can also watch the groups and their lag directly from the broker:
```bash
kubectl -n data exec -it kafka-0 -- kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --all-groups
```
This prints each group's `CURRENT-OFFSET`, `LOG-END-OFFSET`, and `LAG`. Right after an order, lag should
briefly rise then return to 0 as each group catches up. **Lag** is the single most important async health
metric — it's how far behind a consumer group is — and it's exactly what KEDA will autoscale on in
Phase 06.

### Step 5 — Run `thumbnail-job` as a one-shot Kubernetes `Job` (for now)
> What's happening here: `thumbnail-job` is a pure worker — it consumes from `thumbnail.requests` and has
> no HTTP traffic. Eventually KEDA will scale it from zero on Kafka lag (Phase 06). To prove the worker
> image runs and drains messages today, you run it as a plain `Job`: a pod that does work and finishes.

A Kubernetes **Job** = a task that runs to completion and then stops (unlike a Deployment, which keeps
pods running forever). Create `thumbnail-job.yaml`:
```bash
nano thumbnail-job.yaml
```
```yaml
apiVersion: batch/v1
kind: Job
metadata: { name: thumbnail-job, namespace: shop }
spec:
  backoffLimit: 2                 # retry the pod up to 2 times if it errors
  template:
    metadata: { labels: { app: thumbnail-job } }
    spec:
      restartPolicy: Never        # a Job pod that exits is "done", not restarted in place
      containers:
      - name: thumbnail-job
        image: 169424082295.dkr.ecr.ap-south-1.amazonaws.com/ecom-repo:thumbnail-job-<sha>
        env:
        - { name: KAFKA_BROKERS, value: kafka.data.svc.cluster.local:9092 }
        - { name: KAFKA_TOPIC,   value: thumbnail.requests }
        - { name: KAFKA_GROUP,   value: thumbnail }
        - { name: LOG_LEVEL,     value: info }
        - { name: METRICS_PORT,  value: "9100" }
        resources:
          requests: { cpu: 50m,  memory: 96Mi }
          limits:   { cpu: 250m, memory: 192Mi }
```
Read the key fields: `kind: Job` + `restartPolicy: Never` + `backoffLimit: 2` means "run this pod to
completion; if it fails, retry up to twice, then give up." The env here is inline (not a ConfigMap)
because it's a throwaway proof; the worker pulls work only from Kafka, so there's no Service and no port
to expose. `KAFKA_GROUP=thumbnail` must match the consumer group KEDA will later target.

Apply and watch it process, then finish:
```bash
kubectl apply -f thumbnail-job.yaml
kubectl -n shop logs -f job/thumbnail-job      # follow it draining thumbnail.requests
kubectl -n shop get job thumbnail-job          # COMPLETIONS goes 0/1 -> 1/1 when it's done
```
What to expect: the pod consumes any pending `thumbnail.requests` messages, logs
`thumbnails_processed_total`, and the Job shows `COMPLETIONS 1/1`. If it hangs, it's waiting on Kafka —
confirm the broker is reachable. Clean up with `kubectl -n shop delete job thumbnail-job`.

> Why a Job now and KEDA later: a `Job` is perfect for proving the worker image runs and drains a queue,
> but it runs once and stops — it won't wake up when new thumbnail requests arrive. In Phase 06 you'll
> replace it with a Deployment + KEDA `ScaledObject` that watches `thumbnail.requests` lag and scales the
> worker from **0** to N pods on demand. Same container image, smarter lifecycle.

## Verify
- `kubectl -n data exec -it kafka-0 -- kafka-topics.sh --bootstrap-server localhost:9092 --list` includes
  `order.created`.
- After placing one order, all three of `inventory`, `notification`, `recommendation` show they consumed
  the **same** `order.created` event in their logs — that's confirmed fan-out via three distinct groups.
- `kafka-consumer-groups.sh --describe --all-groups` lists `inventory`, `notification`, `recommendation`
  (and `thumbnail` while the Job ran), each with its own offsets and LAG that returns to 0.
- The `thumbnail-job` Job reached `COMPLETIONS 1/1`.

## Concept deep-dive — synchronous request/response vs asynchronous events (and when to use each)
The checkout path uses **both** patterns on purpose, and knowing which to reach for is the senior skill:

```
   SYNCHRONOUS (must answer NOW, caller waits, failure = visible to user):
      frontend → api-gateway → order → payment → inventory(reserve)
      use when: the user needs the result to proceed, and a failure must stop the flow.

   ASYNCHRONOUS (side-effects, fire-and-forget, failure is isolated):
      order ──order.created──► [inventory analytics] [notification] [recommendation]
      use when: the work can happen "soon," and its failure must NOT fail the user's request.
```

- **Synchronous** gives you an immediate answer and a clear success/failure to show the user. The cost:
  the caller's latency and reliability are the *sum* of everything it waits on, and a downstream outage
  propagates straight back to the user. So you reserve it for the steps that genuinely gate the response —
  you can't confirm an order whose payment was declined.
- **Asynchronous** gives you decoupling: `order` returns the instant it writes the event, so checkout
  latency doesn't include notification or recommendation work, and if `recommendation` is down the event
  simply waits in the topic until it's back — no failed orders, no lost events (Kafka retains them, and
  the group's offset resumes on recovery). The cost: **eventual** consistency — for a moment after
  checkout, the confirmation hasn't been sent and recommendations haven't updated. That's fine for
  side-effects; it would be wrong for "was the payment approved?"

The rule of thumb: **if the user must see the outcome to proceed, call it synchronously; if it's a
side-effect that can lag and must not break the request, emit an event.** Kafka makes the async side
durable (events survive consumer restarts) and fan-out-friendly (one event, many independent groups).
*Interview line: "We keep the user-facing critical path synchronous so failures are immediate and
visible, and push side-effects onto a Kafka topic so a slow or down consumer degrades a feature instead
of failing checkout — durable events plus per-group offsets give us crash-safe fan-out."*
