# 4.2 — Wire the async event backbone (Kafka)

## Goal
Completing a checkout doesn't just return to the user — it also **emits an event**. `order` PRODUCES an
`order.created` event to Kafka; `inventory` CONSUMES it independently to commit the stock reservation
(reserved → sold). In the trimmed build `inventory` is the one consumer — but the whole point of an event
backbone is that you can add more consumers later **without touching the producer**.

## Why this part exists (read this first)
In `4.1` the checkout call was **synchronous**: `order` calls `inventory` to reserve stock and waits —
correct, because the user must know "order placed" succeeded. But the *follow-on* work (committing the
reservation; in a fuller system also notifications, recommendations, analytics) does **not** need to block
the user. If `order` had to do all of it synchronously, a slow downstream would make *checkout itself*
slow, and a crashed one would fail orders that should have succeeded.

The fix is to **decouple** that follow-on work. `order` writes one event and moves on; consumers pick it up
when they're ready. The Kafka broker already exists as a StatefulSet from `3.1`; this part wires producer +
consumer on top.

> NEW CONCEPT — synchronous vs asynchronous (event-driven). **Synchronous** = "call and wait": the caller
> holds the line until the callee answers, and fails if the callee is down — request/response, like a
> phone call. **Asynchronous / event-driven** = "fire and forget": the producer writes a message to a log
> and returns immediately; consumers read it later, on their own schedule — like dropping a letter in a
> mailbox. **Why we use it here:** checkout's *core* (reserve inventory) stays synchronous because the user
> must know the outcome now; the *follow-on* work goes async so it can't slow down or break checkout.
> **Why it fits vs alternatives:** keeping everything synchronous couples checkout's reliability to every
> downstream service; events decouple them — that's the whole point of an event backbone.

## Prerequisites
- [`3.1`](./3.1-datastores.md) — **Kafka** (KRaft mode) running as a StatefulSet, reachable at
  `kafka.data.svc.cluster.local:9092`.
- [`4.1`](./4.1-deploy-the-fleet.md) — `order` and `inventory` deployed and READY. Their ConfigMaps carry
  the Kafka keys you set in `4.1` (`KAFKA_BROKERS`, `KAFKA_TOPIC=order.created`, and `inventory`'s
  `KAFKA_GROUP=inventory`). This part confirms and proves that wiring.

> NEW CONCEPT — topic, consumer group, offset (the three words that ARE Kafka).
> - A **topic** is a named, append-only log of messages — here `order.created`. Producers append to the
>   end; the log keeps messages for a retention window even after they're read, split into **partitions**
>   so it can be consumed in parallel.
> - A **consumer group** is a named set of consumers that **share** a topic's partitions. Kafka tracks
>   reading position **per group**. `inventory`'s group gets every message; add a *second* group id later
>   and it gets its **own independent copy** of every message — that's how you'd fan out to more consumers
>   **without changing the producer**. Within *one* group, replicas split the partitions between them
>   (that's how a single service scales out).
> - An **offset** is the position of the next message a group will read. Kafka stores each group's
>   committed offset, so a consumer that restarts resumes exactly where it left off.
> **Why this fits:** the topic gives durable delivery, group ids give per-consumer independent delivery,
> and offsets give crash-safe resume — exactly what an event backbone needs.

## The mental model before you touch anything
```
   checkout (sync):       ┌──────── Kafka topic: order.created (durable append-only log) ────────┐
   frontend → gateway     │  msg ─► msg ─► msg ─► ...  (3 partitions)                              │
        → order ─PRODUCES─►└────────────────────┬───────────────────────────────────────────────┘
        → inventory(reserve)                    │ group=inventory
                                                ▼
                                          inventory consumer (commit the reservation)
   (add another group id later → its own independent copy of every event = fan-out, no producer change)
```
`inventory` appears twice on purpose: `order` calls it **synchronously** to *reserve* stock during checkout
(must succeed first), AND it **consumes** `order.created` asynchronously to *commit* the reservation. Same
service, two paths — a great illustration of when to use each.

## Steps

### Step 1 — Make sure the topic exists
> What's happening here: producer and consumer both reference the topic `order.created`. Kafka can
> auto-create it on first use, but creating it explicitly with the partition count you want is cleaner and
> avoids a 1-partition default that caps consumer scale-out.

```bash
kubectl -n data exec -it kafka-0 -- kafka-topics.sh \
  --bootstrap-server localhost:9092 \
  --create --if-not-exists --topic order.created \
  --partitions 3 --replication-factor 1
```
This creates `order.created` with **3 partitions** (so a group can run up to 3 consumers in parallel) and
**replication-factor 1** (one copy — fine for a single-broker learning cluster; raise it for HA).
`--if-not-exists` makes it safe to re-run. Confirm: `kubectl -n data exec -it kafka-0 -- kafka-topics.sh
--bootstrap-server localhost:9092 --list`. If `kafka-0` isn't found, check the broker StatefulSet name
from `3.1`.

### Step 2 — Confirm `order` is configured to PRODUCE
> What's happening here: you gave `order` the Kafka coordinates in `4.1`. Verify they're present and that
> `order`'s readiness gate (which checks the Kafka writer is initialized) is green.

```bash
kubectl -n shop get configmap order -o jsonpath='{.data.KAFKA_BROKERS}{"\n"}{.data.KAFKA_TOPIC}{"\n"}'
kubectl -n shop get pods -l app=order        # READY 1/1 means /readyz passed (DB + Kafka writer ready)
```
You should see `kafka.data.svc.cluster.local:9092` and `order.created`. If `KAFKA_BROKERS` is missing,
patch it and restart:
```bash
kubectl -n shop patch configmap order --type merge \
  -p '{"data":{"KAFKA_BROKERS":"kafka.data.svc.cluster.local:9092","KAFKA_TOPIC":"order.created"}}'
kubectl -n shop rollout restart deploy/order
```

### Step 3 — Confirm `inventory` consumes with its group
> What's happening here: `inventory` reads `order.created` using `KAFKA_GROUP=inventory` (set in `4.1`).
> Verify it, and remember: any *additional* consumer you add later must use a **different** group id so it
> gets its own copy of every event (same id = they'd split the work instead of each seeing everything).

```bash
kubectl -n shop get configmap inventory -o jsonpath='{.data.KAFKA_GROUP}{"\n"}'   # -> inventory
kubectl -n shop get pods -l app=inventory      # READY 1/1 (the consumer is connected)
```

### Step 4 — Prove it end to end
> Place a real order through the public gateway, then confirm `inventory` consumed the event.

```bash
GW=$(kubectl -n shop get ingress api-gateway -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
# obtain $TOKEN via /api/auth/login as in 4.1, then place an order (items are sent directly):
curl -s -X POST http://$GW/api/orders -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"user_id":1,"items":[{"product_id":1,"name":"Coffee Mug","price_cents":1299,"quantity":2}]}'

# inventory consumed and committed the reservation:
kubectl -n shop logs deploy/inventory | grep -i order.created | tail -3
```
Watch the group's lag directly from the broker:
```bash
kubectl -n data exec -it kafka-0 -- kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --all-groups
```
This prints each group's `CURRENT-OFFSET`, `LOG-END-OFFSET`, and `LAG`. Right after an order, lag briefly
rises then returns to 0 as `inventory` catches up. **Lag** is the single most important async health metric
— how far behind a consumer group is — and it's exactly what KEDA autoscales the `inventory` consumer on
in Phase 06.

## Verify
- `order` produces `order.created` on checkout; `inventory` consumes it (its log shows the event; lag
  returns to 0).
- The two are genuinely **decoupled** — prove it: `kubectl -n shop scale deploy/inventory --replicas=0`,
  place an order (it still succeeds; the event waits in the durable log), then scale `inventory` back up and
  it catches up from its committed offset. That replay-from-offset durability is the whole value of the
  event backbone.
