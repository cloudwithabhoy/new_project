# 03 — Install AWS CLI, kubectl, eksctl

## Goal
Install the command-line tools on the EC2 instance to talk to AWS and Kubernetes, and to create/manage the
EKS cluster.

## Why
- **AWS CLI** — authenticate to AWS; manage ECR/EKS.
- **kubectl** — the Kubernetes client (talk to the cluster once it exists).
- **eksctl** — the simplest way to create/manage an EKS cluster (it orchestrates the VPC, IAM roles,
  and CloudFormation stacks under the hood).

## Prerequisites
- The EC2 instance from `01` with internet access.
- The **`eks-user`** access keys (broad EC2/EKS/IAM/CloudFormation perms — eksctl needs them).

## Steps

### 1. AWS CLI v2
```bash
curl "https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip" -o "awscliv2.zip"
sudo apt install unzip -y
unzip awscliv2.zip
sudo ./aws/install
aws --version
```

### 2. Configure credentials
```bash
aws configure
# AWS Access Key ID     : <eks-user key>
# AWS Secret Access Key : <eks-user secret>
# Default region name   : ap-south-1
# Default output format  : json
```
> These are the **eks-user** keys (broad, cluster-admin perms) used to *create* the cluster. They are
> **separate** from the Jenkins `aws-ecr` credential (which only needs ECR push).

### 3. kubectl — install a CURRENT version (match the cluster)
```bash
curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
chmod +x ./kubectl
sudo mv ./kubectl /usr/local/bin/
kubectl version --client
```
> We first installed **kubectl 1.19.6** (from a 2021 URL). That's far older than the EKS cluster
> (~1.30) and unsupported — kubectl must be within **±1 minor** of the cluster. Use the `stable.txt`
> install above. (Also: `--short` was removed from newer kubectl, so just use `kubectl version --client`.)

### 4. eksctl
```bash
curl --silent --location \
  "https://github.com/weaveworks/eksctl/releases/latest/download/eksctl_$(uname -s)_amd64.tar.gz" \
  | tar xz -C /tmp
sudo mv /tmp/eksctl /usr/local/bin
eksctl version
```

## Gotchas
- **Old kubectl (1.19.6)** → version skew with a modern cluster (weird/blocked commands). Always
  install a current kubectl.
- **`aws configure` uses the eks-user keys** here (cluster admin), not the Jenkins ECR credential —
  keep the two identities distinct.

## Verify
```bash
aws sts get-caller-identity     # confirms which IAM identity is active (should be eks-user)
kubectl version --client
eksctl version
```

## Concept deep-dive — how eksctl & kubeconfig work

**eksctl = intent → CloudFormation.** You describe a cluster (flags or a YAML config) and eksctl **generates
CloudFormation templates** and creates/manages the stacks. One `eksctl create cluster` builds a **VPC**
(subnets, route tables, IGW/NAT), the **EKS control plane**, **IAM roles** (cluster + node + OIDC), and the
**node group** (an Auto Scaling Group). That's why `eks-user` needs EC2 + IAM + CloudFormation + EKS perms (`00`).

**Communication.**
```
eksctl ──> CloudFormation API   (create/describe stacks) ──> provisions VPC + EKS + IAM + ASG
eksctl ──> EKS API              (eks:CreateCluster, ...)
eksctl ──> writes ~/.kube/config (calls eks:DescribeCluster for the endpoint + CA)
```

**kubeconfig / context — how kubectl authenticates.** `aws eks update-kubeconfig` writes a **context**
(cluster endpoint + CA + which credentials). It stores **no password** — it configures an **exec plugin**:
every `kubectl` call runs `aws eks get-token`, which calls **STS** for a short-lived token the EKS API server
verifies. So `kubectl`'s identity == your AWS identity (`eks-user`).
```
kubectl --> [exec: aws eks get-token --> STS] --> bearer token --> EKS API server
```

**Why eksctl fits.** It does the undifferentiated heavy lifting (VPC/IAM/OIDC wiring) in a couple of commands
— ideal for a correct cluster fast. **Why not:** raw **CloudFormation/CLI** = full control but lots of YAML;
**Terraform** = the production IaC choice (declarative, drift detection) but more upfront setup; **console** =
not reproducible. eksctl is the pragmatic middle for learning + small setups.
