# 6.2 — Disruption protection (PodDisruptionBudgets · topology spread · anti-affinity)

## Goal
In `6.1` you made pods come and go automatically. But pods also get **taken away** for reasons that have
nothing to do with load: a node drains for an upgrade, Karpenter consolidates two half-empty nodes into
one, an AZ has a bad afternoon. Right now, any of those can briefly take **all** of a service's pods down
at once. In this part you put guardrails on those events — so that no matter who's draining what, a
minimum number of `catalog`/`api-gateway`/`search` pods stays alive, and your replicas are physically
spread across both `ap-south-1a` and `ap-south-1b` so one AZ can never take you fully offline.

## Why this part exists (read this first)
`6.1` controls scaling — replicas going **up and down on purpose**. This part controls **disruption** —
replicas going down *not because you asked*, but because the platform underneath them moved. Those are
different threats and need different tools.

Here's the gap. Karpenter (`2.2`) is constantly *consolidating*: it loves to drain a lightly-used node and
move its pods elsewhere to save money. EKS node upgrades drain nodes too. Both are healthy, normal
operations — but with no protection, "drain this node" can mean "delete the only 2 `catalog` pods at the
same instant," and for a few seconds `catalog` serves nothing. Worse, if your 2 replicas happen to have
landed on the **same node** or in the **same AZ**, a single failure takes the whole service down.

Two tools fix this, and they're complementary:
- A **PodDisruptionBudget** = a "you may not take more than this many of my pods down at once" sign that
  voluntary operations (drains, consolidation) are forced to obey.
- **Topology spread + anti-affinity** = rules that make the scheduler *place* your replicas on different
  nodes and different AZs in the first place — so there's something left when one falls over.

> NEW CONCEPT — voluntary vs involuntary disruption, and what a PDB actually protects.
> A pod can die two ways. **Involuntary**: a node's hardware fails, the kernel OOM-kills it, an AZ loses
> power — *nobody chose this*, and **no PDB can stop it**. **Voluntary**: a human or controller
> *deliberately* evicts a pod — `kubectl drain`, a node upgrade, Karpenter consolidation, a rolling node
> roll. A **PodDisruptionBudget** governs **only the voluntary kind**: it tells the eviction API "you are
> allowed to evict my pods, but never let fewer than N stay available — block the eviction and wait if
> it would breach that." So a PDB doesn't make pods immortal; it makes *planned* operations polite. The
> defense against *involuntary* loss is having replicas spread across nodes/AZs in the first place — which
> is the next tool.

## Before you start
Run from the machine whose `kubectl` talks to `ecom-cluster`:
```bash
kubectl config current-context     # ecom-cluster / ap-south-1
kubectl get nodes -L topology.kubernetes.io/zone   # see which AZ each node is in (1a / 1b)
```
That last `-L` flag prints each node's **zone label** — `ap-south-1a` or `ap-south-1b`. You'll use that
exact label key for spreading. Account `169424082295`, region `ap-south-1`, namespace `shop`.

## Step 1 — Put a PodDisruptionBudget on the critical services

> A PDB = a sign on the door that reads "at least 2 of us must be working at all times — if your
> maintenance would drop us below that, wait." Drains and Karpenter read that sign and obey it.

> What's happening here: you declare, per service, the **minimum number of pods that must stay Available**
> during any voluntary disruption. The eviction API enforces it: if draining a node would breach the
> budget, the eviction is **refused** until enough replacements are Ready elsewhere. You write one PDB per
> critical service; the `selector` matches the same `app:` label as the Deployment.

Make `catalog`'s PDB (repeat for `api-gateway` and `search`, changing name + selector):
```bash
nano catalog-pdb.yaml
```
```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: catalog, namespace: shop }
spec:
  minAvailable: 2                     # never let voluntary disruption drop catalog below 2 Ready pods
  selector:
    matchLabels: { app: catalog }     # applies to the pods labelled app=catalog
```
```bash
kubectl apply -f catalog-pdb.yaml
kubectl -n shop get pdb
```
Read it back: "for pods labelled `app=catalog`, at least **2** must remain Available; the eviction API
must refuse any voluntary eviction that would drop below that." The `get pdb` output shows
`ALLOWED DISRUPTIONS` — how many pods may be evicted *right now* without breaching. If your HPA min is 2
and `minAvailable` is 2, that column shows `0`: nothing can be voluntarily evicted until a new pod comes
up first. That's the protection working.

> Why `minAvailable: 2` and not `maxUnavailable: 1`? Two ways to say a similar thing. `minAvailable: 2`
> is an **absolute floor** — robust even if the HPA scales you to 10 (still guarantees 2). `maxUnavailable`
> is relative to current replicas. For a floor you can reason about during an incident, the absolute form
> is the senior default. **Do not** set `minAvailable` equal to your *max* replicas — that would mean "no
> pod may ever be evicted," and node drains would hang forever.

## Step 2 — Spread replicas across both AZs (topology spread constraints)

> NEW CONCEPT — topology spread & pod anti-affinity.
> By default the scheduler is free to pack all your `catalog` replicas onto one node in one AZ if that's
> convenient. **Topology spread constraints** flip that: they tell the scheduler "distribute these pods
> *evenly* across a topology key — say, one per AZ — and treat lopsidedness as a scheduling penalty."
> **Pod anti-affinity** is the blunter cousin: "never put two of these on the same *node*." You use them
> together: spread keeps you balanced across **AZs** (survives an AZ outage), anti-affinity keeps you off
> the same **node** (survives a single node failure). Together they guarantee that no single node or AZ
> holds enough of your service to take it down.

> What's happening here: you add a `topologySpreadConstraints` block (spread across AZ) and a
> `podAntiAffinity` block (avoid same node) to the Deployment's pod template. These only affect **where new
> pods get placed** — so you re-apply the Deployment and let a rollout reschedule the pods.

Edit `catalog.yaml` and add this inside `spec.template.spec` (alongside `containers:`):
```yaml
      topologySpreadConstraints:
      - maxSkew: 1                                     # AZs may differ by at most 1 pod
        topologyKey: topology.kubernetes.io/zone       # the AZ label (ap-south-1a / 1b)
        whenUnsatisfiable: ScheduleAnyway              # prefer spread, but don't leave pods Pending over it
        labelSelector: { matchLabels: { app: catalog } }
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 100
            podAffinityTerm:
              topologyKey: kubernetes.io/hostname      # "hostname" = one node; prefer different nodes
              labelSelector: { matchLabels: { app: catalog } }
```
Re-apply and watch it rebalance:
```bash
kubectl apply -f catalog.yaml
kubectl -n shop rollout status deploy/catalog
kubectl -n shop get pods -l app=catalog -o wide   # check the NODE column spans 2 nodes / 2 AZs
```
Read the key flags:
- `maxSkew: 1` + `topologyKey: ...zone` = "the count of `catalog` pods per AZ may differ by at most 1,"
  i.e. with 2 replicas you get one in `1a` and one in `1b`.
- `whenUnsatisfiable: ScheduleAnyway` is a deliberate softness — if perfect spread is impossible (one AZ
  is full), still schedule the pod rather than leave it `Pending`. Use `DoNotSchedule` only if you'd
  genuinely rather run fewer pods than break the spread (rarely what you want for availability).
- The anti-affinity is `preferred...` (soft), not `required...` (hard), for the same reason: a *preference*
  to land on different nodes that degrades gracefully, instead of a hard rule that can wedge a rollout if
  you have more replicas than nodes.

In the `-o wide` output, confirm the two pods sit on **different nodes** and that those nodes are in
**different AZs** (cross-reference the node list from "Before you start"). If both pods are on one node,
your anti-affinity didn't take — check the `labelSelector` matches the pod label exactly.

## Step 3 — Prove it: drain a node and watch the PDB hold the line

> What's happening here: you simulate exactly the operation that used to be dangerous — draining a node —
> and watch the PDB refuse to let `catalog` drop below 2 Ready. This is the same eviction path Karpenter
> consolidation and EKS upgrades use, so passing this means you're protected against all of them.

Pick a node that hosts a `catalog` pod, then drain it:
```bash
kubectl get pods -n shop -l app=catalog -o wide          # note a NODE name running catalog
kubectl drain <that-node> --ignore-daemonsets --delete-emptydir-data
```
Watch in another terminal:
```bash
kubectl -n shop get pods -l app=catalog -w
```
What to expect: the drain evicts the `catalog` pod on that node, but **only after** a replacement is Ready
elsewhere — because `minAvailable: 2` forbids dropping to 1. You'll see a new pod go Ready *before* (or as)
the old one terminates; available count never dips below 2. The drain command may pause for a few seconds
saying it's waiting on the disruption budget — **that pause is the PDB doing its job.** When done, bring the
node back:
```bash
kubectl uncordon <that-node>
```
If instead the drain had **deleted both pods at once** and `catalog` went to 0/2, your PDB selector
doesn't match the pods — fix the `matchLabels` and retry.

## Verify (the part is done when…)
- `kubectl -n shop get pdb` lists `catalog`/`api-gateway`/`search`, each with the expected
  `ALLOWED DISRUPTIONS`.
- `kubectl -n shop get pods -l app=catalog -o wide` shows replicas on **different nodes in different AZs**
  (`ap-south-1a` and `ap-south-1b`).
- A `kubectl drain` of a node hosting `catalog` never drops it below 2 Ready — the eviction waits for a
  replacement first.
