# 7.2 — Logs & traces (Loki · Promtail/Alloy · Tempo · OpenTelemetry Collector)

## Goal
After `7.1` you can *count* things — request rate, error rate, p95 latency. But when checkout's error rate
spikes, a count won't tell you *which* request failed or *why*. In this part you install **Loki** (to store
and search your apps' log lines) and **Tempo** fed by an **OpenTelemetry Collector** (to store the
distributed traces your services already emit), then prove the payoff: from a slow checkout you can jump to
that exact request's logs **and** its trace, linked by a shared `trace_id`.

## Why this part exists (read this first)
Metrics from `7.1` are aggregates. "p95 latency is 2 seconds" tells you *something* is slow, but a graph can't
tell you that the slowness is one specific checkout that stalled waiting on the `payment` service. To answer
*which* and *why*, you need the other two pillars: the **log lines** that request wrote, and the **trace**
that shows its journey across services. And critically, you need them **stitched to the metric** so you can
travel from a spike to the offending request in a couple of clicks.

Your apps are already doing their half of the work (from earlier phases): they write **JSON logs**, they
emit **spans**, and they propagate **W3C trace headers** so a request keeps the same identity as it hops from
`checkout` to `cart` to `payment`. What's missing is the infrastructure to *collect and store* logs and
traces — and that's what you build now.

Three new programs, each with a one-line job:

- **Promtail / Grafana Alloy** = the log courier. An agent on every node that tails each pod's stdout and
  ships those lines to Loki. (Alloy is the newer, more capable courier; Promtail is the simple classic. Same
  job.)
- **Loki** = the log warehouse. Like Prometheus, but for log *lines* instead of numbers — it indexes by
  labels (namespace, pod, app) so you can query "all of checkout's logs in the last 10 minutes" cheaply.
- **Tempo** = the trace warehouse. Stores whole traces, retrievable by `trace_id`.
- **OpenTelemetry (OTel) Collector** = the trace switchboard. Your apps send their spans here; it batches,
  processes, and forwards them to Tempo. One place all telemetry flows through.

> NEW CONCEPT — the three pillars, and how `trace_id` is the thread that ties them. Observability rests on
> three kinds of signal:
> - **Metrics** (from `7.1`) — cheap aggregate numbers over time. "How many? How slow?"
> - **Logs** — discrete timestamped text/JSON events. "What exactly happened, in words?"
> - **Traces** — the path of a single request across services, as a tree of timed **spans**. "Where did the
>   time go, and which hop failed?"
> Alone, each is half-blind: a metric spike has no detail, a log line has no context of the larger request, a
> trace has no body text. The magic is a single shared id — the **`trace_id`** — stamped onto the request at
> the edge and carried into every log line and every span. Because your apps log their `trace_id` and tag
> spans with the same one, you can stand on any pillar and jump to the others: see a slow trace → pull its
> logs; see an error log → open its trace. That correlation is the entire point of this part.

## Before you start — where you run these commands
Run from the machine where `kubectl` talks to `ecom-cluster`. You should already have the `monitoring`
namespace and Grafana from `7.1`:
```bash
kubectl -n monitoring get pods            # Prometheus + Grafana from 7.1 should be Running
helm version                              # Helm 3.x
```
We'll add Loki, Tempo, and the OTel Collector into the same `monitoring` namespace, and wire all three into
the Grafana you already have. Constants: region `ap-south-1`, app namespaces `shop`/`data`.

## Step 1 — Install Loki + the log courier (loki-stack)

> Loki = a warehouse that stores log lines indexed by label, not by full text — so it's cheap. Promtail/Alloy
> = the courier on every node that tails pod logs and ships them to Loki.

> NEW CONCEPT — structured (JSON) logs, and why they matter here. A plain log line is
> `payment failed for order 1234`. A **structured** log line is JSON:
> `{"level":"error","msg":"payment failed","order_id":"1234","trace_id":"abc123","ts":"..."}`. Same words,
> but now every field is a real key. That lets Loki (and you) filter by `level="error"` or — the key one —
> pull every line where `trace_id="abc123"` without fragile text matching. Your apps already emit JSON logs,
> so this just works; the lesson is *why* it was worth doing: JSON logs are what make log↔trace correlation
> possible.

### Step 1 — Install loki-stack with Helm
> What's happening here: one chart installs Loki (the store) plus Promtail (the courier) as a DaemonSet, so
> every node automatically ships its pods' logs.

```bash
helm repo add grafana https://grafana.github.io/helm-charts
helm repo update

helm install loki grafana/loki-stack \
  -n monitoring \
  --set promtail.enabled=true \
  --set loki.persistence.enabled=true \
  --set loki.persistence.size=10Gi
```
Read it back: install Loki, turn on Promtail (the per-node courier), and give Loki a 10Gi persistent disk so
logs survive a restart. Promtail comes up as a **DaemonSet** — one pod per node — because logs live on each
node and the courier has to be where the logs are.

What to expect:
```bash
kubectl -n monitoring get pods | grep -E 'loki|promtail'
```
One `loki-0` and one `promtail-*` per node, all `Running`. If Promtail is `CrashLoopBackOff`, it's usually a
permissions issue reading `/var/log` — the chart's defaults handle it, so check you didn't override the
DaemonSet's volume mounts.

> Prefer **Grafana Alloy** over Promtail? Alloy is the newer agent (Promtail is being phased toward it).
> Swap the chart for `grafana/alloy` and point its `loki.write` component at Loki. Functionally identical for
> our purpose — tail pod logs, ship to Loki — so Promtail is fine to learn on.

### Step 1b — Point Grafana at Loki
The kube-prometheus-stack already gave Grafana a Prometheus data source. Add Loki too. In-cluster, Loki's
address is `http://loki.monitoring.svc.cluster.local:3100`. In Grafana: **Connections → Data sources → Add →
Loki**, URL that address, **Save & test**.

Now query logs in Grafana's **Explore** view with **LogQL** (Loki's query language — it deliberately looks
like PromQL):
```logql
{namespace="shop", app="checkout"} | json | level="error"
```
Read it: "all logs from checkout pods in `shop`, parse each line as JSON, keep only `level=error`." The
`| json` is what unlocks your structured fields. You should see real error lines, each with a `trace_id`
field — remember that field; it's the bridge to Step 3.

## Step 2 — Install the OTel Collector (the trace switchboard)

> OTel Collector = a switchboard all your telemetry flows through. Apps send spans to it; it batches and
> forwards them to a backend (Tempo). One hop you control, so you can change backends without touching apps.

> NEW CONCEPT — spans and a trace. A **span** is one timed unit of work: "checkout handled POST /checkout,
> 1.8s." It has a start, a duration, a name, attributes, and a status (ok/error). A **trace** is a *tree* of
> spans for one request: checkout's span is the parent; the call it made to `cart` is a child span; cart's
> call to its database is a grandchild. Every span in the tree shares the same `trace_id`; each also has a
> `span_id` and points at its parent. Drawn on a timeline, the trace shows you exactly where the 1.8s went —
> "1.6s of it was waiting on payment." Your apps already create these and pass the W3C `traceparent` header
> between services so the tree stays connected across the network.

> NEW CONCEPT — what the OTel Collector is *for* (why not send straight to Tempo?). You *could* point each
> app directly at Tempo. The Collector sits in the middle on purpose: it's a vendor-neutral pipe with three
> stages — **receivers** (accept spans, e.g. over OTLP), **processors** (batch them, drop noise, add cluster
> metadata), and **exporters** (forward to Tempo today, or Jaeger/a SaaS tomorrow). So apps speak one
> standard protocol (OTLP) to one stable address, and you change *where* traces go by editing the
> Collector, not redeploying 6 services. That decoupling is the whole reason it exists.

### Step 2 — Install Tempo (the trace store)
> What's happening here: install Tempo first so there's somewhere for traces to land.

```bash
helm install tempo grafana/tempo -n monitoring
```
This brings up a single Tempo instance that accepts traces over OTLP and stores them retrievable by
`trace_id`. Check `kubectl -n monitoring get pods | grep tempo` → `Running`. (For real volume you'd use the
`tempo-distributed` chart and object storage; single-binary Tempo is right for learning.)

### Step 2b — Install the OTel Collector and point it at Tempo
> What's happening here: install the Collector as a Deployment, configure it to receive OTLP spans from your
> apps and export them to Tempo.

```bash
helm repo add open-telemetry https://open-telemetry.github.io/opentelemetry-helm-charts
helm repo update
```
Create `otel-values.yaml` with `nano otel-values.yaml`, paste:
```yaml
mode: deployment
config:
  receivers:
    otlp:
      protocols:
        grpc: { endpoint: 0.0.0.0:4317 }   # apps send spans here (OTLP/gRPC)
        http: { endpoint: 0.0.0.0:4318 }
  processors:
    batch: {}                              # group spans before forwarding (efficiency)
  exporters:
    otlp:
      endpoint: tempo.monitoring.svc.cluster.local:4317   # forward to Tempo
      tls: { insecure: true }
  service:
    pipelines:
      traces:
        receivers:  [otlp]
        processors: [batch]
        exporters:  [otlp]
```
Then install with those values:
```bash
helm install otel-collector open-telemetry/opentelemetry-collector \
  -n monitoring -f otel-values.yaml
```
Read the config back: it's the three-stage pipe from the concept box — *receive* OTLP spans on ports
4317/4318, *batch* them, *export* to Tempo. The `service.pipelines.traces` block is what actually connects
the three stages into one flow.

### Step 2c — Make sure your apps send to the Collector
Your services emit spans already; they just need the Collector's address. They read the standard env var
`OTEL_EXPORTER_OTLP_ENDPOINT`. Set it in each Deployment (or the shared ConfigMap):
```bash
# the Collector's in-cluster gRPC address
OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector-opentelemetry-collector.monitoring.svc.cluster.local:4317
```
Add that env var to `checkout` (and the rest), then restart so it's picked up:
```bash
kubectl -n shop set env deploy/checkout \
  OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector-opentelemetry-collector.monitoring.svc.cluster.local:4317
kubectl -n shop rollout status deploy/checkout
```
What to expect: after a few requests, traces start arriving in Tempo. If none show up, check the Collector's
logs (`kubectl -n monitoring logs deploy/otel-collector-opentelemetry-collector`) — "connection refused" to
Tempo means the exporter endpoint is wrong; no incoming spans at all means the app's endpoint env var didn't
take.

### Step 2d — Point Grafana at Tempo
**Connections → Data sources → Add → Tempo**, URL
`http://tempo.monitoring.svc.cluster.local:3100`, **Save & test**. Now Grafana can read traces.

## Step 3 — Correlate: one checkout, three views

This is the moment it all pays off. You'll generate a checkout, then travel metric → log → trace using the
shared `trace_id`.

### Step 3 — Wire the log↔trace link in Grafana
> What's happening here: you tell Grafana's Loki data source "the `trace_id` field in a log line is a link —
> when I click it, open that trace in Tempo." This is the one bit of glue that makes the pillars clickable.

In the **Loki** data source settings, add a **Derived field**:
- Name: `trace_id`
- Type: regex or JSON — match the `trace_id` value in your JSON logs
- Internal link → data source: **Tempo**

Save. Now every Loki log line that has a `trace_id` shows a clickable button that jumps straight to that
trace in Tempo. (Optionally, set Tempo's "Trace to logs" the other way so a span links back to its logs —
filtered by `trace_id` and time. Now it's round-trip.)

### Step 3b — Drive a checkout and follow the thread
> What's happening here: make a real checkout, find its logs, click through to its trace.

```bash
# hit checkout through its ingress/ALB (use your real host from Phase 03/05)
curl -X POST http://$SHOP_HOST/checkout -H 'Content-Type: application/json' \
     -d '{"cart_id":"demo-1","payment":"card"}'
```
Now in Grafana **Explore → Loki**:
```logql
{namespace="shop", app="checkout"} | json
```
Find your checkout's line. It carries a `trace_id` like `4bf92f3577b34da6...`. Click the `trace_id` button →
Grafana opens that **trace in Tempo**: a waterfall of spans showing checkout → cart → payment, with the
duration of each hop. If payment was the slow one, you'll *see* the long bar there.

To go the other direction, you already have the metric from `7.1`: a spike in checkout's p95 latency →
**Explore → Tempo**, search traces by service `checkout` ordered by duration → open the slowest → its span
links back to the exact log lines. Metric to trace to log, all by the same id.

## Verify (the whole part is done when…)
- `kubectl -n monitoring get pods` shows `loki-0`, one `promtail-*` per node, `tempo-*`, and the
  `otel-collector-*` pod, all `Running`.
- In Grafana **Explore**, a LogQL query like `{namespace="shop", app="checkout"} | json` returns real JSON
  log lines, each with a `trace_id`.
- Clicking a log line's `trace_id` opens the matching trace in Tempo, showing the checkout's spans across
  services.
- From that trace you can get back to the underlying log lines — round-trip correlation works.
