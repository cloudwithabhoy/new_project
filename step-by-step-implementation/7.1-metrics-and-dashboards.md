# 7.1 — Metrics & dashboards (Prometheus · Grafana · ServiceMonitor)

## Goal
Right now your 6 services are running (Phase 03), routed through Istio (Phase 05), and even auto-scaling on
custom metrics (Phase 06) — but you can't *see* any of it. You have no graph of how many requests `checkout`
is serving, how slow they are, or whether a node is running out of CPU. In this part you install
**Prometheus** to collect those numbers and **Grafana** to draw them, then build three dashboards: RED per
service, USE per node, and the Istio mesh view.

## Why this part exists (read this first)
Back in Phase 06 your HPA scaled `checkout` on a custom metric — but where did that number *come from*?
Something had to be collecting it. That something was Prometheus, and so far it's been a black box you leaned
on without seeing. This part opens the box.

Think of your cluster as a factory floor that's now fully running, but with no instruments on the wall. The
machines (your pods, your Envoy sidecars, your nodes) are already shouting their numbers — your apps emit
RED-style metrics on `/metrics`, and every Istio sidecar emits request metrics for free — but nobody is
writing them down or charting them. Two programs fix that:

- **Prometheus** = the meter reader who walks the floor every 15 seconds, stops at each machine's gauge,
  and writes the current number in a ledger with a timestamp. Do that forever and you have history.
- **Grafana** = the control-room wall of charts. It doesn't collect anything itself; it asks Prometheus
  "give me `checkout`'s request rate for the last hour" and draws the line.

You'll install both at once with the **kube-prometheus-stack** Helm chart, then teach Prometheus *which*
`/metrics` endpoints to read using a **ServiceMonitor**, then build the dashboards that turn raw numbers into
"is the shop healthy right now?"

> NEW CONCEPT — what is a "metric" / "time series"?
> A **metric** is a single named number that changes over time, like `http_requests_total`. Prometheus
> doesn't store just the latest value — it stores a **time series**: the same metric sampled again and again,
> each sample stamped `(timestamp, value)`. A metric also carries **labels** — key/value tags like
> `{service="checkout", method="POST", status="500"}` — so `http_requests_total` isn't one series, it's one
> series *per unique label combination*. That's how you later ask "just the 500s on checkout" without a
> separate metric for it: you filter by label. This labelled time-series model is the whole foundation —
> everything else here is just collecting, filtering, and drawing these series.

## Step 1 — Install Prometheus + Grafana in one shot (kube-prometheus-stack)

> Prometheus = the meter reader who walks every service every 15s and writes down each gauge with a
> timestamp. Grafana = the control-room wall that charts what the meter reader wrote.

We don't install them piece by piece. The **kube-prometheus-stack** chart bundles Prometheus, Grafana,
Alertmanager (you'll use that in `7.3`), and the **Prometheus Operator** — plus pre-built dashboards for the
cluster itself. One install, batteries included.

> NEW CONCEPT — the Prometheus Operator (why a chart, not raw config). Classic Prometheus is configured by
> hand-editing one big `prometheus.yml` file listing every scrape target — painful in a cluster where pods
> come and go. The **Operator** replaces that file with Kubernetes objects: you create a **ServiceMonitor**
> (Step 2) and the Operator rewrites Prometheus's config for you and reloads it. Same controller/reconcile
> pattern you met in `2.2` — declare intent as a Kubernetes object, a controller makes it real. That's why
> we install the whole stack instead of a bare Prometheus.

### Step 1 — Add the Helm repo and install the stack
> What's happening here: you add the community chart catalog, then install everything into a fresh
> `monitoring` namespace with a few values turned on so it scrapes broadly and we can log into Grafana.

```bash
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update

helm install kube-prom-stack prometheus-community/kube-prometheus-stack \
  -n monitoring --create-namespace \
  --set prometheus.prometheusSpec.serviceMonitorSelectorNilUsesHelmValues=false \
  --set prometheus.prometheusSpec.podMonitorSelectorNilUsesHelmValues=false \
  --set grafana.adminPassword='change-me-now'
```
Read this in plain English: "Install the chart as a release named `kube-prom-stack` into a new `monitoring`
namespace." The two `...SelectorNilUsesHelmValues=false` flags are the important ones: by default the
Operator only picks up ServiceMonitors that carry a special label from this chart. Setting these to `false`
tells Prometheus "watch for **any** ServiceMonitor in the cluster, not just my own" — so the one you write in
Step 2 actually gets noticed. `grafana.adminPassword` sets the Grafana login (user is `admin`); change it.

What to expect: a dozen-ish pods come up over a minute or two. Check them:
```bash
kubectl -n monitoring get pods
```
You want `prometheus-kube-prom-stack-kube-prometheus-0`, `kube-prom-stack-grafana-...`, and
`alertmanager-...` all `Running`. If a pod is `Pending`, it's almost always disk — Prometheus asks for a
**PersistentVolume**; confirm your EBS CSI driver / `gp3` StorageClass from earlier phases exists with
`kubectl get sc`.

### Step 1b — Open Grafana and Prometheus in your browser
These run *inside* the cluster, so port-forward them to your machine to look:
```bash
# Grafana on http://localhost:3000  (login admin / the password you set)
kubectl -n monitoring port-forward svc/kube-prom-stack-grafana 3000:80

# in another terminal — Prometheus's own UI on http://localhost:9090
kubectl -n monitoring port-forward svc/kube-prom-stack-kube-prometheus 9090:9090
```
Open `http://localhost:3000`. The stack already ships cluster dashboards — click around "Kubernetes /
Compute Resources" to confirm data is flowing. That data is the cluster's own metrics; next you make
Prometheus also read *your apps'* metrics.

## Step 2 — Tell Prometheus to scrape your app's `/metrics` (ServiceMonitor)

> A ServiceMonitor = a sticky note that tells the meter reader "also visit every pod behind *this* Service,
> on this port, at this URL path, every 15 seconds."

Your apps already expose RED-style metrics — go look:
```bash
kubectl -n shop port-forward deploy/checkout 8080:8080 &
curl -s localhost:8080/metrics | head -20    # you'll see http_requests_total, http_request_duration_seconds, etc.
```
Prometheus *can* read that, but it doesn't know the endpoint exists yet. You announce it with a
ServiceMonitor.

> NEW CONCEPT — scraping, and the pull model. Most monitoring you've heard of is **push**: the app sends its
> numbers somewhere. Prometheus is the opposite — **pull**: Prometheus reaches out and *fetches* `/metrics`
> from each target on a schedule. This sounds like a detail but it shapes everything. Because Prometheus
> initiates, it always knows the full list of who *should* exist (it reads that list from Kubernetes) — so a
> target that goes silent is instantly visible as "down," instead of just... no data arriving and nobody
> noticing. Pull also means your app doesn't need to know where Prometheus is, can't accidentally flood it,
> and `/metrics` is just a plain HTTP page you can `curl` yourself to debug. That's why it fits a cluster of
> ephemeral pods: the source of truth for "who exists" is Kubernetes, and Prometheus pulls from that list.

> NEW CONCEPT — what a ServiceMonitor actually is. It's a small Kubernetes object (added by the Operator)
> that says: "find every Service matching *these labels*, and scrape the pods behind it on *this port* at
> *this path*." The Operator reads it and writes the corresponding scrape job into Prometheus's config for
> you. You never edit `prometheus.yml`. The selector is the key part — it matches your **Service's** labels,
> and Prometheus then scrapes each pod the Service points at.

### Step 2 — Write a ServiceMonitor for your services
First make sure your `checkout` Service names its metrics port (the ServiceMonitor matches the port by
name). If your Service from Phase 03 doesn't, add a named port:
```yaml
# excerpt of svc/checkout — the metrics port needs a NAME
ports:
- { name: http, port: 8080, targetPort: 8080 }
```
Now create the ServiceMonitor. Run `nano checkout-servicemonitor.yaml`, paste:
```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: checkout
  namespace: monitoring            # the Operator watches all namespaces, so monitoring is fine
  labels: { release: kube-prom-stack }
spec:
  namespaceSelector:
    matchNames: ["shop"]           # look for the Service over in the shop namespace
  selector:
    matchLabels: { app: checkout } # match the checkout Service by its label
  endpoints:
  - port: http                     # the NAMED port from the Service above
    path: /metrics                 # where your app exposes them
    interval: 15s                  # how often the meter reader visits
```
Then apply it:
```bash
kubectl apply -f checkout-servicemonitor.yaml
```
Read it back: "Go to the `shop` namespace, find the Service labelled `app: checkout`, and every 15 seconds
scrape `/metrics` on its `http` port." The `labels: { release: kube-prom-stack }` is a courtesy that matches
the chart's convention — harmless, and handy if you later re-tighten the selector you loosened in Step 1.

What to expect: within ~30 seconds Prometheus picks it up. Confirm in the Prometheus UI
(`http://localhost:9090`) under **Status → Target health** — you should see a `checkout` target listed as
`UP`. If it's missing, the selector labels don't match your Service; if it's `DOWN`, the port name or path is
wrong — `curl` the pod's `/metrics` again to confirm the real path.

> You'll have one ServiceMonitor per service, but they're copy-paste: change `name`, the `matchLabels` app,
> and the port name. Or, since all your services share a label convention, write a single ServiceMonitor with
> a broader selector (e.g. `matchLabels: { 'app.kubernetes.io/part-of': ecom }`) to catch them all at once.

### Step 2b — You're already getting Istio metrics for free
Because Phase 05 put an Envoy sidecar next to every pod, each sidecar emits `istio_requests_total` and
latency histograms *without your app doing anything*. The stack's Istio integration (or a ServiceMonitor on
the `istio-system` `envoy-stats` port) surfaces these. Confirm in Prometheus:
```promql
istio_requests_total{destination_service_name="checkout"}
```
This is gold: it's request/error/latency data measured at the *proxy*, so it's consistent across every
service whether or not the app instruments itself.

## Step 3 — Build the dashboards (RED per service, USE per node, Istio mesh)

Now Grafana has the data; you make it legible. Two classic recipes decide *what* to chart.

> NEW CONCEPT — RED vs USE (two ways to ask "is it healthy?"). These are two complementary lenses:
> - **RED** is for *services* (things that handle requests). Chart three numbers per service:
>   **R**ate (requests/sec), **E**rrors (failed requests/sec), **D**uration (latency, usually p50/p95/p99).
>   RED answers "are my users having a good time?"
> - **USE** is for *resources* (things that get consumed — CPU, memory, disk, network). Chart:
>   **U**tilization (how busy), **S**aturation (how much queued/waiting), **E**rrors. USE answers "is the
>   machine about to fall over?"
> You want both because they catch different failures: RED shows the symptom (checkout got slow), USE often
> shows the cause (the node's CPU is saturated). Phase 06's HPA literally scales on the R and D of RED.

> NEW CONCEPT — what is PromQL? You don't pick a metric from a menu; you *query* for it.
> **PromQL** is Prometheus's query language. A few shapes you'll use constantly:
> - `http_requests_total{service="checkout"}` — a counter's raw value (only ever goes up; not useful alone).
> - `rate(http_requests_total[5m])` — the per-second rate over a 5-minute window. **`rate()` is how you turn
>   an ever-increasing counter into a "requests per second" line** — you'll wrap almost every counter in it.
> - `histogram_quantile(0.95, sum(rate(http_request_duration_seconds_bucket[5m])) by (le))` — the p95 latency
>   from a histogram metric. `le` ("less-than-or-equal") buckets are how histograms store a distribution.
> Grafana panels are just saved PromQL queries with a chart attached.

### Step 3 — RED dashboard for a service
> What's happening here: you build one row with three panels — Rate, Errors, Duration — for `checkout`,
> using PromQL against the metrics Prometheus is now scraping.

In Grafana: **Dashboards → New → New dashboard → Add visualization → pick the Prometheus data source.** Add
three panels with these queries:

```promql
# Rate — requests per second
sum(rate(http_requests_total{service="checkout"}[5m]))

# Errors — 5xx per second (the bad ones)
sum(rate(http_requests_total{service="checkout", status=~"5.."}[5m]))

# Duration — p95 latency in seconds
histogram_quantile(0.95,
  sum(rate(http_request_duration_seconds_bucket{service="checkout"}[5m])) by (le))
```
Read the Errors one: `status=~"5.."` is a **regex label match** — "status code starting with 5", i.e. all
server errors. The Duration one reassembles the p95 from histogram buckets. Save the dashboard as
"RED — checkout". To cover every service instead of one, replace the fixed `service="checkout"` with a
Grafana **template variable** `$service` and add a dropdown — one dashboard, pick any service.

If you'd rather not hand-build it, the Istio sidecar metrics give you the *same* RED numbers measured at the
proxy. Either source works; app metrics are richer (your own labels), proxy metrics are uniform.

### Step 3b — USE dashboard for nodes
> What's happening here: a row showing each node's CPU/memory utilization and saturation, from the
> `node-exporter` the stack installed on every node.

The chart already runs **node-exporter** (the agent that exposes per-node `/metrics`), so the data is there.
Add panels:
```promql
# Utilization — CPU busy fraction per node (1 minus idle)
1 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m]))

# Saturation — run-queue pressure (load average vs core count is a fine proxy)
node_load1

# Memory utilization — used fraction
1 - (node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes)
```
Honestly, the stack ships a node dashboard already ("Node Exporter / Nodes") — open it and you'll see USE for
free. Building your own once is still worth it so you understand what the panels mean.

### Step 3c — Import the Istio mesh dashboard
> What's happening here: instead of building the mesh view by hand, you import a community dashboard by its
> ID — it's pre-wired to the `istio_*` metrics your sidecars emit.

In Grafana: **Dashboards → New → Import**, enter dashboard ID **7639** (the official "Istio Mesh" dashboard),
pick your Prometheus data source, **Import**. You instantly get global request volume, success rate, and p50/
p90/p99 latency across the whole mesh, plus a per-service breakdown. There are companion IDs for the Service
(7636) and Workload (7630) views — import those too. This is the fastest way to see the entire shop's health
on one screen.
